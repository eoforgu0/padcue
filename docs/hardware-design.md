# Nintendo Switch 2 自動操作システム 設計文書

作成日: 2026-07-27 ／ 対象: Nintendo Switch 2(工場出荷状態)

**構成**: 本編(1〜9章)に方法論と選定理由を記載し、判断の根拠となる数値・技術詳細
は付録(A〜I)に分離した。

---

## 本編

### 1. 目的とスコープ

#### 1.1 目的

Nintendo Switch 2 のゲーム操作を、PC からの指示に基づいて自動化する。対象は
60fps のゲーム全般であり、**特定タイトルに依存しない汎用システムとする**。

想定用途は、周回によるアイテム収集など長時間の反復作業の代行と、入力タイミングの
正確さを要する動作確認である。ただしこれらは UI や追加機能を検討する際の参考であ
り、システムの根幹はいずれの用途にも依存しない。

利用者は開発者本人であり、不特定多数への配布は想定しない。ただし手順の追加・変更
は日常的に発生するため、**その反映が容易であることを重視する**。

#### 1.2 利用者にとっての価値

設計判断の際は、以下の優先順位で考える。

1. **狙った操作が確実に実行される** — タイミングのずれで手順が破綻しないこと(R1
   の実質的な意味)
2. **手順の試行錯誤が速い** — 手順を書き換えて再実行するまでの手数が少ないこと
3. **放置できる** — 長時間の無人運用に耐え、異常時に暴走しないこと

#### 1.3 スコープ

| 範囲     | 内容                                                                                                                              |
|----------|-----------------------------------------------------------------------------------------------------------------------------------|
| 含む     | 手順データの作成・転送・保存、実行と停止、コントローラーとしての動作、異常時のログ送信、ファームウェア更新、複数台の同時運用(2台) |
| 含まない | ゲーム内容の解析                                                                                                                  |

**画面認識の位置づけ**: 当初はキャプチャボードによる画面認識を補助的に使う想定だっ
たが、**実装していない**。固定待機と「待って選ぶ」(待機分岐)で足りており、画面認
識を主軸にしない方針は変えていない(7.3)。

**PC 側の UI 形式**: ブラウザで動く操作画面に決着した(design/gui-principles.md)。
手順は画面で作り、保存形式は JSON と CSV(specs/flow-format.md)。

#### 1.4 用語

| 用語               | 定義                                                                                                                                                             |
|--------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **手順データ**     | 一連の操作を記述したデータ。ボタン・スティック(およびモーション)の状態と時間経過を表現する。PC で作成しマイコンへ転送する。分岐を含む場合の表現形式は 7.5 を参照 |
| **シーケンス実行** | マイコンが手順データを解釈し、USB レポートとして順次出力する処理                                                                                                 |
| **転送層**         | USB ディスクリプタとレポート生成を担う層(7.2)                                                                                                                    |
| **アプリ層**       | 実行エンジン・WiFi・OTA・データ管理を担う層(7.2)                                                                                                                 |

### 2. システム概要

PC から指示を受けたマイコンが、Nintendo Switch 2 に有線接続されたコントローラー
として動作し、あらかじめ登録された操作手順を高い時間精度で実行する。

```text
[PC] ---- WiFi ---- [マイコン] ---- USB 有線 ---- [Switch 2 ＋ 純正ドック]
```

PC は手順データの作成・転送と実行/停止の指示のみを担い、**実行中のタイミング制御
には関与しない**。マイコンが手順データを保持し、自身のハードウェアタイマーで自律
実行する。

### 3. 要件

要件は3層に分かれる。**R1 が唯一の第一原理**であり、D 系は R1 から演繹された設計
上の帰結、W 系は運用上の要望である。

#### R. 本要件

| #      | 内容                                                               |
|--------|--------------------------------------------------------------------|
| **R1** | **入力精度が最優先**。以降のすべては R1 を毀損しない範囲で採用する |

**R1 が意味する範囲**: R1 は「意図した時刻に入力を送出すること」を指し、「ゲーム
が意図どおりのフレーム数として受け取ること」までは保証しない。後者はゲーム側のサ
ンプリング位相が不明なため確率的にずれる。ただし**そのずれの発生頻度は送信精度に
反比例して下がる**ため、精度向上には常に価値がある(付録 A-1・A-2)。

#### D. R1 から導かれる帰結

これら自体を要件として定義したものではなく、R1 を満たすために選択の余地なく決まっ
た事項である。

| #      | 内容                                                       | 導出理由                                                                                                   |
|--------|------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| **D1** | Switch とマイコンは**有線接続**とし、接続したまま運用する  | 無線接続では入力粒度が 60Hz(16.7ms)に固定され、ゲームのフレーム量子化と同オーダーの不確かさが加わる(付録B) |
| **D2** | 手順データは**マイコン側に保持**し、マイコン単体で実行する | 1入力ごとに PC から逐次指示すると、OS のスケジューラジッタ(1〜15ms)が全入力に加算される(付録A)             |

#### W. 運用要望

| #      | 内容                                                                                               |
|--------|----------------------------------------------------------------------------------------------------|
| **W1** | PC から手順データを作成・転送できる(ファームウェア再書き込みを伴わない)                            |
| **W2** | PC から実行開始・停止を指示できる                                                                  |
| **W3** | マイコンから PC へ異常時のログを送信できる。また PC からファームウェアを更新(OTA)できると なお良い |
| **W4** | **ジャイロ操作**ができると なお良い                                                                |

**W4 の扱い(設計原則)**: W4 は必須条件ではなく、実現できなくてもプロジェクトは成
立する。ただし**設計上のデフォルトは「実現できる」側に倒す**。すなわち、ジャイロ
を断念する具体的な理由が生じるまで、ジャイロ非対応の選択肢は採らない。既存の公開
情報から実装可能と見込まれるため、当初から対応する前提で設計する。

#### 許容条件

- PC ⇔ マイコン間は**遅延不問**
- 画面確認は**必須ではない**。固定待機で足りる場面が基本であり、必要な箇所でのみ
  選択的に使用する(キャプチャボードは所持済み、数秒の遅延を許容)
- 費用・初期構築の手間は不問

#### 運用シナリオ例(典型例)

Switch に接続したまま、以下のような操作が繰り返される。

1. コントローラー登録手順を1回実行
2. 周回手順をループ実行
3. PC から中断を指示
4. 終了手順を1回実行

**手順データの転送と実行は時間的に分離される**(実行中に別の手順データを流し込む
必要はない)。この性質が 7.4 の設計制約の前提となる。

ただし手順そのものは直線的とは限らず、実行中に分岐が生じる場合がある(7.5)。

### 4. 前提・環境制約

- **Switch 2 向けのカスタムファームウェアは存在しない**(2026年7月時点)。本体メモ
  リを直接読む方式は選択肢外であり、外部から得られる情報は画面・振動・音に限られ
  る(付録C)
- Switch は USB 接続のライセンス品コントローラーを認識する。ただし本体設定「Pro
  コントローラーの有線通信」が工場出荷時 OFF であり、ON にしない限り USB 接続の
  コントローラーは認識されない(2026-07 任天堂公式サポートで確認)。マイコンによる
  自動化は、この既存のコントローラー仕様に沿ったデバイスとして動作させる方式が主
  流である
- **ゲームは 16.7ms(60fps)ごとに入力を読み取る**。これがフレーム数の分解能の下限
  だが、送信精度を高めるほどフレーム境界でのずれの発生頻度は下がるため、**精度は
  高いほど良い**(付録 A-1・A-2)
- 利用規約上の制約があり、オフライン／ローカル用途に限定する(付録G)

### 5. アプローチの選定

| アプローチ                          | 入力粒度       | ジャイロ          | 公開情報            | Switch 2 実績       | 判定     |
|-------------------------------------|----------------|-------------------|---------------------|---------------------|----------|
| **有線USB・Pro コントローラー方式** | 優 1ms 宣言可  | 可 対応可         | 可 Linux 実装例あり | 可                  | **採用** |
| 有線USB・HID ゲームパッド方式       | 優 同上        | 不可 構造的に不可 | 優 豊富             | 可                  | 却下     |
| 無線BT・Pro コントローラー方式      | 不可 60Hz 固定 | 可                | 可                  | 難 接続不安定の報告 | 却下     |
| 本体メモリ直接読み取り              | -              | -                 | -                   | 不可 前提が不成立   | 却下     |
| 物理押下(サーボ等)                  | 不可           | -                 | 難                  | 可                  | 却下     |


**選定理由**

R1 により無線方式が脱落する(付録B)。本体メモリ方式は Switch 2 で前提が成立せず、
物理押下は精度で論外。

残る有線 USB の2方式のうち、HID ゲームパッド方式はレポートフォーマットにモーショ
ン用の領域が存在せず、W4 を構造的に満たせない。**W4 の設計原則(3章)により、ジャ
イロ非対応の選択肢は採らない**ため却下する。

Pro コントローラー方式は Linux 上の実装例とプロトコル技術文書が公開されており、
新規のプロトコル調査を要さず実装可能と見込まれる。HID ゲームパッド方式に対する機
能的上位集合であるため、**Pro コントローラー方式に一本化**する。

**注記(2026-07 調査)**: 表の「Switch 2 実績 可」は、純正 Pro コントローラーの有
線公式対応およびライセンス品有線コントローラーの動作確認に基づく。**自作互換機が
Switch 2 の有線 USB で動作した直接の公開報告は確認できていない**。その確認が 9
章の未検証事項 3 に当たる(なお HID ゲームパッド方式は自作機での Switch 2 動作報
告が複数ある。付録F 参照)。

### 6. マイコンの選定

#### 6.1 チップの選定

| ボード                         | USB デバイス | 手順保持  | 無線    | OTA           | 判定        |
|--------------------------------|--------------|-----------|---------|---------------|-------------|
| ATmega32U4(Leonardo 等)        | 可           | 難 32KB   | 不可    | 不可          | 不可        |
| ATmega16U2(Uno R3)             | 可           | 不可 16KB | 不可    | 不可          | 不可        |
| RP2350(Pico 2 W)               | 可           | 可        | 可      | 可 公式実装例 | 次点        |
| **ESP32-S3**                   | 可 OTG       | 可        | 優 WiFi | 優 IDF 標準   | **採用**    |
| ESP32 その他(S2/C3/C6/P4/無印) | 各々に欠落   |           |         |               | 不可(付録D) |
| Raspberry Pi(USB Gadget)       | 可           | 可        | 優      | 優 ssh        | 次々点      |

**選定理由**

D1・D2 と W1〜W3 より「USB デバイス機能＋無線＋手順データ保持」の同時成立が必要
であり(OTA は任意だが標準機能として備わることが望ましい)、AVR 系(Leonardo / Uno
/ Teensy)は無線を持たず全滅する。

ESP32 系で USB デバイス機能を持つのは S2 / S3 / C6 のみだが、S2 と C6 は単コアの
ため無線処理と実行タスクをコア分離できず R1 に不利であり、**S3 に確定**する(消去
法の全体は付録D)。

Pico 2 W(RP2350)は OTA を含め機能上ほぼ同等であり、次点として成立する(付録E)。
Raspberry Pi は要件を満たし Pro コントローラー方式の実装例も持つが、OS のスケジ
ューラジッタ・SD カードの脆弱性・起動時間の分だけ R1 と常時接続運用に対して不利
であり、ESP32-S3 での実装が困難と判明した場合の移行先とする(付録F)。

#### 6.2 ボードの選定

**M5Stack AtomS3 Lite** を採用する。

条件を満たすボードは複数存在し(付録H)、いずれも機能・性能に実用上の差はない。し
たがって選定基準は**設置しやすさと価格**となる。

| 選定理由   | 内容                                                                                 |
|------------|--------------------------------------------------------------------------------------|
| 筐体付き   | 24.0 × 24.0 × 9.5 mm のプラスチック筐体。基板露出品と異なり絶縁処理が不要            |
| 設置安定性 | 立方体形状で据わりが良く、背面 M2 ネジ穴で固定できる                                 |
| 仕様充足   | ESP32-S3FN8 デュアルコア、8MB フラッシュ、WiFi 内蔵、ネイティブ USB を Type-C に露出 |
| 価格       | 約 ¥1,600。条件を満たす候補中で最も安価                                              |

**USB は1系統**: ログは WiFi 経由で送信するため運用上の支障はない。開発期間中の
ファームウェア書き込み時のみ、Switch から抜いて PC に接続する必要がある(OTA 稼働
後は解消)。他候補との比較は付録H を参照。

### 7. システム構成

#### 7.1 責務の分担

| 要素                               | 責務                                                                                                     |
|------------------------------------|----------------------------------------------------------------------------------------------------------|
| **AtomS3 Lite / コア0**            | WiFi 通信、手順データの受信・保存、実行/停止コマンドの受理、ログ送信、OTA                                |
| **AtomS3 Lite / コア1**            | USB デバイス処理(TinyUSB・Pro コントローラー互換・bInterval=1)、シーケンス実行(ハードウェアタイマー駆動) |
| **PC**                             | 手順データの作成・転送、実行/停止の指示。**タイミング経路には関与しない**                                |
| **キャプチャボード**(所持済・任意) | 固定待機で不足する箇所でのみ、画面一致確認による再同期に使用                                             |

#### 7.2 レイヤー構成

```text
+--------------------------------------------+
| アプリ層                                   |
|  実行エンジン / WiFi / OTA / データ管理    |
+--------------------------------------------+  <- 層の境界
| 転送層                                     |
|  USB ディスクリプタ / レポート生成         |
+--------------------------------------------+
```

**両層を明確に分離して実装する。** 将来 Raspberry Pi へ移行する場合(付録F)、書き
直しは転送層のみに限定され、アプリ層は流用できる。

#### 7.3 精度設計

1. **bInterval=1 を宣言する** — 入力反映の不確かさを 5ms から 1ms へ低減する。こ
   れによりフレーム境界でのずれの発生確率が約 30% から約 6% へ下がる(付録 A-2)。
   実質的なデメリットはないが、実在製品と異なる値のためビルド時に 5ms へ戻せる構
   成としておく
2. **マイコン自律実行**(D2 の実装) — 実行中は PC と通信せず、ハードウェアタイマー
   のみでシーケンスを進める。タイミングは**開始時刻からの絶対時刻で算出**し、相
   対時刻の積み上げにしない(付録 A-3)
3. **ウォッチドッグ** — 制御断・異常時は全入力をニュートラルへ復帰させる
4. **フレーム単位の表現** — 対象が 60fps である以上、手順データの時間はフレーム
   単位で表現できること。これは利便性のためだけでなく、**フレーム周期の整数倍で
   なければフレーム数が位相依存になる**ため(付録 A-2)。フレーム周期そのものは設
   定値として持ち、実機で調整できることが望ましい
5. **異常の記録** — エラー、クラッシュ、ウォッチドッグ作動、USB の切断、および**タ
   イマーが想定時刻を超えた場合**を記録し PC へ送信できること。正常時の全フレー
   ムを記録する必要はない(付録 A-4)
6. **選択的な画面確認** — 固定待機を基本とし、ロード時間のブレが問題になる箇所で
   のみ画面一致確認を挟む(付録G)

**前提として理解しておくべき原理的な限界**: 上記をすべて実施しても、ゲーム側のサ
ンプリング位相が不明であるため、N フレームの指示に対し実際は N−1 〜 N+1 フレーム
の範囲でばらつく。これは入力精度を高めても解消しない。詳細と実装上の指針は**付録
A-1 を必ず参照すること**。

#### 7.4 通信の設計制約

| 通信                    | 実行タイミング             | USB 接続への影響             | 制約                                                   |
|-------------------------|----------------------------|------------------------------|--------------------------------------------------------|
| 実行/停止指示           | 自動操作の実行中に随時     | なし(RAM 上のフラグ操作のみ) | -                                                      |
| ログ送信                | 異常発生時                 | なし                         | 記録対象は異常のみ(付録 A-4)。送信は実行ループ外で行う |
| 手順データ転送          | 自動操作の実行前           | **実行中に行ってはならない** | 下記参照                                               |
| ファームウェア更新(OTA) | 自動操作をしていない時のみ | 再起動により切断される(許容) | 実行中は行わない                                       |

**フラッシュ書き込みに関する制約**: ESP32 ではフラッシュ書き込み中にキャッシュが
無効化され、他のコードの実行が一時停止する。この間 USB のレポート送信も止まるた
め、**自動操作の実行中に手順データをフラッシュへ書き込んではならない**。受信デー
タは一旦 RAM に保持し、実行停止中にフラッシュへ反映する。運用シナリオ(3章)では転
送と実行が時間的に分離されるため、この制約は自然に満たされる。

**OTA 後の再接続**: OTA 完了時の再起動で USB 接続は一度切断される。Switch 側が自
動的に再認識するかは未検証のため、**OTA 後はドックへの挿し直しを要する場合がある**前
提とする。OTA は自動操作をしていない時にのみ実行するため、運用上の支障はない。

#### 7.5 実行フローの分岐(設計上の論点)

手順は直線的なシーケンスとは限らず、実行中に分岐が生じる場合がある。**分岐は待機
の有無で性質が大きく異なる**ため、区別して扱う必要がある。

| 種別         | 例                                                     | 待機                    | 精度への影響                 |
|--------------|--------------------------------------------------------|-------------------------|------------------------------|
| **外部分岐** | 画面認識の結果による分岐、ユーザーの判断による分岐     | あり(PC との往復を伴う) | 待機箇所なので影響しない     |
| **内部分岐** | 周回回数による分岐(奇数回目と偶数回目で操作を変える等) | なし                    | **フレーム精度を毀損しうる** |

**内部分岐が論点となる理由**: 待機を伴わないため、分岐の判定自体がフレーム精度に
影響する。マイコン内の変数を参照して次を選ぶだけなら µs で済むが、判定のたびに
PC へ問い合わせる実装にすると成立しない。

**考えられる方針(いずれも未検証)**

- 外部分岐: 待機が発生するため、判定後に次の手順データを送信する方式が取りうる
- 内部分岐: 手順データに制御フローを持たせる、あるいは繰り返し回数分を展開して1
  つの手順データにまとめる

いずれも一案に過ぎない。**これらで問題ないのか、他により適した解決策がないか、そ
もそも懸念すべき点が上記だけで足りるのかは検証していない。** ソフトウェア設計時
に、手順データの表現形式とあわせて十分に検討すること。

判断の際は、**内部分岐が実行中のフレーム精度を毀損しないこと**(R1)と、**実行中に

## 付録

### A. 精度の分解と支配要因

入力タイミングの誤差は次の3層の**直列加算**で決まる。

| 層             | 意味                             | 大きさ                                     | 制御可否                                                    |
|----------------|----------------------------------|--------------------------------------------|-------------------------------------------------------------|
| 実行ジッタ     | 「押す瞬間」が予定時刻に来るか   | PC 実行: 1〜15ms ／ マイコン自律: 1µs 未満 | **設計で潰す**(D2)                                          |
| ポーリング間隔 | 押した状態が Switch に伝わる粒度 | ディスクリプタの bInterval 依存: 1〜5ms    | **1ms を宣言する**                                          |
| フレーム量子化 | ゲームが入力を読む周期           | 16.7ms(60fps)／33.3ms(30fps)               | 不可。ただし送信精度を上げると境界でのずれ頻度は下がる(A-2) |

**既存ライブラリが 5ms を採用している理由**: 実在製品のディスクリプタをそのまま
踏襲した結果であり、最適化ではない。実在製品が 1ms にしない理由(電池駆動であるこ
と、人間の操作には 60Hz で十分であること)は、バス給電の自動化機には該当しない。
なお 5ms 採用は AVR/LUFA 系ライブラリの伝統であり、arduino-esp32 の USBHID は
interval=1(bInterval=1ms)を用いて旧 Switch に認識された実績がある(2026-07 ソース
確認)。未検証事項 1 の成功見込みを高める材料となる。

**bInterval=1 のデメリット**: 実質的に存在しない。

| 一般に挙げられる懸念     | 本件での影響                               |
|--------------------------|--------------------------------------------|
| デバイスの消費電力増     | バス給電のため無関係                       |
| ホストの帯域予約が増える | 数十バイト/ms は USB Full Speed に対し些少 |
| ホストの CPU 負荷増      | ゲームパッド1台分では問題にならない        |
| マイコンの割り込み頻度増 | 240MHz デュアルコアに対し無視できる        |

唯一の留意点は実在製品と異なる値を宣言する点であり、Switch 側の受容は実機確認を
要する。このためビルド時に 5ms へ戻せる構成としておく。

**その他**: Windows の既定タイマ分解能は約 15.6ms であり、PC を実行経路に置くと
これを被る(D2 の根拠)。水晶発振の誤差(±20〜50ppm ≒ 1時間で 0.2 秒)は個別の待機時
間に対しては無視できる。

#### A-1. フレーム境界での欠落・重複(原理的な限界)

**入力精度をどれだけ高めても解消できない問題**があり、実装前に把握しておく必要がある。

ゲームは 16.7ms ごとに入力を読み取る(サンプリング)。しかし**そのサンプリング時刻
がいつなのかを、こちらは知る手段がない**。ゲーム側と同期していないため、自分の入
力切り替えがサンプリングの直前に落ちるか直後に落ちるかは不定である。

その結果、「N フレーム押す」という指示に対して次の2種類のずれが起こりうる。

```text
凡例: | = ゲームのサンプリング時刻    v = 入力の切り替え

意図(2F 押す)
  |----|----|----|
    v押     v離      -> 2回サンプリングされる(正しい)

欠落(押下が直後・解放が直前に落ちた場合)
  |----|----|----|
     v押   v離        -> 1回しかサンプリングされない

重複(押下が直前・解放が直後に落ちた場合)
  |----|----|----|
   v押       v離      -> 3回サンプリングされる
```

押下と解放は**それぞれ独立に**前後どちらかへ倒れるため、N フレームの指示に対し実
際は **N−1 〜 N+1 フレーム**の範囲でばらつく。

> **上の図の「欠落」は「1 フレーム分だけ短く見える」という意味であり、「入力その
> ものが現れない」ではない。**混同しやすいので明示する。観測されるフレーム数の**下
> 限は N−1** なので:
> | 指示 | 観測されるフレーム数 | 「まったく押されない」が起きるか |
> |---|---|---|
> | **1F** | **0 〜 2** | **起きる**(下限が 0) |
> | 2F | 1 〜 3 | 起きない |
> | NF | N−1 〜 N+1 | 起きない |
>
> したがって「入力が丸ごと失われる」危険があるのは **N=1 のときだけ**である。
> 2 フレーム以上では長さがぶれるだけで、押されること自体は必ず起こる。
> (この性質は「切り替えが見えるまでの遅れ < 1 フレーム」が前提。実機の遅れは
> 送信の粒度=1ms、保険モードでも 8ms であり 16.7ms より十分小さい。
> 数え上げによる検証: `pctool/tests/test_sampling_model.py`)
>
> リントが 1 フレームのときだけ警告するのはこの区別による。以前は 2 フレームにも
> 警告していたが、上の図の「欠落」を「入力の消失」と読み違えたことによる過剰警告だった。

**重要な点**: これは入力の粒度(bInterval=1ms)や実行ジッタ(µs 未満)とは無関係であ
る。未知なのは自分の精度ではなく**ゲーム側の位相**であり、粒度を細かくしても位相
が判明しない限り解消しない。

**実装上の指針**

- 1F 単位の正確さを要する操作は、**必ず指示どおりに実行されると仮定してはならな
  い**。同じ手順を複数回実行すると結果が変わりうる
- **1F の押下・待機だけは「まったく現れない」ことがある**(下限が 0)。2F 以上にす
  ればこれは無くなる。長さのばらつき(±1F)は残る
- 手順データを作成する際、ユーザーはばらつきを考慮して作成する。フレーム境界に依
  存しない待機時間(前後に余裕のある指示)を基本とする
- 1F の差が結果を分ける場面では、複数回試行して分布を見る以外に確実な方法はない
- ゲーム側の位相を推定する手段は原理的には存在しうるが(画面のフレーム更新タイミ
  ングからの逆算など)、キャプチャ経路の遅延が 16.7ms より大きいため本システムで
  は実用にならない

#### A-2. 誤差の発生確率は送信精度に比例する

A-1 は「ずれが起こりうる」という話であって「必ず起こる」ではない。**発生確率は送
信タイミングの誤差に比例するため、精度を上げれば頻度を下げられる。**

押下から解放までの間隔が**フレーム周期のちょうど整数倍**であれば、その区間に含ま
れるサンプリング点の数は位相によらず一定になる(周期 P のサンプリングにおいて、長
さ N×P の半開区間には必ず N 個の点が含まれる)。つまり位相が不明でもフレーム数は
確定する。

ずれが生じるのは実際の間隔が N×P から外れた場合であり、そのずれ量を ε とすると、
誤差の発生確率はおよそ **|ε| ÷ P** となる。

| 送信間隔の誤差 ε         | 誤差の発生確率(目安) |
|--------------------------|----------------------|
| ±5ms(bInterval=5ms 相当) | 最大 約 30%          |
| ±1ms(bInterval=1ms 相当) | 最大 約 6%           |
| ±0.1ms                   | 最大 約 0.6%         |

**したがって送信精度は高いほど良い。** ただし ε=0 は達成できないため確率をゼロに
はできず、また精度向上が他の性能や機能を損なうなら、その時点で判断すべきトレード
オフとなる。

**成立条件**: この性質は、手順データの時間が**フレーム周期の整数倍で表現されてい
る場合にのみ**成立する。ミリ秒で任意の値を指定すると(例: 30ms ≒ 1.8 フレーム)間
隔が整数倍にならず、位相依存が残る。7.3 でフレーム単位の表現を求めているのはこの
ためである。

**確認すべき事項**: フレーム周期が正確に 1/60 秒(16.6667ms)か、59.94Hz 相当
(16.6833ms)かによって「整数倍」の値が変わる。差は 1 フレームあたり 0.017ms だが、
60 フレーム保持で約 1ms、600 フレームで約 10ms の累積となり無視できない。**フレー
ム周期は設定値として持ち、実機で調整できるようにすることが望ましい。**

#### A-3. 時刻の基準(実装上の助言)

タイミング算出を**相対時刻の積み上げで行ってはならない**。

| 方式               | 算出方法                             | N フレーム後の誤差  |
|--------------------|--------------------------------------|---------------------|
| 相対時刻(**不可**) | 前フレームの実際の送出時刻 + 1/60 秒 | **N × δ**(累積する) |
| 絶対時刻(**推奨**) | 開始時刻 + N/60 秒                   | **δ**(累積しない)   |

δ は 1 回あたりのタイマー誤差。相対方式では各回の誤差が加算され続けるため、長い
手順ほどずれが拡大する。絶対方式なら毎回開始時刻から算出し直すので、誤差は常に単
発分に留まる。

**これは A-2 の誤差率に直結する。** 相対方式で 1000 フレーム後に 10ms ずれていれ
ば、その時点での誤差発生率は約 60% に達する。手順が長くなるほど破綻しやすくなり、
しかも「最初は正しく動くが後半で崩れる」という発見しにくい形で現れる。

#### A-4. ログの範囲

**正常時の入力を全フレーム記録する必要はない。** マイコンが報告できるのは「自身
のタイマーに従って指示どおり送出した」ことのみであり、実際にずれを生むゲーム側の
サンプリング位相(A-1)はマイコンから観測できない。したがって全フレームのログを取っ
ても、知りたいことは分からない。

記録すべきは異常のみである。

| 対象                                   | 目的                           |
|----------------------------------------|--------------------------------|
| エラー、クラッシュ、ウォッチドッグ作動 | 無人運用中の障害把握           |
| USB の切断・再列挙                     | 接続断の検知                   |
| 実行の開始・完了・中断                 | 実行状況の把握                 |
| **タイマーが想定時刻を超えた場合**     | A-3 の累積誤差や処理遅延の検出 |

最後の項目は、想定時刻を超えたときのみ記録する例外ログとする。正常時のコストがゼ
ロであり、実行ループの時間を変動させない。

**この方針であれば、ログ処理が精度を損なう懸念は生じない。** いずれも実行ループ
内で毎回走る処理ではないため、記録先や整形方法に特段の制約を課す必要がない。ただ
し異常の記録が集中した場合に備え、送信は実行ループ外(別コア)で行うことが望ましい。

### B. 有線と無線の比較(D1 の根拠)

- コミュニティのプロトコル技術文書によれば、モーションデータを含む入力レポート
  (0x30, standard full mode)は**無線 60Hz、有線 Pro コントローラーは 120Hz** で
  送信される。レートは有線が上である
- **「有線は経路を余分に挟むため遅い」という通説について**: 実在の Pro コントロー
  ラーは センサー → 内部MCU → 内部の UART 系伝送路 → (Bluetooth | USB) という構
  造であり、有線接続時のハンドシェイクに `0x80 0x03`(ボーレート設定)が含まれるの
  がその構造の反映である。**この内部経路は製品内部のものであり、パケットを直接生
  成する自作デバイスには存在しない**。したがってこの通説は本システムには適用され
  ない
- 自作デバイスは自前のディスクリプタにより bInterval=1(1kHz)まで宣言可能であり、
  実在製品の有線の 8 倍、無線の 16 倍の粒度となる
- 無線側には 2.4GHz 帯の干渉によるジッタ、再送遅延、ペアリングの断続といった追加
  リスクがある

### C. アプローチ各論

**本体メモリ直接読み取り**: 2026年7月時点、Switch 2 向けのカスタムファームウェア・
改造チップは公開されていない。旧 Switch で用いられた手法は成立しない。

**HID ゲームパッド方式でジャイロが不可能な理由**: HID レポートディスクリプタにモー
ション用フィールドが定義されておらず、値を格納する領域自体が存在しない。機能の未
実装ではなく構造的な不可である。

**Pro コントローラー方式の実装要素**:

- `0x80` 系のハンドシェイク(0x01 デバイス情報／0x02／0x03 ボーレート／0x04
  HID-only モード)
- サブコマンド応答
  - 0x02 デバイス情報
  - 0x03 入力レポートモード設定
  - **0x10 SPI フラッシュ読み出し**(一度に最大 0x1D バイト。スティックおよびモー
    ションセンサーのキャリブレーション領域を返す)
  - 0x30 プレイヤー LED
  - 0x40 モーションセンサー有効化
  - 0x48 振動有効化
- `0x21`(サブコマンド応答)／`0x30`(モーションデータを含む全状態)レポートの生成と
  パケットカウンタの維持

**参照可能な情報源**: プロトコル技術文書(無線・有線の両方)、Linux USB Gadget に
よる実装例(付録I)。新規のプロトコル調査は不要である。

**副次的な利点**: Pro コントローラー方式では Switch 側から振動データが送られてく
るため、これをゲーム内イベントの検知に利用できる。画面確認より低遅延であり、本シ
ステムでは必須ではないが将来的な拡張余地となる。

### D. ESP32 ファミリの消去法

| 型番       | USB デバイス機能              | 無線              | コア  | 結論                               |
|------------|-------------------------------|-------------------|-------|------------------------------------|
| 無印 ESP32 | 不可 なし                     | WiFi + BT Classic | 2     | 不可 USB 不可                      |
| C3 / H2    | 不可 Serial/JTAG 固定機能のみ | WiFi+BLE ／ BLE   | 1     | 不可 任意の USB デバイスになれない |
| S2         | 可 OTG                        | WiFi のみ         | **1** | 難 コア分離不可                    |
| **S3**     | 可 OTG                        | WiFi + BLE5       | **2** | **優**                             |
| C6         | 可 デバイス専用               | WiFi6 + BLE       | 1     | 難 単コア・前例なし                |
| P4         | 可 OTG                        | 不可 非内蔵       | 2     | 不可 無線が別チップ必要            |

- **デュアルコアの実益**: WiFi スタックはコア0で動作するため、USB 処理と実行エン
  ジンをコア1に固定すれば通信中も送信タイミングが揺れない。単コア機ではこの分離
  ができず R1 に影響する
- **注意**: Secure Boot ／フラッシュ暗号化を有効にすると ROM の USB-OTG スタック
  が無効化される。本用途では使用しない
- USB データ線は GPIO19(D-)／GPIO20(D+)に固定される。ボード選定時はこれがコネク
  タに引き出されているか確認する
- **USB モードの切り替え**: ESP32-S3 の USB ポートは、既定の USB Serial/JTAG と、
  任意のデバイスとして動作できる USB-OTG(TinyUSB)モードを切り替えられる。ビルド
  設定(Arduino IDE のメニュー、または `ARDUINO_USB_MODE`)で指定するものであり、
  ハードウェア改造は不要である。ただし OTG モードでは書き込み後の自動リセットが
  かからず、再書き込み時はリセットボタンを2秒以上押してダウンロードモードへ戻す
  操作を要する

### E. RP2350(Pico 2 W)との比較

- **OTA は同等**: RP2350 は bootrom が A/B パーティションとバージョンによる起動
  イメージ選択・ロールバックをサポートし、公式 pico-examples に WiFi 経由 OTA の
  実装例(`pico_w/wifi/ota_update`)がある。OTA の自作が必要という制約は RP2040 世
  代の事情であり、RP2350 には当たらない
- **残る差分**: ①フラッシュ 4MB(本用途では十分) ②既存の Switch 制御ライブラリが
  RP2040 向けで移植を要する ③筐体付き製品の選択肢が乏しい
- ESP32-S3 が入手困難な場合の代替として十分に成立する

### F. Raspberry Pi への移行判断(ジャイロ実装が困難な場合)

- ESP32-S3 で Pro コントローラー方式を実装できない**構造的な理由は存在しない**(USB
  コアは他社 MCU でも広く使われる Synopsys DWC2)。したがって「仕様上不可能と判明
  する」事象は想定されない
- **移行の発動条件**: 以下3つがすべて成立した時に限る
  1. ESP32-S3 での実装を実際に試みた
  2. 動作させられない、または工数が見合わないと判断した
  3. ジャイロを断念した場合の不利益が、Pi 移行のコスト(OS ジッタ・SD カード運用・
     起動時間)を上回ると判断した
- **①の前に Pi を購入しない**
- 移行コストは 7.2 のレイヤー分離により転送層のみに限定される
- 補足: 画面を見ない運用でのジャイロ操作は、ゲーム側が角速度を時間積分するため誤
  差が蓄積する。狙った角度への収束が必要な場面では、画面確認による補正が有効とな
  る可能性がある
- 補足(2026-07 調査): 有線 USB・HID ゲームパッド方式はマイコン自作機での Switch
  2 動作報告が複数確認されている。ジャイロを断念する場合、Pi 移行のほかに「**ESP32-S3
  のまま転送層のみ HID ゲームパッド方式へ差し替える**」縮退案が成立する(7.2 の分
  離によりアプリ層・手順データ・OTA 等の資産は温存)。発動条件③の比較はこの縮退案
  を含めて行う

### G. 運用リスクと対策

| リスク                                                                                                                    | 対策                                                                                                   |
|---------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| 利用規約(2025年5月改定で、許諾のない利用に対しデバイスを使用不能にできる旨が明記された)                                   | オフライン／ローカル用途に限定する。オンライン対戦・ランキングでは使用しない                           |
| システムソフトウェア 21.0.0 以降、一部サードパーティ製ドックの動作停止事例がある                                          | 純正ドックを使用する                                                                                   |
| 本体設定「Proコントローラーの有線通信」が工場出荷時 OFF のため、OFF のままでは USB 接続のコントローラーが一切認識されない | 初回セットアップで ON にする(設定 → コントローラーと周辺機器)。本体初期化後は OFF に戻るため再設定する |
| 他のコントローラー接続中はマイコンが 2P 扱いとなり無反応に見える                                                          | 接続時に Joy-Con 等を切断する                                                                          |
| Switch 2 は旧 Switch とロード時間・ホーム画面の挙動が異なり、旧機種向けスクリプトが誤動作する                             | 該当箇所でのみ画面一致確認による再同期を挟む(数秒の遅延で足りる)                                       |
| 無人運用中の異常停止                                                                                                      | ウォッチドッグで全入力をニュートラル化する。本体側は自動スリープ・通知・自動更新を OFF にする          |

### H. ボード候補の比較(6.2 の根拠)

条件(ESP32-S3・ネイティブ USB 露出・WiFi・国内通販容易)を満たす製品は複数存在す
るが、**機能・性能に実用上の差はない**。したがって選定基準は設置しやすさと価格に
なる。

| 分類               | 該当製品                         | 評価                                                            |
|--------------------|----------------------------------|-----------------------------------------------------------------|
| **筐体付き・小型** | **AtomS3 Lite**、AtomS3U         | **採用**。AtomS3U とは形状のみの差で、Lite が安価かつ設置が安定 |
| 筐体付き・多機能   | M5StickS3、CoreS3 系             | 画面・カメラ等の未使用機能が価格の大半を占める                  |
| 筐体なし・1系統    | XIAO ESP32S3                     | 絶縁処理が必要。選ぶ利点がない                                  |
| 筐体なし・2系統    | ESP32-S3-DevKitC-1、kohacraft 製 | 下記参照                                                        |

**2系統品について**: ネイティブ USB と USB シリアルの2ポートを持ち、Switch に接
続したまま書き込みとログ取得ができるため開発期間中は有利。しかし条件を満たす製品
はいずれも筐体を持たない。ログは WiFi で代替でき、書き込みの不便さは OTA 稼働ま
での有限期間に限られるため、恒久的に続く設置性を優先して筐体付きを選択した。

**PSRAM は選定基準にならない**: 手順データは数KB〜数十KB であり内蔵 SRAM で足り
る。PSRAM は内蔵 SRAM よりアクセスが遅く、タイミング重視の処理には用いない。
