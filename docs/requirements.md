# 要件と制約

## 0. 位置づけ

目的(purpose.md)から、要件(R。何ができなければならないか)、制約(C。変えられない環境の事実)、許容条件(要件のうち緩めてよいこと)を導く。対象は purpose.md §6 のとおり Nintendo Switch 2 と初代 Switch で、以下 Switch と書く。

## 1. 要件

### 意図どおりに実行される(purpose.md §1・§4-1 から)

- **R1 時間の正しさ**: 入力は意図した時刻に送られる。時刻の単位はフレーム、すなわち padcue が入力を切り替える時間の単位で、送信時刻の誤差はフレーム周期より十分小さい。手順が長くても誤差は累積しない。(導出: purpose.md §4-1・§3-1 の長時間の反復)
- **R2 状況の正しさ**: 手順は、状況を観測し、それに応じて進んだり選んだりすることを表現できる。状況が確認できないときは進まず、待つか停止する。(導出: purpose.md §4-1)
- **R3**: 判断は時間の正しさを損なわない。判断のために観測や計算を挟んでも、入力の送信時刻はずれない。(導出: R1・R2)
- **R4**: 意図しない入力を出さない。手順にない入力は出ず、停止するときは全入力が離れる。(導出: purpose.md §4-1・§4-2)
- **R5**: コントローラーでできる操作はすべて手順で書ける。ボタン・スティック・モーション(ジャイロ・加速度)を含む。(導出: purpose.md §1)
- **R6**: Switch には通常のコントローラーとして見え、本体にもゲームにも手を加えない。(導出: purpose.md §1・§5)
- **R7**: 手順を書ける。何を、どの順で、どんな状況になったら行うかを書ける。くり返し、再利用できる単位、ラベル(区切り)、判断点、合流点、外部処理の呼び出しを含む。くり返しには名前と、回数を周回数にする指定がある。判断点には、人が選ぶもの、観測で選ぶもの、回数で選ぶものがある。(導出: purpose.md §1・§5)

### 見ていなくても動く(purpose.md §4-2 から)

- **R8**: 人がいなくても続く。周回数を指定でき、無限にもできる。(導出: purpose.md §4-2)
- **R9**: 異常時に暴走しない。装置が自分の異常を検出したら全入力を離して停止する。操作用の PC との通信が途切れても実行は続く。この状態が「未検出」である。操作用の PC とつながっていない状態でも、装置だけでその場で停止できる。(導出: purpose.md §4-2・§5)
- **R10**: 異常が分かる。何が起きたかの記録が残り、「完了」「異常停止」「選択待ち」「未検出」を、画面を見ていなくても知ることができる。(導出: purpose.md §4-2)
- **R11**: 人の関与は必要な箇所だけで済む。人が選ぶ判断点を手順に書くことができ、そこで PC から選べる。(導出: purpose.md §4-2)
- **R12**: 進捗が見える。いまの位置と、くり返しの何回目かが分かる。(導出: purpose.md §4-2・§4-3)
- **R13**: 複数台を一人で同時に運用できる。台数を固定せず、まとめて始めたり止めたりでき、台ごとの進捗が見える。台ごとに独立し、1 台の異常や無応答がほかの台の表示と操作を妨げない。合流点では全台が揃うのを待ってから進められる。(導出: purpose.md §2・§5)
- **R14**: 手順の追加・変更に装置の作り直しを要さない。(導出: purpose.md §4-3。手順は日常的に変わる)

### 試行錯誤が速い(purpose.md §4-3 から)

- **R15**: 手順の作成・変更から実行までの手数が少ない。専用のツールでも、保存したものを直接編集しても作れる。(導出: purpose.md §4-3)
- **R16**: 実行前に「何が、いつ送られるか」が分かる。(導出: purpose.md §4-3・§4-1)
- **R17**: 途中から試せる。開始位置を指定して始められ、停止した位置からも始められる。開始位置は、手順の中の点と、くり返しの何回目かで指定する。一部を外して試せる。(導出: purpose.md §4-3・R12)
- **R18**: 実機がなくても手順を作り、試せる。(導出: purpose.md §4-3)

### 自分で組み立てて使う人(purpose.md §2 から)

- **R19**: 文書だけで、組み立てから日常の運用までたどり着ける。(導出: purpose.md §2)
- **R20**: 入手しやすい市販の部材で作ることができ、特別な設備を要さない。(導出: purpose.md §2)
- **R21**: 装置のファームウェアを、利用者が自分で更新できる。ケーブルをつなぎ替えずに更新できるとなお良い。(導出: purpose.md §2・R14)
- **R22**: 利用者にアドレスなどの管理をさせない。装置は自動で見つかり、利用者は見つかった中から使うものを選ぶだけでよい。(導出: purpose.md §4-3・§2)

### 含むもの・前提とする条件(purpose.md §5・§6 から)

- **R23**: ローカルで完結する。インターネットにも外部のサービスにも依存しない。(導出: purpose.md §6)
- **R24**: 信頼できる家庭内ネットワークを前提とし、それを利用者に明示する。(導出: purpose.md §6)
- **R25**: 手順と条件(concepts.md §6)は、利用者が信頼するものだけを動かす前提とし、それを明示する。手順は任意の処理を呼び出すことができ、条件は指定された場所を読むためである。(導出: purpose.md §5・§6)
- **R26**: 根幹は特定のゲームや用途に依存しない。用途に固有のことは、手順・条件・利用者の処理の側に書ける。(導出: purpose.md §3・§5)
- **R27**: 実行中の装置を、自分の別のツールが横取りしない。(導出: purpose.md §4-2・§6)
- **R28**: 手順と条件を、利用者どうしでやり取りできる。手順の実行に必要なものを一緒に渡せる。形式が合わないものは、理由と、利用者が次にすることを示して拒否する。古い形式を読めることは、ほかの改良より優先しない。機能が良くなるなら、古い形式で書かれたものを読めなくしてよい。(導出: purpose.md §5)

## 2. 制約

環境の事実であって、設計で変えられない。制約は現在の事実で、変われば書き換える。

- **C1**: ゲームは自分の周期で入力を読み、その周期と位相は外から分からない。読み取りの周期がフレーム周期と同じなら、N フレームの指示は N-1 から N+1 フレームの範囲に確率的にずれる。ずれの頻度は送信時刻の誤差に比例して下がる。読み取りの周期は実機ごとにわずかに異なりうる(60.00Hz と 59.94Hz 相当など)。外から知る手段はなく、長い手順の後半でだけずれとして現れる。(出典: hardware-design.md §1-2・§1-3、runbook.md §3-2)
- **C2**: Switch は有線の Pro コントローラーを認識する。本体設定「Nintendo Switch Proコントローラーの有線通信」は、工場出荷時や本体初期化時は OFF になっている可能性がある。有線ではコントローラー側が入力レポートの間隔を 1ms まで宣言できるが、本体が実際に読み取る間隔は実測でおよそ 5 から 8ms である。無線(Bluetooth)では、Pro コントローラーの入力レポートは 120Hz(約 8.3ms ごと)で送られる。(出典: hardware-design.md §1-1・§2-1、glossary.md の「読み取り待ち」、runbook.md §2 の「状態を表示」の項目の表)
- **C3**: Switch 2 の本体を改造する手段(カスタムファームウェア等)は公開されていない。外から得られる情報は画面・音・振動に限られる。改造する手段は初代 Switch には存在するが、この目的では使わない(purpose.md §5)。(出典: hardware-design.md §2)
- **C4**: オンラインでの自動操作は利用規約に反しうる。(出典: hardware-design.md §5)
- **C5**: 汎用 OS の PC には、ミリ秒単位のスケジューラーのばらつき(1 から 15ms)がある。1 入力ずつ送ると、そのばらつきがすべての入力に加わる。(出典: hardware-design.md §1-1)
- **C6**: Switch の側は、モーションを角速度として受け取り、一定の値が続くとゼロ点とみなして打ち消す(自動の較正)。打ち消しているのが本体かゲームかは確認していない。ゲーム側の補正は線形でなく、生値とフレーム数から回転角への単一の換算係数はない。打ち消されずに済む最小の差は、1 つのゲームのカメラの動きを目で見て測った値であり、ほかのゲームでは異なりうる。(出典: glossary.md の「ゆらぎ」「GY / GR / GP」、runbook.md §1-7、binary-format.md の「設計判断」)
- **C7**: 無線を搭載する機器を国内で使うには技適(工事設計認証)が必要である。(出典: hardware-design.md §4)
- **C8**: Switch の映像を外で受け取る経路の遅延は 1 フレーム周期より大きい。したがって観測で読み取りの位相を合わせることはできず、観測は判断にだけ使える。(出典: hardware-design.md §1-2)

## 3. 許容条件

要件のうち、ここに挙げた範囲では緩めてよい。

- 手順を渡す、実行を指示するといった伝達の遅延は問わない。時間の正しさ(R1)は実行中の入力の送信について求める。(導出: purpose.md §4-1。時間の正しさは、Switch が入力を受け取る時刻についての価値である)
- 判断点では数秒の遅延を許容する。待つことが必然の箇所だからである。(導出: R2・R3)
- 費用と初期構築の手間は問わない。(導出: purpose.md §2。自分で組み立てて使うツールなので、初めの手間より運用の手間を優先する)
- 固定の待ちで足りる箇所では観測を要さない。(導出: purpose.md §4-1。進み方が決まっている箇所では、状況を観測で確認しなくても状況の正しさは保たれる)
- 複数台の間で入力の時刻を合わせることは求めない。合わせるのはゲームの側で行う。(導出: purpose.md §2・§4-1。Switch の本体どうしも時刻がずれるので、装置の時刻を合わせてもゲームの上では一致しない)
- 複数台は同じ家庭内ネットワークの同じセグメントで運用する。(導出: purpose.md §2・§6)
