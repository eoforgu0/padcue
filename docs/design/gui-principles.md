# 操作画面の設計原則

どんな些細な見た目・文言・配置も、**ここから説明できる状態を保つ**ための文書。
新しい画面要素を作るとき・変えるときは、まずこの原則に照らす。原則に合わない
変更は、原則の側を(理由を書いて)改めるか、変更を諦める。場当たりの追加を禁じる。

対象読者は開発者。ユーザー向けの使い方は runbook、用語は glossary が正。

---

## 0. 前提: この画面は何か

Switch を自動操作する装置の**運転**と、その材料(手順・部品・装置・プリセット)の
**管理**のための画面。使用者は所有者本人(少人数で、使うほど熟練する)。
初見の分かりやすさは大事だが、毎日の運転の速さ・確実さを損なってまで
初見に寄せない。

## 1. 大きな分け方: 操作(運転席)と環境(格納庫)

**判定基準は目的**。このソフトウェアの根本の目的は「自動操作」であり、
画面はその主軸と、それを支える周囲環境に分かれる(2026-08-06 ユーザーと
議論して確定)。

- **右(広い側)= 操作(運転席)**: 自動操作そのものを運転する。実行、停止、
  進行、判断(選択肢)、連結バー、手動操作、記録の閲覧(ログ)。
- **左(狭い側)= 環境(格納庫)**: 自動操作を支える持ち物の管理。
  装置(接続・解除・名づけ・診断のすべて)、Switch 本体、プリセット。
  **運転中に見なくても運転できるもの**がここに入る。

**結論と対処の規則**: 運転席には「動かせるか/動いているか」の**結論だけ**を
置く(レーンの状態チップ1つ)。原因の説明と対処(接続先・探す・診断値・
登録解除)は環境側に置き、結論から導線で繋ぐ(チップ→装置行が開く)。
未接続・異常のときは環境側の該当行が**自動で開いて赤くなる**
(=対処の場所を自ら名乗る)。

- 系: **格納庫には生きた実行状態(実行中・周回数)を並べない**。運転席と
  二重になるため。存在の目安(接続の有無のドット)までは可。
- 系: 診断値(方式・ファーム・ジャイロ・ずれ実測)は装置行の開閉式詳細に
  畳む(診断は稀=表示の引き算)。開けば無条件に全て見える
  (値をしきい値で隠さない、の本旨は維持)。
- 系: 実行対象の選択(手順プルダウン)は運転席の設定行の仕事。
  手順の在庫管理(並べ替え・フォルダ・表示選別)は「手順を編集」の仕事。
  ホームに手順一覧カードは置かない。
- 系: **1台と2台は同型**(レーンが1本になるだけ)。台数で構造を変えない。

以前は「いつ触るか(頻度)」で分けていたが、接続と登録解除が別の場所に
割れる欠陥があり、目的による分離へ改めた。頻度は配置でなく
「畳むかどうか」(表示の引き算)の判断に使う。

- 系: **どちらにも属さないもの = ヘッダ**。運転の対象でも持ち物でもない
  「この画面そのものの設定」(配色・通知)は左右のどちらにも入らないので、
  ヘッダ右の **⚙ 1つ**にまとめる。**設定の入口を2つに割らない**——
  ◐(配色)と ⚙ を並べると、配色を探す人がまず ⚙ を開けることになる
  (同じ意味は同じ形。§5)。設定は装置にもプロジェクトにも属さないので、
  保存先はブラウザ(localStorage)であってプロジェクトのファイルではない。

## 1b. 通知の原則

画面を見ていない人に届ける唯一の仕組みなので、他の表示とは別の規則を持つ。

- **きっかけの判定はサーバが持つ**。ブラウザは裏に回るとタイマーを絞られる
  (隠れて5分たつと毎分1回)ため、画面の定期取得で「終わった」を捉えると
  放置運転の知らせが最大1分遅れる。サーバで判定して押し出す(SSE)。
  画面側は受け取って鳴らすだけ——**何を知らせるか(サーバ)と、どう知らせるか
  (画面の設定)を分ける**。
- **自分の操作の結果には鳴らさない**。「今すぐ止める」を押した本人はその瞬間に
  画面を見ている。待つことになる操作(「今の周で止める」の予約)は鳴らす。
- **1つの仕事につき1回**。連結中は両方が終わって1回(連結=1つの仕事)。
- **人が動かないと進まないときだけ「操作待ち」**。自動合流で解ける駐機は
  待っていれば進むので鳴らさない。
- 知らせは**必ず消せる**(§5)。タブ名の点滅は画面に戻った時点で自ら止まる。
- **場面と知らせ方は掛け合わせる**(2026-08-08)。「音か点滅か」の3択にすると、
  席を外すときは音・戻ってから気づきたいときは点滅、という**同時に成り立つ
  要求**が表せない。設定は「場面(行)×知らせ方(列)」の表にし、音は場面ごとに
  種類と音量を持つ(部屋とゲーム音によって、通る音が違う)。
  - 系: 場面を増やしても表の行が増えるだけで、UI の形は変わらない。
  - 系: **効かない欄は押せなくする**(音を切った行の種類・音量)。消すのでは
    なく無効にするのは、その場面に音の設定が「ある」ことは残すため。

## 2. 運転席の原則

- **レーンは1台ぶんが自己完結する**(案C。2026-08-05 の4案比較で確定)。
  相方の情報を混ぜない。2台をまたぐ操作は連結バーだけが持つ。
- **設定は上、行動は下**。読み順 = 何を(手順)→ どれだけ(周回)→
  どこから(開始ラベル)→ 押す(実行・停止)。
- 停止は実行の並びの右に置き、危険色で区別する(位置と色の二重の区別)。
- 前提条件は「押す前に読むもの」なので行動の上(2026-08-02 確定)。
- 実行中に触れる欄は「**次の開始から効く**」を原則とし、そう動かせない欄は
  実行中は無効化する。
- 進行の表示は、表示対象と実行対象が**一致しているときだけ**出す。

## 3. 格納庫の原則

- 一覧の行はすべて同じ作法: `[状態ドット] 名前 [行アイコン ✎ ⧉ 🗑 …]`、
  詳細は下の meta 行。行アイコンは普段薄く、行にポインタで濃く。
- 新規作成は一覧カードの下の「＋」ボタン。
- 呼び出し・適用の結果は、**運転席が変わること自体**で伝える(文を足さない)。

## 4. 保存の作法(編集できるものすべてに共通)

- **編集している対象のそば**に「保存」ボタンと「保存済み / 未保存の変更」
  バッジを置く。保存の成功はバッジの点滅で伝える(文は出さない)。
- 手順エディタ・部品エディタ・連結バー(いまの割り当て→プリセット)は
  すべてこの同型。エディタ=手順を編集する場所、連結バー=割り当てを
  編集する場所、と読む。
- 名前を付ける行為(新規)はダイアログ(prompt)で。以後の保存は上書き。
- **上書きと別名は分けて、押す前にどちらか分かるようにする**(2026-08-08)。
  保存の対象が決まっている間は、ボタンは「上書き保存」と名乗り、隣に
  「別名で保存…」を出す。別名で保存したら、以後はそちらを編集している
  ことにする(世間の「名前を付けて保存」と同じ)。上書きは名前のとおり
  なので確認しないが、**別のものを潰すときだけ**確認する。
  - 系: **プリセットの新規作成は §3 の例外で、一覧の＋ではなく連結バーに置く**。
    §3 の＋は「一覧が編集対象の入口」であるもの(手順・部品・装置)の作法。
    プリセットは編集対象(いまの割り当て)が運転席にあるので、新規も上書きも
    「編集している対象のそば」= 連結バーに集約する方が §4 と整合する。

## 5. 伝え方の原則(確定事項の集約)

- **表示より状態変化で伝える**。メッセージは既存 UI では伝わらないときの
  仕方なくの手段で、必ず消せるようにする。
  - 系: **消えない席を作るのは、読み落とすと困るものだけ**(失敗・警告)。
    正常で・軽く・自分で押したと分かっている操作の成功は、押したボタンの
    そばに数秒だけ出して自ら消える(2026-08-08)。知らせのたびに行が増えると、
    そのぶん下の内容が動く——**正常系の操作でレイアウトを揺らさない**。
- **1項目 = 1つの値**。「procon / bInterval=1」のように値の中へ項目名を
  書かない(2026-08-08)。値が2つ以上あるものは、親項目の下に名前と値の対で
  ぶら下げる。読む側に値を切り分けさせない。
- **名前に付く補足は名前のそば**。ID・所要時間のような「その行が何者か」を
  補う情報は、名前の右に小さく薄く置く。下段へ落とすと、行に複数の対象
  (装置と Switch 本体)が絡むとき、何に付く値なのか読み取れなくなる。
- **よく使う操作を開閉の奥に置かない**。畳んだ行でも、その行に対する主操作
  (呼び出す等)は押せる位置に出す。畳むのは「見なくても運転できる詳細」。
- **誤爆しうる入力は既定で切る**。画面を見ずに打てるキーボードショートカット
  は、他のソフトの割り当てと取り違えて事故になる。既定は切にし、⚙ で入に
  した人にだけ効かせる。**効かない設定の凡例は画面に出さない**(入にした
  人にだけ凡例が要る)。
- **名前で分からせる**。名前で分かることを title や hint で説明し直さない。
  説明を書くのは非自明な情報だけ、最短で。テキストを盛るのは設計の敗北。
- **迷ったら出さない**(2026-08-07 ユーザー指示)。「書かなくても分かるだろう」
  寄りに判定を倒す。足りなければ使う人が指摘でき、その方が書きすぎを
  削り続けるより安い。世間の同種ツールの定型(例: 更新中は「抜かないで
  ください」)も判断材料にする。
- **同じ意味は同じ形**(チップ・バッジ・確認文・アイコン・配色)。形を
  変えるのは意味が違うときだけ。新しい形を発明する前に既存の形を探す。
- 押しても失敗するだけのボタンは、理由つきで無効化する。
- **進行中のユーザー操作の足元を作り変えない**(ドラッグ・文字入力・
  フォーカス)。**更新の方式(定期・イベント駆動)を問わず**守る不変条件。
  画面の更新事情はユーザーの操作より優先されない。装置の状態は操作と
  無関係に変わり続けるため、どんな更新方式でも「操作中に正当な更新が
  届く」ことは残る——だから手段でなく不変条件として持つ。
  - 手段は下位で差し替え可: 更新の保留と追いつき/変化検知による再構築の
    抑制/対象要素だけの差分更新。「ドラッグ中は作り直しを保留」は
    現実装(毎秒取得+変化検知)での一手段であって、方針ではない。
- 色の意味: 赤=異常、黄=注意(毎周の正常には使わない)、緑=良好・成功、
  青(強調色)=情報・選択。
- 操作の結果は、その操作をしたカードに出す(視線の場所)。

## 6. 用語の原則

- 用語は glossary が正。**同じ概念に別の語を使わない**(装置・ID・
  プリセット・選択肢…)。
- 日常語を優先する。業界語・内輪語・比喩は画面に出さない
  (例: arm の直訳「腕」→「選択肢」)。内部のコード・API 名は互換のため
  変えなくてよいが、画面には出さない。

## 7. この文書の運用

- 原則とぶつかる要望が来たら、まず原則との衝突を明示して相談する。
- 原則を変えたときは、影響する既存 UI を洗い出して同時に直す
  (原則がブレたまま画面ごとに違う、が最悪の状態)。
