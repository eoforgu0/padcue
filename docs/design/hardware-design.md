# 装置の方式とハードウェアの選定

装置の方式(有線の Pro コントローラー)、マイコン(ESP32-S3)、ボード(M5Stack AtomS3 Lite)を定め、それぞれの理由と、理由の元になる入力の時刻の分析を書く。何を満たすべきかは [requirements.md](../requirements.md)、どう作るかの方針は [principles.md](../principles.md)、ファームウェアの作りは [design/firmware-architecture.md](firmware-architecture.md) にある。

公開されている情報についての記述は、2026 年 7 月の時点のものである。

## 1. 入力の時刻の精度

### 1-1 誤差の内訳

入力の時刻の誤差は、次の 3 つが順に重なって決まる。

| 段 | 意味 | 大きさ | 扱い |
|---|---|---|---|
| 実行時刻のばらつき | 押す時刻が予定の時刻に来るか | PC から送ると 1 から 15ms。装置が自分で送ると、1 マイクロ秒の分解能のタイマーで予定の時刻を決める(実際の遅れは「状態を表示」と `python -m padcue status` の「最大遅延」に出る) | 装置が自分で送る(P2) |
| 読み取りの間隔 | 押した状態が Switch へ伝わる細かさ | 装置が宣言する bInterval と、本体が実際に読む間隔で決まる | bInterval に 1(1ms)を宣言する |
| 読み取りの周期 | ゲームが入力を読む周期 | ゲームごとに違い、描画の fps と同じとは限らない | 変えられない。境界でのずれの起きる頻度は 1-3 で下げられる |

実物の Pro コントローラーの bInterval は 8 である([design/procon-protocol.md](procon-protocol.md))。装置は 1 を宣言する。1 を宣言したときの不利な点として挙げられるものは、どれもこの装置では問題にならない。

| 1 を宣言したときの不利な点 | この装置での影響 |
|---|---|
| 装置の消費電力が増える | バスから給電されるので関係しない |
| 本体が帯域を多く予約する | 64 バイトのレポートを 1ms ごとに送っても毎秒 512kbit で、USB Full Speed(12Mbps)の約 4% である |
| 本体の処理が増える | Switch 2 は平均 5.8ms ごとに読む(下の測定)。8ms ごとの約 1.4 倍である |
| 割り込みが増える | 読み取りは毎秒 200 回に満たない(下の測定) |

残るのは、実物と違う値を宣言することである。Switch 2 と初代 Switch は 1 を受け入れる。受け入れない本体のために、装置の設定で 8 にできる(comm-protocol.md の CONFIG の usb_binterval。配布するファームウェアは 1 種類のまま、次の起動から使う)。

1 を宣言しても、Switch が実際に読みに来る間隔は平均 5.8ms、最大 8ms である(実機の Switch 2 での測定。6.7 秒の実行で 1149 回読まれた)。前の値が読まれるまで次の値を USB へ渡せないので、この間隔が「状態を表示」と `python -m padcue status` の「最大遅延」の「読み取り待ち」の大きさを決める。ずれの起きる頻度を決めるのも、宣言した値ではなくこの間隔である。

このほか、Windows のタイマーの既定の分解能は約 15.6ms で、PC を送信の経路に置くとこれを受ける。水晶の誤差(20 から 50ppm。1 時間で約 0.2 秒)は、1 つの待ちの長さに対しては無視できる。

### 1-2 フレームの境界での欠落と重複

送信の時刻をどれだけ正確にしても、なくならない誤差がある。

ゲームが入力を読む時刻(読み取りの位相)を、外から知る手段はない。そのため、入力の切り替えが読む直前に来るか直後に来るかは決まらない。ゲームがフレーム周期と同じ周期で読むとき、「N フレーム押す」という指示は、次のようにずれうる。

```text
凡例: | = ゲームが読む時刻    v = 入力の切り替え

意図(2 フレーム押す)
  |----|----|----|
    v押     v離      -> 2 回読まれる(正しい)

短く見える(押すのが直後、離すのが直前に来た)
  |----|----|----|
     v押   v離        -> 1 回しか読まれない

長く見える(押すのが直前、離すのが直後に来た)
  |----|----|----|
   v押       v離      -> 3 回読まれる
```

押す時刻と離す時刻は、それぞれ前後どちらにも転ぶので、N フレームの指示は N-1 から N+1 フレームの範囲でばらつく。「短く見える」は 1 フレームぶん短いという意味で、入力が消えることではない。

| 指示 | 読まれるフレーム数 | 1 回も読まれないことがあるか |
|---|---|---|
| 1 フレーム | 0 から 2 | ある |
| 2 フレーム | 1 から 3 | ない |
| N フレーム | N-1 から N+1 | ない |

このモデルでは、入力そのものが失われうるのは 1 フレームのときだけで、2 フレーム以上なら長さがばらつくだけである。前提は 2 つある。ゲームの読み取りの周期がフレーム周期と同じであることと、切り替えが Switch に見えるまでの遅れが 1 フレームより短いことである。遅れを決める読み取りの間隔は、Switch 2 の測定で最大 8ms だった。これは測定の値で、すべての環境の上限ではない。数え上げによる確認は `pctool/tests/test_sampling_model.py` にある。編集画面が 1 フレームの入力にだけ注意を出すのは、この区別による(P28)。

読み取りの周期が違うゲームには、この表は当てはまらない。一般に、見える長さの最小(指示の長さから遅れの上限を引いた長さ)が読み取りの周期より長ければ、1 回以上読まれる。例えば、読み取りの周期が 33.3ms で遅れの上限が 8ms なら、既定のフレーム周期の 2 フレームは見える長さの最小が 25.3ms なので、読まれないことがある。

未知なのは送信の正確さではなくゲームの側の位相なので、読み取りの間隔を細かくしてもこの問題は残る。手順を書くときは次のことを前提にする。

- 1 フレームの単位で結果が変わる操作は、毎回同じ結果になるとは限らない
- 1 フレームの押下と待ちだけは、まったく読まれないことがある。2 フレーム以上にすればそれはなくなり、長さのばらつきだけが残る
- 待ちは、前後に余裕を持たせた長さで書くのを基本にする
- 1 フレームの差が結果を分ける場面では、何度か試して結果の分布を見るほかに確かな方法はない
- 画面の更新の時刻から位相を推し量る方法はありうるが、映像を受け取る経路の遅れが 16.7ms より大きいので、このツールでは使えない(C8)

### 1-3 ずれの起きる確率は送信の誤差に比例する

1-2 のずれは「起こりうる」もので、必ず起こるわけではない。押してから離すまでの間隔がフレーム周期のちょうど整数倍なら、その区間に入る読み取りの回数は位相によらず一定になる(周期 P で読むとき、長さ N x P の半開区間には必ず N 回の読み取りが入る)。

ずれが起きるのは、実際の間隔が N x P から外れたときである。外れた量を e とする。読み取りの位相は外から分からないので、ここでは位相が 1 周期の中に一様に分布するとして数える。このモデルでは、ずれの起きる確率は |e| / P である。表はこのモデルの値で、実機の失敗率の上限を保証するものではない(同じ位相でくり返し開始すれば、毎回ずれることも、毎回ずれないこともある)。

| 送信の間隔の誤差 | ずれの起きる確率(位相を一様としたモデル) |
|---|---|
| 8ms(実物の Pro コントローラーの bInterval) | 最大で約 48% |
| 5ms | 最大で約 30% |
| 1ms(宣言どおり 1ms ごとに読まれる場合) | 最大で約 6% |
| 0.1ms | 最大で約 0.6% |

e を決めるのは、本体が実際に読みに来る間隔(1-1 の平均 5.8ms、最大 8ms)である。e を 0 にはできないので確率も 0 にはならないが、送信が正確なほど頻度は下がる。

この性質は、手順の時間がフレーム周期の整数倍で書かれているときにだけ成り立つ。ミリ秒で任意の値を書くと(30ms はおよそ 1.8 フレーム)、間隔が整数倍にならず、位相への依存が残る。手順の時間をフレームで書くのはこのためである(P8)。

フレーム周期がちょうど 1/60 秒(16.6667ms)か、59.94Hz 相当(16.6833ms)かで、整数倍の値が変わる。差は 1 フレームあたり 0.017ms だが、60 フレームで約 1ms、600 フレームで約 10ms になる。フレーム周期を設定の値として持ち、Switch 側の周期に合わせて変えられるのはこのためである([runbook.md](../runbook.md) §3-2)。

### 1-4 時刻は開始からの絶対時刻で計算する

| 計算のしかた | 次の時刻の求め方 | N フレーム後の誤差 |
|---|---|---|
| 相対時刻 | 前のフレームを実際に送った時刻 + 1/60 秒 | N x d(積み重なる) |
| 絶対時刻 | 開始の時刻 + N/60 秒 | d(積み重ならない) |

d は 1 回あたりのタイマーの誤差である。相対時刻では誤差が回数ぶん積み重なり、手順が長いほどずれが広がる。1000 フレーム後に 10ms ずれると、その時点のずれの起きる確率は 1-3 のとおり約 60% になる。しかも「始めは正しく動くが、後半でずれが広がる」という見つけにくい形で現れる。装置は絶対時刻で計算する(P8)。

### 1-5 装置が記録する範囲

正常なときの入力を全フレーム記録しても、ずれの有無は分からない。装置が保証できるのは「自分の時計のとおりに送った」ことだけで、ずれを生むゲームの側の位相(1-2)は装置から見えないからである。

装置が記録するのは、異常と、異常を調べる手がかりになる主なイベントである(P19)。

| 記録するもの | 目的 |
|---|---|
| エラー、異常終了 | 人が見ていない間の障害を知る |
| USB の切断と再列挙 | 接続が切れたことを知る |
| 起動、実行の開始と終わり、状態の変化 | 異常の前後に何が起きていたかを知る |
| タイマーが予定の時刻を過ぎたこと | 処理の遅れを知る |

最後のものは、予定を過ぎたときだけ記録する。正常なときは何もしないので、送信の時刻をばらつかせない。どれも送信の割り込みの中では書かないので、書き方に特別な制約は必要ない。

## 2. 方式の選定

装置が Switch を自動で操作する方式には、次のことが必要である。

- 入力を切り替える時刻を、1 フレームより十分細かく Switch へ伝えられる(R1)
- ボタンとスティックに加えて、モーション(ジャイロと加速度)を送れる(R5)
- 通常のコントローラーとして見え、本体にもゲームにも手を加えない(R6)

有線 USB の Pro コントローラー方式を採用する。理由は次のとおりである。

- 有線では、読み取りの間隔を 1ms まで宣言できる(2-1)
- 入力レポート(0x30)にモーションの領域があり、ボタン・スティック・モーションを 1 つのレポートで送れる(2-2)
- 純正の Pro コントローラーと同じ識別子とレポートの形式を使うので、Switch には有線の Pro コントローラーとして見える。純正の Pro コントローラーは Switch 2 でも有線で使える(本体設定に「Nintendo Switch Proコントローラーの有線通信」がある。C2)。padcue の装置は、Switch 2 と初代 Switch のどちらにも、有線の Pro コントローラーとして認識される
- プロトコルの技術文書と Linux の実装例が公開されており(6 節)、それに従って作れる。汎用ゲームパッド方式でできることは、この方式ですべてできる

採用しない方式と、その理由は次のとおりである。

| 方式 | 入力の粒度 | モーション | 採用しない理由 |
|---|---|---|---|
| 有線 USB の汎用ゲームパッド方式 | 1ms まで宣言できる | 送れない(領域がない) | レポートの形式にモーションの領域がなく、R5 を構造的に満たせない(2-2) |
| 無線(Bluetooth)の Pro コントローラー方式 | 120Hz(約 8.3ms) | 送れる | 入力の粒度が有線の実測(平均 5.8ms)より粗く、電波の干渉によるばらつきと再送の遅れも加わる(2-1) |
| 本体のメモリを直接読む | - | - | Switch 2 の本体を改造する手段が公開されておらず、成り立たない(C3)。本体やゲームに手を加えないことも前提である(R6) |
| ボタンを物理的に押す | 機構の速さで決まる | 送れない | 時刻の正確さが足りず、モーションも送れない |

### 2-1 有線と無線

- dekuNukem の技術文書(6 節)によれば、Bluetooth では、モーションを含む入力レポート(0x30、standard full mode)は 60Hz で、Pro コントローラーは 120Hz で送られる。有線での頻度は書かれていない
- 実物の Pro コントローラーは、センサーの値を中の MCU が受け、中の UART の伝送路を通してから Bluetooth か USB へ出す作りである。有線の手順に `0x80 0x03`(ボーレートの設定)が定義されているのは、この作りのためである。この経路は製品の中のもので、レポートを直接作る padcue の装置にはない。padcue の装置では、有線でつないでも、この経路のぶん遅れることはない
- padcue の装置は bInterval に 1(1kHz)を宣言できる。本体が実際に読みに来る間隔は平均 5.8ms、最大 8ms で(1-1)、無線の Pro コントローラーの約 8.3ms より細かい
- 無線には、2.4GHz 帯の電波の干渉によるばらつき、再送の遅れ、接続の途切れが加わる

### 2-2 Pro コントローラー方式で作るもの

- `0x80` 系のハンドシェイク(0x01 装置の情報、0x02 ハンドシェイク、0x03 ボーレート、0x04 HID だけの通信)
- サブコマンドへの応答: 0x01 登録(ペアリング)、0x02 装置の情報、0x03 入力レポートの形式、0x04 トリガーの経過時間、0x10 SPI フラッシュの読み出し(一度に 0x1D バイトまで。スティックとモーションセンサーの較正の領域を返す)、0x21 NFC と IR の MCU の設定、0x30 プレイヤーの LED、0x40 モーションセンサーを有効にする、0x48 振動を有効にする
- `0x21`(サブコマンドへの応答)と `0x30`(モーションを含むすべての状態)のレポートを作り、レポートごとの番号を進める

実際のやり取りの記録と、実装が返す値は [design/procon-protocol.md](procon-protocol.md) にある。汎用ゲームパッド方式でモーションを送れないのは、HID レポートディスクリプターにモーションの欄が定義されておらず、値を入れる場所そのものがないからである。

Switch は Pro コントローラーへ振動の指示を送る。これを受け取ればゲームの中の出来事を画面より速く知れるが、padcue は使わない。

## 3. マイコンの選定

マイコンには、次のことが同時に必要である。

| 必要なこと | 理由 |
|---|---|
| 任意の USB の装置になれる | Pro コントローラーとして Switch につながる(P1) |
| 手順データを置ける | 装置が手順を持ち、自律して実行する(P2・P3)。受信バッファーは 96KiB である(firmware-architecture.md §5) |
| 無線を持つ | USB ポートは Switch につないでいるので、手順の転送と状態の読み出しは無線で行う(P3・P5・R14) |
| コアを 2 つ持つ | 無線の処理と送信を別のコアで動かし、通信している間も送信の時刻をばらつかせない(R1。3-1) |

無線での更新は必須ではないが、ケーブルをつなぎ替えずに更新できるとよい(R21)。

ESP32-S3 を採用する。理由は、上の 4 つを 1 つのチップで満たし、USB の装置(TinyUSB)と、無線での更新と、新しいバージョンが正しく起動しなかったときに前のバージョンへ戻す仕組みを、どれも ESP-IDF の標準の機能で作れることである。USB の回路は、他社のマイコンでも広く使われている Synopsys の DWC2 で、Pro コントローラー方式を作るのに構造上の妨げはない。

採用しないマイコンと、その理由は次のとおりである。

| マイコン(載せたボードの例) | 採用しない理由 |
|---|---|
| ATmega32U4(Leonardo など)と ATmega16U2(Uno R3) | 無線を持たない。フラッシュ(32KB と 16KB)も手順データの受信バッファー(96KiB)より小さい |
| ESP32 の S3 以外の型番 | ESP-IDF v6.1 が正式に扱う型番は、4 つのどれかが欠ける(3-1) |
| Raspberry Pi(USB Gadget) | Pro コントローラー方式の実装例がある(6 節)が、OS の実行時刻のばらつき、SD カードの壊れやすさ、起動の時間のぶんだけ、R1 とつないだままの運用に不利である |

RP2350(Raspberry Pi Pico 2 W など)も上の 4 つを満たし、無線での更新には公式の例がある(6 節)。ファームウェアのうち、実行エンジンと、Pro コントローラーのプロトコル処理(`firmware/components/pademu_core/`)は ESP-IDF に依存しない C で書いてある。ほかのマイコンへ移すときに書き直すのは、ESP-IDF の上に作った `firmware/main/` である(firmware-architecture.md §1)。

### 3-1 ESP32 の型番

ESP-IDF v6.1 が正式に扱う型番のうち、3 節の 4 つを満たすのは ESP32-S3 だけである。

| 型番 | USB の装置になれるか | 無線 | コア | 欠けるもの |
|---|---|---|---|---|
| ESP32 | なれない | Wi-Fi と BT Classic と BLE | 2 | USB の装置になれない |
| ESP32-C2 | なれない | Wi-Fi と BLE | 1 | USB の装置になれない |
| ESP32-C3、ESP32-C5、ESP32-C6、ESP32-C61 | Serial/JTAG の固定の機能だけ | Wi-Fi と BLE | 1 | 任意の USB の装置になれない |
| ESP32-H2 | Serial/JTAG の固定の機能だけ | BLE | 1 | 任意の USB の装置になれない |
| ESP32-S2 | なれる(OTG) | Wi-Fi だけ | 1 | 送信と通信をコアで分けられない |
| ESP32-S3 | なれる(OTG) | Wi-Fi と BLE | 2 | ない |
| ESP32-P4 | なれる(OTG) | 内蔵していない | 2 | 無線に別のチップが必要 |

ESP32-S31 も USB-OTG と Wi-Fi と 2 つのコアを持つが、ESP-IDF v6.1 の対応の一覧(COMPATIBILITY.md)にはまだ記載されていない。

ESP32-S3 を使うことで、ファームウェアの作りには次のことが決まる。

- 2 コアであることが役に立つのは、Wi-Fi の処理がコア 0 で動くからである。USB の処理と送信をコア 1 に固定すれば、通信している間も送信の時刻がばらつかない
- フラッシュへ書き込んでいる間は、命令の読み出しのキャッシュが停止し、フラッシュに置いたコードは動けない。USB のレポートの送信も停止するので、実行している間はフラッシュへ書き込まない(P3。[design/firmware-architecture.md](firmware-architecture.md) §5)
- Secure Boot かフラッシュの暗号化を有効にすると、ROM の USB-OTG の処理が無効になる。padcue のファームウェアはどちらも有効にしない
- USB のデータ線は GPIO19(D-)と GPIO20(D+)に決まっている。ボードは、これがコネクターに出ている必要がある(4 節)
- ESP32-S3 の USB ポートは、既定の USB Serial/JTAG と、任意の装置として動く USB-OTG(TinyUSB)を切り替えられる。切り替えはビルドの設定(ESP-IDF の Kconfig と sdkconfig)で決まり、回路の改造は必要ない。OTG にすると、書き込んだ後に自動ではリセットされないので、ケーブルで書き直すときは装置を書き込みの状態へ戻す(AtomS3 Lite では、リセットのボタンを 2 秒以上押す)

## 4. ボードの選定

ボードには、次のことが必要である。

- ESP32-S3 を搭載し、USB のデータ線(GPIO19 と GPIO20)がコネクターに出ている(3-1)
- フラッシュが 8MB 以上ある。パーティションテーブル([firmware/partitions.csv](../../firmware/partitions.csv))は、更新に使う 2 つのパーティション(3MiB ずつ)と手順を保存するパーティション(1MiB)を置き、7MiB あまりを使う
- 装置のボタンと、状態を色で出す LED がある(concepts.md §7、runbook.md の付録「装置のボタン」)
- 基板が筐体に入っている。Switch につないだまま置いておくので、むき出しの基板では絶縁の手当てが必要
- 国内で使うものは、技適(工事設計認証)を受けている。無線を搭載する機器で、認証のないものを国内で電波を出す状態で使うのは、電波法に反する(C7)

M5Stack AtomS3 Lite を採用する。理由は、上のすべてを満たすことである。

| 項目 | M5Stack AtomS3 Lite |
|---|---|
| チップ | ESP32-S3FN8(2 コア、8MB のフラッシュ)。Wi-Fi を内蔵し、USB を Type-C に出している |
| 入出力 | ボタン(GPIO41)、フルカラーの LED(WS2812、GPIO35) |
| 筐体 | 24.0mm 角、厚さ 9.5mm のプラスチックの筐体。背面の M2 のねじ穴で留められる |
| 技適 | 技適を受けた国内の正規の流通品を使う |

ファームウェアは、このボードに合わせてある。ボタンと LED のピンは [firmware/main/app_config.h](../../firmware/main/app_config.h) にあり、フラッシュの大きさはビルドの設定(`firmware/sdkconfig.defaults`)で 8MB にしている。ほかの ESP32-S3 のボードで使うときは、上の必要なことを満たすかを確認し、ピンをそのボードに合わせる。

USB ポートは 1 つで、Switch とつなぐのに使う。記録の読み出しと更新は Wi-Fi で行う([getting-started.md](../getting-started.md))。Switch から外して PC につなぐのは、最初にファームウェアを書き込むときと、無線でつながらない装置を診断モードで調べたり、Wi-Fi の設定を書いたりするときである。

## 5. 運用のリスクと対策

| リスク | 対策 |
|---|---|
| 利用規約(任天堂のアカウントの利用規約は、許諾のない利用をした本体を使えなくすることがあると定めている) | オフラインかローカルの用途に限る。オンラインの対戦やランキングでは使わない(C4) |
| 本体の設定「Nintendo Switch Proコントローラーの有線通信」がオフのままでは、有線のコントローラーが認識されない。工場出荷時や本体初期化時はオフになっている可能性がある | 最初の準備でオンにする(設定、コントローラーと周辺機器) |
| Switch 2 と初代 Switch では、読み込みの時間とホーム画面の動きが違い、一方に合わせて書いた手順がもう一方では合わない | 合わない箇所でだけ、画面を見て判断する(判断は数秒の遅れを許す) |
| 人のいない間の異常 | 装置は自分の異常を見つけると、全入力を離して停止する(R9)。本体の自動スリープ、通知、自動更新をオフにしておくことを推奨する |
