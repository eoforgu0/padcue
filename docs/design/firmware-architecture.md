# ファームウェア詳細設計

状態: **実装済み**(firmware/main/ と
firmware/components/pademu_core/)。実機で検証済み。実装中に変わった点は
本文書へ反映してある。

## 0. 目的からの演繹

R1(意図した時刻に入力を送出)> 試行錯誤の速さ > 放置、の順で全判断を導出する。

- R1 → タイミング経路(実行エンジン→USB送出)はコア1に隔離し、経路上に 動的確保・
  フラッシュアクセス・ブロッキングを置かない(設計文書 7.1/7.4/付録D)
- 試行錯誤 → 実行エンジンは移植可能な純粋C(ホストで Python 参照実装と送出列一致
  を検証してから実機へ)
- 放置 → 全異常は「全ニュートラル化+位置記録」に収束させ、状態機械の外の暗黙状態
  を持たない
- **ニュートラルの定義**: ボタンなし・スティック中央・角速度 0・**加速度は重力ぶ
  ん(0,0,4096 = 1G)**。加速度センサーは重力も測るため、静止していても 1G が出続
  ける。全軸 0 は静止ではなく自由落下であり実機では起こらない。重力が無いと基準
  の姿勢が決まらず、ジャイロを送っても向きが変わらないゲームがある。実装は
  `pademu_state_neutral()` に一本化し、`memset` による 0 埋めは使わない(PC 側は
  `binfmt.REST_A*`)

## 2. 実行エンジン(コア1、R1 の心臓部)

- **タイマー**: GPTimer 1MHz を実行開始時に 0 リセット。「次イベントの絶対時刻(µ
  s) = 開始時刻 + (base + frame) * frame_period_ns / 1000」でアラームを張り、
  ISR(IRAM 配置)で処理する
- **ISR の仕事**(すべて RAM 上の O(1) 操作): 期限が来たイベントを適用(STATE→現在
  状態構造体へコピー/SETCNT/DJNZ/JMP/AWAIT/END)、同一時刻のイベントを連続適用、
  次アラーム設定。**遅延検出**: 実時刻−予定時刻 > 閾値(既定 200µs)なら超過ログを
  リングへ記録(A-4)
- **現在状態の共有**(engine ISR = 単一書き手、usb タスク = 読み手、同一コア):
  seqlock(偶奇カウンタ)付き構造体。**C11 atomic + release/acquire で実装**し、コ
  ンパイラの並べ替えを禁止する
- **ISR の防御上限**: 1回のアラーム処理で適用する時間非消費イベント
  数に上限(64)を設け、超過時は実行を中断+ERROR(壊れたバイナリ・コンパイラバグに
  よる ISR 内無限ループを構造的に排除する第2層。第1層は decode 検証)
- **停止経路**: stop フラグ(atomic)。①ISR は毎アラームで確認 ②usb タスクは毎レポー
  ト生成時に確認し、立っていれば即ニュートラルを送出(長い wait 中でも 1ms 以内に
  停止が効く)。graceful は「AWAIT/セッション境界で消化」のフラグ
- **実行データ**: RUN 前に PC から受信済みの RAM バッファ(イベント配列)を検証
  (CRC・ジャンプ範囲・**時間非消費閉路の静的検証**)後にポインタ渡し。実行中の確
  保・解放なし
- **ウォッチドッグ**(故障を2分類する):
  - **無音死**(ISR が発火しなくなる): engine が生存カウンタを更新、usb タスク(同
    一コアだがタスクは生きている)と sys タスク(コア0)が監視 → 強制ニュートラル
    +ERROR
  - **livelock**(ISR が戻らない): 同一コアの是正は原理的に不能。ESP-IDF の
    Interrupt WDT を意図した最終防波堤とし(パニック→リブート)、起動時に
    esp_reset_reason を「前回の死因」として PC へ報告する。RAM 上の位置記録は失
    われることを許容(発生自体は decode 検証+ISR 上限で防ぐ)

## 3. 転送層インターフェース(7.2 のレイヤー境界、C ヘッダ)

```c
// アプリ層が保持する論理状態(生値。手順データ仕様と同一の座標系)
typedef struct {
  uint32_t buttons;            // 論理ビット割り当て(binfmt.BUTTONS と一致)
  int16_t  lx, ly, rx, ry;     // -2048..+2047(中心0、左/下が負)
  int16_t  gyro[3], accel[3];  // センサー生値
  uint32_t seq;                // seqlock
} pad_state_t;

typedef struct {
  void (*on_player_lights)(uint8_t bitmap);   // 1P/2P 表示(LED へ)
  void (*on_rumble)(const uint8_t *raw);      // 将来のイベント検知用(記録のみ)
  void (*on_host_activity)(void);             // ホスト生存確認
} transport_callbacks_t;

esp_err_t transport_start(transport_mode_t mode /* PROCON | HIDPAD */,
                          const pad_state_t *state,
                          const transport_callbacks_t *cb);
```

- 転送層はレポート生成のたびに `state` を seqlock 読みし、**ワイヤ形式への変換は
  転送層内**で行う(プロコン: +2048 の12bit詰め+IMU 3サンプル複製/HIDパッド: 8bit
  へ丸め、モーション破棄)
- モード切替は NVS へ保存して**再起動で反映**(USB 再列挙の複雑さを回避。切替は稀
  で IDLE 時のみ)

## 4. プロコン方式転送層(dekuNukem 文書+mzyy94 実装を典拠)

- ディスクリプタ: VID 0x057E / PID 0x2009、EP IN/OUT 各1、bInterval は Kconfig(既
  定1、5へ戻せる)
- **HID レポートディスクリプタ(203B)は実測バイト列をそのまま複製する**(機能的に
  等価に見えても再構成しない)。実体は `pademu_usb_desc.c`(注釈付き原文は
  `docs/reference/hid_report_descriptor.txt`)。コンフィグ記述子の
  wDescriptorLength は `PADEMU_PROCON_HID_DESC_LEN` から生成し、手打ちの二重管理
  をしない
- **IN エンドポイントの仲裁**: TinyUSB の `tud_hid_report()` は
  前の転送が未完了だと**レポートを黙って捨てる**(内部キューなし)。サブコマンド応
  答が捨てられるとハンドシェイクが進まず接続が止まるため、`pademu_tx`(応答は深さ
  4の優先キュー、定期入力レポートは埋め草)を必ず経由する。送出は完了コールバック
  駆動で「応答があれば応答、無ければ定期入力」。溢れた応答は数えて異常ログの対象
  にする(正常時 0)
- **`tud_hid_report()` の report_id には 0 を渡す**: 本実装のバ
  ッファは先頭バイトが既にレポートID。0 以外を渡すと TinyUSB がもう1バイト前置し
  ようとして EP バッファ長を超え、転送失敗のままエンドポイントが解放されず**以後
  一切送出できなくなる**。送出直前に `pademu_tx_report_id_valid()` で検査する
- 0x80 系ハンドシェイク応答(01: 状態+MAC、02: ACK、03: ACK、04: HID-only 有効)を
  状態機械で実装し、**到達段階をブレッドクラム記録**(未検証3の切り分け用)
- サブコマンド応答(0x21): 0x02 デバイス情報 / 0x03 レポートモード / 0x04 / 0x08
  / **0x10 SPIリード**(スティック・IMU キャリブレーションを返す。**直線マッピン
  グになる値を自作定義**=生値原則の成立点)/ 0x30 プレイヤーLED(→コールバック) /
  0x40 IMU有効 / 0x48 振動有効 / その他は安全な既定応答
- 0x30 入力レポート: タイマー u8、ボタン 3B、スティック 6B、IMU 6軸×3サンプル。
  IMU は現フレーム値を3サンプルに複製(較正フェーズで見直し)
- **検証**: PC 上のプロトコルシミュレータ(Python)が Switch 側を模擬し、応答列を
  公開仕様と突き合わせる。転送層のプロトコル処理部は USB 依存を注入分離し、ホス
  トでも同一コードを検証可能にする

## 5. メモリ・フラッシュ予算

| 用途                  | 上限                                                                                                                                                              | 根拠                                      |
|-----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------|
| 実行データ RAM プール | 96KB(3072イベント×32B。`app_store.h` の APP_STORE_MAX_PROC_SIZE)                                                                                                  | 長尺行列部品を許容しつつ SRAM 512KB の1/4 |
| ログリング            | 16KB(**3リング構成**: engine-ISR 用 / usb タスク用 / コア0共用(mutex)。各 SPSC で log タスクが集約 — 複数コア書き手による破損を排除)                              | 異常時のみ記録の方針(A-4)                 |
| 手順保存領域          | procs パーティション 1MB(**SPIFFS**。ESP-IDF 標準で外部依存なし。手順名は形式仕様どおり 32 バイトまで。パス長を収めるため `CONFIG_SPIFFS_OBJ_NAME_LEN=48` を指定) | 複数手順+セグメント                       |

**実装必須の設定**: `CONFIG_GPTIMER_ISR_IRAM_SAFE` /
`CONFIG_GPTIMER_CTRL_FUNC_IN_IRAM` / ISR コールバックの IRAM_ATTR。さらに
RUNNING 中の**暗黙のフラッシュ書き込み**(アプリ外)を排除する:
`esp_wifi_set_storage(WIFI_STORAGE_RAM)` で WiFi 設定の NVS 書込を抑止し、
RUNNING 中は自作コードからの NVS 書込も状態機械でゲートする(7.4 の禁止はアプリ明
示書込だけでなく内部書込にも及ぶ必要がある)。

## 6. 状態機械(コア0所有。LED 表示は既定義の語彙に対応)

BOOT → WIFI_CONNECTING → IDLE ⇄ RUNNING(⇄ AWAITING=待機分岐)/ ERROR(ラッチ)/ OTA
**本節を状態機械の正本とし、comm-protocol.md はここを参照する**。

- フラッシュ書き込み(COMMIT/OTA/NVS)は IDLE でのみ許可(7.4 のゲートを状態機械で
  強制)
- RUNNING 中の USB サスペンド・再列挙(給電維持下)→ 中断+全ニュートラル+位置記録
  → ERROR。物理抜去は給電喪失のため検出不能(リセット理由+PC 側 TCP 断で事後推定)
- WiFi 断は状態遷移させない(実行継続。ログは RAM 保持→再接続後送出)
- **ERROR の解除**: `CLEAR_ERROR` コマンド(comm-protocol に追加)で IDLE へ復帰。
  ログ回収前の自動解除はしない
- **AWAITING からの遷移表**(優先順位順):

| 事象                           | 遷移                                                                  |
|--------------------------------|-----------------------------------------------------------------------|
| 即時停止                       | IDLE(破棄・位置記録)                                                  |
| SELECT(腕番号)                 | RUNNING(選んだ腕の経路へ。待った時間は時計から抜けるので付け替えない) |
| タイムアウト(on_timeout=abort) | IDLE(中断として記録。ERROR ではない=想定内の結末)                     |
| タイムアウト(on_timeout=腕k)   | RUNNING(既定腕へ)                                                     |
| 区切り停止フラグ               | AWAITING を維持(選択は必要)。消化はセッション境界で                   |

**WiFi は省電力を切る**(`esp_wifi_set_ps(WIFI_PS_NONE)`)。既定の MIN_MODEM の
ままだとビーコン間隔ごとに眠って受信を取りこぼす。実測で ping の 86% が落ち、
応答が最大 1.1 秒まで伸びて PC から事実上つながらない。
USB/ドック給電なので節電する理由がなく、制御リンクは応答性が全て。

## 7. ホストなし検証(受け入れ条件と、いまの実現状況)

1. **C 実行エンジン**: FreeRTOS/ESP 非依存の純粋 C。ホスト(MinGW-w64 を導入)でビ
   ルドし、**Python 参照実装と送出列(フレーム+全状態)完全一致**をテストデータ一
   式で検証 — **実現済み**(`tests/test_hostc.py` ほか。CI は `PADCUE_REQUIRE_GCC`
   を立てて、gcc が無いときの skip に逃げられないようにしてある)
2. **プロコン プロトコル部**: 同じく純粋 C 化し、Python シミュレータの対話ログで
   検証 — **実現済み**(`tests/test_procon.py` と `padcue/switchsim.py`)
3. 実機ビルドは全バリアントを CI で確認 — **一部**。CI が回すのは既定の1構成
   (`sdkconfig.defaults`)だけ。転送層は**ビルドの分岐ではなくなった**ので対象外
   (2種とも常に1つのイメージへ入り、`padcue mode` が NVS で切り替える)。残るのは
   `PADEMU_USB_BINTERVAL`(1 / 8)で、こちらは組み合わせを回していない

## 8. 確定した設計決定と残論点

**確定**:
- 待機分岐の実行: **単一のイベント配列**で表す(正本 flow-format.md §7)。コンパイ
  ラが「腕ごとに、分岐より後ろの続き」を展開するので、engine は AWAIT で全ニュー
  トラル化して AWAITING へ移り、SELECT で受けた腕の飛び先へ跳ぶだけでよい。セグ
  メント連鎖(SEGEND)案は不採用(flow-format.md §3 は記録として残した当初案)
- RUN の開始位置(部分実行): 任意 index ではなく**再開点表**(コンパイラが出力する
  `{name, index, base, frame}` の一覧。トップレベルのラベルがそのまま再開点)から
  選ぶ。デバイスは範囲と「そこから最初に到達する時間消費イベントが STATE である
  こと」を検証する(**SETCNT は時間を消費しないので手前に挟まってよい** — くり返
  しの直前にラベルを置くと必ずそうなる)。**再開点は時刻0に寄せる**(その絶対フレー
  ムを全送出時刻から引く)ので、飛ばした前半ぶんは待たない。周回数2以上なら各周回
  がその位置から始まる。詳細は specs/procedure-format.md
- Pi 移行(設計文書 7.2)の但し書き: 転送層に加え、タイマー駆動・ストレージ・OTA
  等の基盤も置換対象になる。実際に温存されるのは「純粋C の実行エンジン+プロトコ
  ル論理+PC 側全部」(7.2 の見積りはこの範囲で読む)

**残論点**(「実装初期に解決」と書いたまま、本文書へは反映していない2件):
- esp_timer ではなく GPTimer ISR を選んだ判断の実測確認。**観測の手段は入ってい
  る** — ファームが `max_late_us` を STATUS に載せ、`padcue status` と操作画面が
  「ずれ最大 / フレームの刻み」として出す。ISR 経路がフラッシュに残っていないこと
  は CI が map から確かめる(`tests/test_firmware_iram.py`)。実測値そのものは本文
  書に書いていない
- IMU 3サンプル複製の妥当性(較正フェーズで見直し。§4 の 0x30 入力レポートにも同
  じ但し書きがある)
