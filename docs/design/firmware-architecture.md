# ファームウェアの設計

装置のファームウェア(`firmware/main/` と `firmware/components/pademu_core/`)の作りを定める。何を満たすかは [requirements.md](../requirements.md)、どう作るかの方針は [principles.md](../principles.md)、マイコンとボードを選んだ理由は [hardware-design.md](hardware-design.md) にある。PC と装置の通信は [specs/comm-protocol.md](../specs/comm-protocol.md)、装置が受け取る手順データの形式は [specs/binary-format.md](../specs/binary-format.md) が定める。

## 1. 作りの考え方

目的の価値の順(時間の正しさ、見ていなくても動く、試行錯誤が速い。purpose.md §4)を、ファームウェアでは次のように実現する。

- 時間の正しさ(R1): 入力を送信する経路(実行エンジンから USB の送信まで)をコア 1 に置き、その経路では動的なメモリの確保、フラッシュの読み書き、待ちをしない。Wi-Fi の処理はコア 0 で動くので、通信している間も送信の時刻がばらつかない(hardware-design.md §3-1)
- 見ていなくても動く(R9): どの異常も、全入力を離し、止まった位置を記録して ERROR にする 1 つの処理に集める。6 節の遷移にない状態は持たない
- 試行錯誤が速い: 実行エンジンと、Pro コントローラーのプロトコル処理は ESP-IDF に依存しない C で書き、PC でもビルドして Python の参照実装と照合する(7 節)。装置に書き込まずに意味を確認できる

全入力を離した状態は、ボタンを何も押さず、スティックが中央で、角速度が 0、加速度が重力のぶん(0, 0, 4096 で 1G)である。加速度センサーは重力も測るので、静止していても 1G が出続ける。全軸が 0 なのは静止ではなく自由落下で、実物では起こらない。重力がないと基準の姿勢が決まらず、ジャイロを送っても向きが変わらないゲームがある。この状態は `pademu_state_neutral()` だけが作り、0 で埋めて作らない(PC の側の同じ値は `binfmt.REST_A*`)。

## 2. タスクとコア

| タスク | コア | 優先度 | 役割 |
|---|---|---|---|
| usb(`app_usb.c`) | 1 | 10 | レポートの送信(転送層)。IN の転送が終わるたびと 1 ミリ秒ごとに、次のレポートを送信の待ち行列に入れる。自前のタスクの中で最も高い |
| TinyUSB(esp_tinyusb のタスク) | 1 | 9 | TinyUSB のイベント処理。本体からの出力レポートを受けて応答を待ち行列に入れ、接続・切断・サスペンドを知らせる |
| (実行エンジンは専用のタスクを持たない) | 1 | 割り込み | GPTimer のアラームの割り込み(IRAM に置く)として動く |
| ctrl(`app_ctrl.c`) | 0 | 5 | TCP のサーバー。コマンドを受ける(HELLO・PUT・RUN・STOP・STATUS など)。記録の読み出し(LOGS)と無線での更新(OTA)も、このタスクで行う |
| btn(`app_button.c`) | 固定しない | 5 | 装置のボタンを 20 ミリ秒ごとに読む |
| supervisor(`main.c`) | 0 | 4 | 実行の終わりを見つけて、状態と LED を戻す(3 節) |
| discover(`app_discover.c`) | 0 | 3 | 探索の問い合わせ(UDP)に答える |
| led(`app_state.c`) | 0 | 3 | 状態に応じた LED の表示。IDENTIFY を受けると、5 秒間白く速く点滅させる |
| (Wi-Fi のスタック) | 0 | ESP-IDF の既定 |  |

状態の遷移は、それぞれのタスクが `app_state_transition()` で行う。今の状態が期待した状態であるときだけ書き換えるので、遷移を担当するタスクを 1 つに決めなくてよい。ERROR から出すのは `app_state_clear_error()`(CLEAR_ERROR のコマンド)だけである。このほかに、起動のときだけ動く engine_init がある。タイマーの割り込みをコア 1 に置くために、コア 1 でタイマーを初期化して終わるタスクである。

実行の開始(RUN)と、実行の終わりの処理(supervisor と STOP が呼ぶ `app_run_end_land()`)は、1 つのロック(`app_state_run_lock()`)の中で行う。終わりの処理が「実行が停止している」と確認してから状態を戻すまでの間に次の実行が始まると、終わった実行の報告と状態の書き換えを、次の実行に当ててしまうからである。選択(PC の SELECT と、選択待ちの時間切れ)は、宛てた選択待ちの通し番号を `app_engine_select()` に渡し、選ぶ権利を取った後で照合する。番号を読んでから選ぶまでの間に、その選択待ちがほかのタスクに選ばれて次の選択待ちへ進んでいても、次の選択待ちは進めない。

ctrl のタスクは 1 本で、すべての接続を担当する。応答を読まない相手に送ると、送り終わるまで待つ間は、ほかの接続の停止も受けられない。そのため応答 1 つを送り終わるまでの上限を 1 秒にしてあり、上限を超えた接続は閉じる。上限は応答ごとに 1 回決め、少しずつ読む相手にも、応答全体でそれ以上は待たない。lwIP が期限を確認するのは送信バッファーが空いたときと 1 秒ごとの定期処理のときなので、相手が読まなくなってから閉じるまでは最長で約 2 秒かかる。lwIP は待ち時間をミリ秒に切り捨て、0 ミリ秒を「上限なし」と読むので、渡す残り時間はミリ秒に切り上げる。

相手が消えた接続(PC の電源が切れた、PC の回線が切れた)には、FIN も RST も送られない。TCP の keepalive で見つけて閉じる。無通信が 10 秒続いたら 5 秒ごとに確認し、3 回応答がなければ閉じるので、約 25 秒で閉じる。lwIP の既定(2 時間)のままでは、無通信で閉じる 180 秒より先には見つけず、消えた接続が 4 本の枠を占める。

## 3. 実行エンジン

- タイマー: GPTimer を 1MHz で動かし、実行の開始で 0 に戻す。次のレコードの時刻を「開始の時刻 + (base + frame + shift) x frame_period_ns / 1000」マイクロ秒として求め、そこにアラームを設定する。base はくり返しが進める基準、shift は通った選択肢の長さの合計である(binary-format.md「ARMJOIN レコード」)。時刻は開始からの絶対時刻で計算し、誤差を積み重ねない(P8)
- 割り込みの仕事は、どれも RAM 上で一定の時間で終わる操作である。予定の時刻が来たレコード(STATE、SETCNT、DJNZ、AWAIT、ARMJOIN、END)を適用し、同じ時刻のレコードを続けて適用し、次のアラームを設定する
- 遅れの検出: 実際の時刻と予定の時刻の差が 200 マイクロ秒を超えたら件数を数え、最大値を覚える。記録(hardware-design.md §1-5)は supervisor が件数の増加を見て書く。最大値は「状態を表示」と `python -m padcue status` の「最大遅延」の「フレーム処理」に出る
- 今の入力の状態は、割り込みが書き、usb タスクが読む(同じコア)。偶数と奇数の数で書きかけを判別する形(seqlock)にし、C11 の atomic の release と acquire で並べ替えを防ぐ
- 1 回のアラームで適用する、時間を進めないレコードは 64 件までにし、超えたら実行を停止して ERROR にする。壊れた手順データや変換の誤りで割り込みの中の処理が終わらなくなることを、形の確認(下の「実行データ」)に続く 2 段目として防ぐ
- 停止: 停止のフラグ(atomic)を、割り込みは毎回のアラームで、usb タスクはレポートを作るたびに見る。フラグが立っていれば、usb タスクは次に作るレポートから全入力を離すので、長い待ちの途中でも次のアラームを待たない。そのレポートを USB へ渡せるのは前のレポートを Switch が読んだ後で、Switch が受け取るのはその次に読みに来たときである(読みに来る間隔は hardware-design.md §1-1)。「区切りで停止」は予約のフラグで、割り込みがフラグの付いたレコードの予定の時刻に確認する
- 実行データ: RUN のときに、保存した手順データ(<id>.bin)をフラッシュから RAM に読み込んで確認する(中身の id がファイルの名前と合うか、CRC、飛び先の範囲、時間を進めない閉路)。確認したものだけを実行に渡し、実行中は確保も解放もしない

割り込みが戻らなくなったときは、同じコアの中からは回復できない。ESP-IDF の Interrupt WDT が最後の手段で、装置を再起動させる。起動したときは、前回の再起動の理由を PC へ報告する。RAM の上の止まった位置は失われる。この事態そのものは、手順データの確認と、1 回のアラームの上限で起こさない。

実行が正しく終わったのに、状態がまだ RUNNING か AWAITING のまま残ることがある。supervisor(コア 0、100 ミリ秒ごと)がこれを見つけ、終わりの処理(`app_run_end_land`)へ進める。これは表示を実行に合わせるためのもので、実行エンジンの無反応を見つける仕組みではない(9 節)。

## 4. 転送層

ファームウェアは、実行エンジン・Wi-Fi・OTA・手順データの管理を持つ層と、USB のディスクリプターとレポートを作る転送層に分かれる。2 つの層の境は、今の入力の状態を表す `pademu_state_t`(`pademu_core.h`)である。生値で持ち、手順データと同じ座標をとる。転送層はレポートを作るたびにこの値を読み、Switch へ送る形への変換を中で行う(スティックは +2048 して 12 ビットで詰め、モーションは同じ値を 3 サンプルに複製する)。本体から来る通知のうち、プレイヤーの番号は `pademu_procon.h` のコールバックで受ける。振動の指示は使わないので受けない(hardware-design.md §2-2)。

転送層は、有線の Pro コントローラーとして振る舞う 1 つの方式だけを持つ。別の方式に替えるときに書き直すのは転送層だけである。やり取りの記録と、実装が返す値は [design/procon-protocol.md](procon-protocol.md) にあり、根拠は dekuNukem の技術文書と mzyy94 の実装例である(hardware-design.md §6)。

- ディスクリプター: VID 0x057E、PID 0x2009、IN と OUT のエンドポイントを 1 つずつ持つ。bInterval は装置の設定(NVS の usb_binterval)で決め、起動のときにディスクリプターへ書き込む(既定は 1。実物と同じ 8 にもできる。comm-protocol.md の CONFIG)
- HID レポートディスクリプター(203 バイト)は、純正の Pro コントローラーから読み出したバイト列をそのままコピーする。働きが同じに見えても組み立て直さない。中身は `pademu_usb_desc.c` にあり、注釈を付けた原文は `docs/reference/hid_report_descriptor.txt` にある。コンフィグのディスクリプターの wDescriptorLength は `PADEMU_PROCON_HID_DESC_LEN` から作り、手で 2 か所に書かない
- IN のエンドポイントの取り合い: TinyUSB の `tud_hid_report()` は、前の転送が終わっていないとレポートを黙って捨てる(中に待ち行列を持たない)。サブコマンドの応答が捨てられると接続の手順が進まなくなるので、必ず `pademu_tx` を通す。応答は深さ 4 の優先の待ち行列に入れ、定期の入力レポートはその隙間を埋める。usb タスクは IN の転送が終わるたびに起こされ(起こされなくても 1 ミリ秒ごとに確認する)、エンドポイントが空いていれば、応答があれば応答を、なければ定期の入力レポートを送る。待ち行列から溢れた応答は数え、記録の対象にする(正常なときは 0)
- 待ち行列と転送層の状態は、TinyUSB のタスク(本体の要求を受けて応答を待ち行列に入れる)と usb タスク(取り出して送る)の両方が読み書きするので、ミューテックスで守る。割り込みを禁止する排他にしないのは、同じコア 1 で動く実行エンジンの割り込みを遅らせないためである。TinyUSB はコールバックを呼ぶ間に自分のミューテックスを持たないので、usb タスクがこのミューテックスを持ったまま `tud_hid_report()` を呼んでも、互いを待ち続けることはない
- このミューテックスは、USB を始めるかどうかにかかわらず、起動の最初に作る(`app_usb_init()`)。診断モードと Wi-Fi の設定待ちは USB を始めないが、監視のタスクと STATUS は送信の計測値を読む
- USB の再接続(USB_RECONNECT)は、制御のタスクが受けて、Switch とのやり取りの状態をミューテックスの中で最初からにし、切断と接続は usb タスクが行う。USB のレジスターを操作するのを、TinyUSB と同じコア 1 に合わせるためである。`app_usb_is_mounted()` が真なのは、ATTACHED(設定の完了)を受けてから、切断かソフトでの切断までの間だけである。TinyUSB は設定の値を書いた時点で設定済みと答えるが、ATTACHED はその後に出るので、その間に実行を始めると、列挙し直しの検出(ATTACHED のときに実行中なら停止する)と矛盾する。ソフトで切断しても TinyUSB は切断を知らず、設定したままに見えるので、Switch が設定し直すまで偽を返す。送信、実行の開始の判断、STATUS の usb_mounted は、どれもこの関数で決まる
- `tud_hid_report()` の report_id には 0 を渡す。この実装の送る列は、先頭のバイトが既にレポート ID である。0 以外を渡すと TinyUSB がもう 1 バイトを前に付けてエンドポイントの長さを超え、転送が失敗したままエンドポイントが空かず、以後は何も送れなくなる。送る直前に `pademu_tx_report_id_valid()` で確認する
- `0x80` 系のハンドシェイク(01 は状態と MAC を返す、02 と 03 は ACK、04 は HID だけの通信へ切り替えて応答しない)を状態の遷移として作り、どこまで進んだかを到達段階として記録する。つながらないときに、どこで停止したかを外から読むためである
- サブコマンドの応答(0x21): 0x01 登録(ペアリング)、0x02 装置の情報、0x03 入力レポートの形式、0x04、0x10 SPI の読み出し(スティックとモーションの較正の値を返す。生値と実際の値が直線の関係になる値を装置の側で決める)、0x21 NFC と IR の MCU の設定、0x30 プレイヤーの LED(コールバックへ渡す)、0x40 モーションを有効にする、0x48 振動を有効にする。そのほかには安全な既定の応答を返す
- 入力レポート 0x30: タイマーが 1 バイト、ボタンが 3 バイト、スティックが 6 バイト、モーションが 6 軸を 3 サンプル。モーションは今のフレームの値を 3 サンプルに複製する

## 5. メモリとフラッシュ

| 用途 | 上限 | 理由 |
|---|---|---|
| 手順データの受信バッファー | 96KiB(`app_store.h` の APP_STORE_MAX_PROC_SIZE)。頭の 18 バイトを除いて、32 バイトのレコードが 3071 件入る | 長いフレーム表を入れつつ、SRAM 512KB の 4 分の 1 に収める |
| 記録のリング | 12.5KiB(1 件 20 バイトで 640 件、12800 バイトのリング 1 本)。書くのはどれもタスクで、割り込みからは書かない。ロックで順に書き、読むのと削除するのは ctrl タスクの LOGS だけである | PC が記録を読めない間も 2 時間ぶんの記録を保てる大きさにする(hardware-design.md §1-5) |
| 手順を保存するパーティション | procs のパーティション 1MiB(SPIFFS)。内容のハッシュ(16 進 32 桁)を名前にして `<id>.bin` で保存する。パスの 43 バイトが入るよう `CONFIG_SPIFFS_OBJ_NAME_LEN=48` にする | 複数の手順を置いておけるようにする。ESP-IDF の標準で、ほかに依存しない |
| 制御の受け渡し | 送信 8KiB を 1 本、受信 8KiB を接続ごと(同時に 4 本まで。つないでいる間だけ確保する) | 4 本すべてで 40KiB。1 本の受け取りを待ってほかが停止しないよう、受信は分ける |

実行している間はフラッシュへ書き込まない(P3、hardware-design.md §3-1)。このため、送信の割り込みは `CONFIG_GPTIMER_ISR_CACHE_SAFE` と `CONFIG_GPTIMER_CTRL_FUNC_IN_IRAM` を有効にし、割り込みから呼ぶ関数に `IRAM_ATTR` を付けて、フラッシュの外に置く。アプリの外での書き込みも無効にする。Wi-Fi の設定を NVS へ書く機能は `CONFIG_ESP_WIFI_NVS_ENABLED=n`(`sdkconfig.defaults`)で切り、自前のコードの NVS への書き込みは状態の遷移(6 節)で IDLE のときだけに絞る。

## 6. 状態の遷移

```text
BOOT -> WIFI_CONNECTING <-> IDLE <-> RUNNING <-> AWAITING(選択待ち)
                            IDLE <-> OTA(書き込みが済むと再起動する)
(どの状態からも) -> ERROR -> (CLEAR_ERROR) -> IDLE
```

状態の遷移はこの節が定め、comm-protocol.md はここを参照する。IDLE の間に Wi-Fi が切れると WIFI_CONNECTING へ戻り、つながると IDLE へ移る(LED の色で分かる)。

装置のボタンを押したまま電源を入れると、診断モードで起動する(LED は白くゆっくり点滅する)。USB を開始しないので Switch では使えないが、シリアルのログが出続け、シリアルから Wi-Fi の設定を書ける。状態の遷移は上と同じである。

Wi-Fi の接続先が保存されていないときと、新しく保存した接続先に起動のときにつながらなかったときも、ボタンを押さずに同じ形(Wi-Fi の設定待ち)で起動する(app_boot.h)。新しく保存した接続先とは、CONFIG か設定コンソールで保存してから、まだ一度もつながっていない値である。接続先のない装置は PC から何もできず、新しい値でつながらないのは値が誤っている可能性が高いからである。一度つながった接続先につながらないときは、ルーターの不調のような一時的な理由もあるので、普通に起動してつなぎ直し続ける。設定コンソールは、新しく保存した接続先につながらなかった理由を、起動したときの表示と `wifi show` の 1 行(「SSID」に接続できません: 理由)で出す。

更新して最初の起動で Wi-Fi につながらないとき、普通の起動では前のバージョンへ戻すが、診断モードでは新しいバージョンのまま確定する。つながらないバージョンを調べるために診断モードで起動したとき、前のバージョンへ戻ってしまわないようにするためである。

- フラッシュへの書き込み(COMMIT、OTA、NVS)は IDLE のときだけ受け付ける(5 節)
- IDLE でも、USB が未接続のとき(Switch とつながっていない)と、サスペンドしているとき(Switch がスリープしている)は、RUN を拒否する。入力が Switch に送られないまま手順の終わりまで進み、何もしなかった実行が完了として残るからである。Switch 2 はスリープしてもサスペンドせず、レポートを読み続けるので、装置はスリープに気づけない
- RUNNING と AWAITING の間に USB がサスペンドされるか、列挙し直されたら(給電は続いている)、実行を停止し、全入力を離し、止まった位置を記録して ERROR にする。選択待ちで止まっている間も、続きの入力が Switch に送られないので同じにする。ケーブルを抜くと給電も切れるので、装置の側では見つけられない。再起動の理由と、PC の側で TCP が切れたことから、後で PC の側が推定する
- Wi-Fi が切れても状態は変えず、実行を続ける(R9)。その間の記録は RAM に残り、PC が LOGS で読む
- ERROR は CLEAR_ERROR のコマンドで IDLE へ戻す。記録を読む前に自分で戻ることはしない
- AWAITING からは次のように移る(上ほど先に見る)

| 起きたこと | 移る先 |
|---|---|
| 停止 | IDLE(実行を捨て、止まった位置を記録する) |
| USB の切断かサスペンド | ERROR(実行を捨て、止まった位置を記録する) |
| SELECT(選択肢の番号) | RUNNING(選んだ選択肢の経路へ。待った時間は時計に含まれないので、予定の時刻を直さない) |
| 時間切れ | RUNNING(時間切れの選択肢へ) |
| 区切りで停止の予約 | 予約の種類にその選択待ちのフラグが含まれていれば IDLE(その場で停止し、位置を記録する)。含まれていなければ AWAITING のまま |

Wi-Fi の省電力は切る(`esp_wifi_set_ps(WIFI_PS_NONE)`)。既定の MIN_MODEM のままだと、装置はアクセスポイントのビーコンの間隔に合わせてしか受信しないので、PC からの要求を取りこぼし、応答も遅れる。どれだけ取りこぼすかはアクセスポイントの設定(ビーコンの間隔と DTIM)で変わり、多いと PC からはつながらないのと同じになる。USB かドックから給電されるので節電する理由はなく、制御の接続では応答の速さを優先する。

## 7. PC での検証

装置に書き込まずに確認するため、ESP-IDF に依存しない部分を PC の gcc でビルドして動かす。

| ビルドするもの | 何を確認するか | テスト |
|---|---|---|
| 実行エンジン(`pademu_core.c` と `host/core_host.c`) | Python の参照実装(`engine.py`)と、出力する列(フレームとすべての状態)が一致する | `test_firmware_core.py` ほか |
| Pro コントローラーのやり取り(`pademu_procon.c` と `host/procon_host.c`) | Python で書いた Switch の側(`pctool/tests/switchsim.py`)とのやり取りが、公開の仕様と合う | `test_firmware_procon.py` |
| `main/` の状態の遷移・操作権・ボタン・Wi-Fi の資格情報・更新の確定(`main/host/app_host.c`) | ロック・時刻・ボタンの GPIO・NVS・LED・更新先のパーティションを差し替えて、文書に書いた規則どおりに動く | `test_firmware_main.py` |
| 割り込みの側の実行エンジン(`app_engine.c` と `main/host/engine_host.c`) | アラームごとの進み方、停止、止まった位置の記録 | `test_firmware_main.py` |

## 8. 設計判断

- 選択待ちは 1 本のレコードの列で表す(手順の側の形は file-format.md §5)。実行エンジンは AWAIT で入力を変えずに AWAITING へ移り、SELECT で受けた選択肢の飛び先へ跳ぶ。選択肢の末尾の ARMJOIN が、選択肢の長さのぶんだけ時刻をずらして、共有の続きへ戻る(binary-format.md)
- 装置は開始の位置も周回数も受け取らない。実行は必ず先頭のレコードから始まり、END で終わる。周回は手順データの中の SETCNT と DJNZ が数える。途中の位置から始めるときは、その位置から続く手順データを PC が作って送る。周回数と同じく、位置が違えば中身が違うので、別の id になる(binary-format.md)

## 9. 既知の限界

- 実行エンジンの無反応(割り込みがそもそも呼ばれなくなる故障)は見つけられない。Interrupt WDT が装置を再起動させるのは割り込みに入ったまま戻らない場合だけで、GPTimer が割り込みを上げなくなると、実行中のフラグが立ったまま停止する。アラームは毎フレームではなく次に送るレコードの時刻に設定し直すので、間隔が手順ごとに変わり、決まった間隔で監視する方法ではしきい値を決められない
- モーションを 3 サンプルに複製することが、Switch の側の較正とどこまで一致するかは確認していない
