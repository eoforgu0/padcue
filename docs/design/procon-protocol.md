# 有線の Pro コントローラーとしてのやり取り

装置が有線の Pro コントローラーとして Switch とやり取りする内容と、装置が返す値を定める。根拠は、dekuNukem/Nintendo_Switch_Reverse_Engineering(コミュニティの技術文書)、mzyy94 の Linux USB Gadget による実装例、純正の Pro コントローラーと Switch 本体の間の USB 通信の記録(`docs/reference/bypass_procon_log.txt`。以下、通信の記録)である。資料の URL は hardware-design.md §6 にあり、原文のコピーはリポジトリに含めない。通信の記録で確認した値には「実測」と記す。

## 1. USB のディスクリプター(実測)

| 項目 | 値 |
|---|---|
| VID / PID | 0x057E / 0x2009 |
| 文字列 | "Nintendo Co., Ltd." / "Pro Controller" / iSerial "000000000001" |
| クラス | HID(bcdHID 1.11)、Report Descriptor 203 バイト |
| EP IN | 0x81 Interrupt、64B、bInterval=8(実物の値。この装置は 1 を宣言する。hardware-design.md §1-1) |
| EP OUT | 0x01 Interrupt、64B、bInterval=8(実物の値。この装置は IN と同じ値を宣言する) |
| 電源 | Bus Powered + Remote Wakeup、MaxPower 500mA |

レポート ID:

- 入力: 0x30(通常の入力)、0x21(サブコマンドへの応答)、0x81(ハンドシェイクへの応答)
- 出力: 0x01(振動とサブコマンド)、0x10(振動だけ)、0x80(ハンドシェイクの要求)、0x82(用途は分かっていない)

実測では、本体からコントローラーへの出力レポートは種類ごとに長さが違う(0x01 は 49 バイト、0x10 は 10 バイト、0x80 は 2 バイト)。コントローラーから本体への入力レポートは 64 バイトに固定で、余りを 0 で埋める。

## 2. 0x80 系ハンドシェイク

| 要求 | 意味 | 応答(実測) |
|---|---|---|
| 80 01 | 接続状態・デバイス種別・MAC | `81 01 00 03 <MAC 6B 逆順>` (03 = Pro Controller) |
| 80 02 | ハンドシェイク(セッション 1 回) | `81 02` |
| 80 03 | ボーレート 3Mbit 切替 | `81 03`。有線では本体が送らない(通信の記録にない) |
| 80 04 | HID-only・タイムアウト無効 | 応答の有無と形式は分かっていない(通信の記録に 0x81 の応答がない)。この装置は応答しない |
| 80 05 | タイムアウト許可(BT へ戻れる) | 応答の有無と形式は分かっていない。実測では接続の最初に送られる。この装置は応答しない |

MAC のバイト順は、0x80 01 への応答では逆順、サブコマンド 0x02 への応答では正順である(実測。2 つの並びは互いにちょうど逆になっている)。

## 3. 出力レポート 0x01(本体からコントローラーへ)

| オフセット | 内容 |
|---|---|
| 0 | 0x01(振動だけのときは 0x10) |
| 1 | 送るたびに 1 ずつ増える番号(0x0 から 0xF をくり返す) |
| 2-9 | 振動 8 バイト(振動しないときは `00 01 40 40 00 01 40 40`) |
| 10 | サブコマンドの ID |
| 11- | サブコマンドの引数 |

## 4. 入力レポート 0x21(サブコマンドへの応答)

| オフセット | 内容 |
|---|---|
| 0 | 0x21 |
| 1 | timer(送るたびに増える) |
| 2 | 上位ニブル=電池残量(8=満、LSB=充電中)、下位=接続情報(Pro/USB 給電は 0x1) |
| 3-5 | ボタン 3 バイト |
| 6-8 / 9-11 | 左 / 右スティック(12 ビットの値 2 つを 3 バイトに詰める。6 節) |
| 12 | vibrator report |
| 13 | ACK(MSB=1。単純 ACK=0x80、種別付きは 0x80\|種別) |
| 14 | 応答するサブコマンドの ID(要求の値をそのまま返す) |
| 15-49 | 応答のデータ(最大 35 バイト) |

ACK の値(実測)は、サブコマンド 0x01 に 0x81、0x02 に 0x82、0x04 に 0x83、0x10 に 0x90、0x21 に 0xa0 で、0x03、0x08、0x30、0x40、0x48 には単純 ACK の 0x80 である。

## 5. 入力レポート 0x30(通常の入力。IMU を含む)

| オフセット | 内容 |
|---|---|
| 0 | 0x30 |
| 1 | timer |
| 2 | 電池/接続(0x21 と同じ) |
| 3 | Y=0x01 X=0x02 B=0x04 A=0x08 SR=0x10 SL=0x20 R=0x40 ZR=0x80 |
| 4 | Minus=0x01 Plus=0x02 R スティック=0x04 L スティック=0x08 Home=0x10 Capture=0x20 |
| 5 | Down=0x01 Up=0x02 Right=0x04 Left=0x08 SR=0x10 SL=0x20 L=0x40 ZL=0x80 |
| 6-8 / 9-11 | 左 / 右スティック(12 ビットの値を詰めたもの。6 節) |
| 12 | vibrator report |
| 13-48 | IMU 36 バイト。3 サンプル(0、5、10ms 相当)のそれぞれに accel XYZ と gyro XYZ を、各 int16 LE で並べる |

生値から物理量への換算は、この装置が返す較正値(工場較正の 0x6020 と、ユーザー較正の 0x8028。7 節)が決める。

静止しているときも、加速度には重力のぶんを送る。下の式に、この装置が返す原点 0 と accel の係数 16384 を入れると、1G は生値 4096 になる。実物の Pro コントローラーが 0x6080 で返す水平オフセットの実測値 `50 fd 00 00 c6 0f` = (-688, 0, 4038) も、Z 軸がほぼ 1G である。加速度を全軸 0 で送ると、自由落下を報告していることになり、重力から基準の姿勢を決めるゲームでは、ジャイロを送っても向きが変わらない。公開されている変換式(Linux の hid-nintendo などが実装しているもの)は次の形で、分母はコントローラーが自分で申告した係数である。

```text
accel[G]   = (raw - accel原点)  * 4.0   / (accel係数 - accel原点)
gyro[dps]  = (raw - gyro原点)   * 936.0 / (gyro係数  - gyro原点)
```

この装置が返す値(`pademu_procon.c`)は、原点 0、accel の係数 16384、gyro の係数 13371 である。13371 は dekuNukem の資料に工場較正の例として記載されている値である。これらを式に入れると、次のようになる。

| 軸 | 換算 | 生値 1 あたり |
|---|---|---|
| accel | 4.0 / 16384 | 0.000244140625 G |
| gyro | 936.0 / 13371 | 0.0700022 dps |

較正値を使わずに、測る範囲を 32768 で割って読む方法もある。この読み方では、gyro の生値 1 は 2000dps / 32768 = 0.06103 dps で、上の式の 0.0700 dps とは違う。accel では 8G / 32768 = 0.000244 G で、上の式の値と一致する。accel で一致することは、上の式が正しいことの傍証になる。

Switch 2 がこの式どおりに較正値を使うか(使わずに決まった係数で読むか)は確認していない(9 節)。

### この値の扱い

角度で指定する機能は作らない。ゲームの側の補正で、生値と角度の関係が線形にならないためである(specs/binary-format.md の「設計判断」)。生値をそのまま送るので、換算がどうであっても運用は成り立つ。較正値は標準の値のまま固定する。

上限 32767 は、上の式で約 2294 dps に当たる。この上限で足りる速さが出るかは確認していない(9 節)。足りないときは、申告する gyro の係数を小さくする。係数を半分にすると、生値 1 あたりの dps が倍になり、上限の速さも倍になるが、分解能は下がる。ただし、これは Switch 2 がこの装置の較正値を使っているときにだけ働く。使っているかは、係数を 2 倍か半分にして、回る量が比例して変わるかで判別できる。角度を読む必要はなく、半分になったか変わらないかを見れば足りる。

## 6. スティックの値の詰め方

3 バイトから 12 ビットの値を 2 つ読む式は次のとおりである。

```text
x = d[0] | ((d[1] & 0x0F) << 8);  y = (d[1] >> 4) | (d[2] << 4)
```

この装置の符号付きの生値(-2048 から +2047)の各軸に 2048 を足し、その値を x と y として 3 バイトに詰める。生値と詰めた値は 1 対 1 に対応する。読み出すときは、上の式で得た x と y から 2048 を引く。

## 7. サブコマンドへの応答の内容

- 0x01 ペアリング: 有線でも送られる。引数の構造は `[0]=フェーズ [1..6]=本体 BT MAC(LE) [7..]=フェーズ依存` である。
  - フェーズ 0x04(登録済みの本体の情報を渡す): 実測。引数は "Nintendo Switch" の ASCII と、鍵とみられる末尾を含む。実物の Pro コントローラーの応答はデータ部が `03`(以降は 0)で、この装置も同じ応答を返す(通信の記録とデータ部が一致する)
  - フェーズ 0x01(新しいペアリングの開始): 本体にこの装置の登録の記録がないときに送られ、完了するまで 100〜400ms の間隔で要求がくり返される。完了しない間、本体はコントローラーを登録せず、すべての入力を無視する(この装置をつないで確認した)。このとき、ハンドシェイク、IMU の有効化、LED までは正常に進み、操作だけが反映されない。応答は、dekuNukem の資料に従って、データ部 `[01][装置の MAC(LE) 6 バイト][ディスクリプター(中身は分かっていないので 0)]` を返す
  - フェーズ 0x02(LTK の要求): データ部 `[02][LTK 16 バイト]` を返す。LTK は装置の MAC から決まる固定の値で、各バイトを 0xAA と XOR する。毎回同じ値なので、本体の側に保存された値と常に一致する
  - フェーズ 0x03(保存): データ部 `03` を返す(フェーズ 0x04 の応答と同じ)
  - フェーズ 0x01 と 0x02 の応答は、実物の Pro コントローラーで測っていない(dekuNukem の Bluetooth の資料に従う)。STATUS の pair_reqs と pair_step で、要求がくり返されている(受け付けられていない)ことを外から判別できる。「pair_step が 1 か 2 のままなら未完了」という判別方法も同じ資料による仮定で、正常な有線のやり取りがフェーズ 0x03 か 0x04 で終わることは測っていない(9 節)
- 0x02 装置の情報(実測): `03 48 03 02 <MAC 6 バイト 正順> 03 01`。前から順に、FW 3.72、種別 3(Pro)、固定値 0x02、MAC、byte10(資料では常に 0x01 だが、実測では 0x03)、色の情報あり(0x01)
- 0x03 入力レポートの形式の設定: 引数 0x30(standard full mode)に、単純 ACK を返す
- 0x04 トリガーの経過時間: uint16 LE を 7 つ(L、R、ZL、ZR、SL、SR、HOME。単位は 10ms)
- 0x08 出荷時の省電力の設定: 単純 ACK を返す(本体は接続ごとに `08 00` を送る)
- 0x10 SPI の読み出し: 要求はアドレス(u32 LE)とサイズ(u8。最大 0x1D)。応答はアドレス(u32 LE)、サイズ、データ
- 0x30 プレイヤーの LED: 下位 4 ビットが点灯、上位 4 ビットが点滅(USB では点滅も点灯として扱われる)。単純 ACK を返す。装置は受けた値をシリアルのログに出すだけで、装置の記録(LOGS)にも LED の表示にも使わない(comm-protocol.md「装置の状態と LED」)
- 0x40 IMU の有効化と 0x48 振動の有効化: 引数は 0 か 1。単純 ACK を返す
- 0x21 NFC と IR の MCU の設定: USB でも送られる(ACK は 0xa0)。応答のデータ部は、通信の記録の値をそのまま返す。`01 00 ff 00 03 00 05 01` で始まり、オフセット 48 に `5c` がある。意味は分かっていないが、本体が中身を確認していても通るように、純正品と同じバイト列にする

### SPI のアドレスと、この装置が返す値

| アドレス | 内容 | 実測の応答 |
|---|---|---|
| 0x6000 | シリアル番号 | `ff` が 16 バイト(未設定) |
| 0x603D (25B) | 左右のスティックの工場較正と、本体の色 | 較正の 18 バイトは個体ごとの値なので記載しない。続く 7 バイトは `ff 32 32 32 ff ff ff` |
| 0x6020 (24B) | IMU の工場較正(accel の原点と係数、gyro の原点と係数。各 int16 LE)。生値から物理量への換算を決める(5 節) | 通信の記録にない |
| 0x6080 (24B) | IMU の水平オフセットと、スティックのパラメーター 1 | 先頭が `50 fd 00 00 c6 0f`(既定値と一致) |
| 0x6098 (18B) | スティックのパラメーター 2 | パラメーター 1 の後半と同じ |
| 0x8010 | ユーザー較正の領域。0x8010〜0x8025 はスティック(実測では `ff` で未設定)、0x8026〜0x8027 はユーザー IMU 較正の目印 `b2 a1`(実測で設定済み) | `ff` が 22 バイトと、`b2 a1` |
| 0x8028 (24B) | ユーザー IMU 較正の本体 | 個体ごとの値なので記載しない |

実測では 0x8026 の目印が立っており、本体は 0x8028 のユーザー較正を読んで使う。工場較正 0x6020 を読む経路は通信の記録に一度も現れず、確認していない。この装置は実物と同じ経路を通す。目印 `b2 a1` を立て、0x8028 にも工場較正と同じ値(原点 0、accel の係数 16384、gyro の係数 13371)を返す。どちらを読まれても、生値から物理量への換算は同じ直線になる(specs/binary-format.md の「生値原則」)。

スティックの較正のデータは、9 バイトに 12 ビットの値を 6 つ詰めたもの(X と Y の最大、中心、最小)で、最小と最大は中心からの差で表す。この装置は中心を 2048 にし、振れ幅を最大に取って、線形になる値を返す。送れる値の分解能を下げないためである。

## 8. 接続の手順(実測の順序)

```text
80 05 -> 80 01 -> 80 02
-> 0x03(入力レポートの形式を 0x30 に)
-> 80 04(HID-only)
-> 0x48(振動 off)-> 0x02 x2(装置の情報)-> 0x08(省電力 off)
-> 0x10 x2(SPI: 0x6000, 0x6050)
-> 0x01(有線のペアリング。フェーズ 0x04 = 登録済みの本体の情報を渡す。7 節)
-> 0x03(再送)-> 0x04
-> 0x10 x5(SPI: 0x6080, 0x6098, 0x8010, 0x603D, 0x8028)
-> 0x40(IMU on)-> 振動だけの出力レポート x6
-> 0x48(振動 on)-> 0x21(NFC と IR の MCU の設定)-> 0x30(LED 点灯)
-> 以後、入力レポート 0x30 を続けて送る
```

0x80 04 より前にもサブコマンドを受け取る(上の 0x03)。このため装置は、0x80 系のハンドシェイクが終わるのを待たずにサブコマンドに応答する。

## 9. 確認していないこと

1. 0x80 04 と 0x80 05 への応答の有無と形式
2. 0x02 の応答の byte10 の正しい値(資料では 0x01、実測では 0x03)
3. 出力レポート 0x82 の用途
4. 実物が 0x30 を送る頻度(60Hz か 120Hz か)。この装置は、Switch が読みに来るたびに送る。Switch 2 の本体での測定では、約 172 回/秒である(`firmware/main/app_usb.c`)
5. サブコマンド 0x01(有線のペアリング)の引数の詳細
6. タイムアウトの具体的な秒数
7. 0x21 のサブコマンドの応答に含まれるボタンとスティックの欄を、Switch がゲームの入力として読むか。この装置は、mzyy94 の実装例と同じく、全入力を離した値を入れる。読むのであれば、入力を保っている間にサブコマンドの応答が挟まると、その応答の間だけ入力が離れたように読まれる(R1 を損なう)
8. Switch 2 が較正値(0x6020 と 0x8028)を 5 節の式どおりに使うか
9. 生値の上限 32767 のジャイロで、足りる速さが出るか
10. 有線のペアリングでのフェーズ 0x01 と 0x02 への応答と、正常なやり取りが終わるフェーズ
