# Pro コントローラー 有線USB プロトコル実装メモ

作成: 2026-07-29 ／ 出典: dekuNukem/Nintendo_Switch_Reverse_Engineering(コミュニティ資料)、mzyy94 の Linux USB Gadget 実装および**実機キャプチャログ**(純正 Pro コン↔Switch 本体の USB 通信を中継取得したもの)。**実機キャプチャで確認できた値には「実測」と記す**。

## 1. USB ディスクリプタ(実測)

| 項目      | 値                                                                        |
|-----------|---------------------------------------------------------------------------|
| VID / PID | 0x057E / 0x2009                                                           |
| 文字列    | "Nintendo Co., Ltd." / "Pro Controller" / iSerial "000000000001"          |
| クラス    | HID(bcdHID 1.11)、Report Descriptor 203 バイト                            |
| EP IN     | 0x81 Interrupt、64B、**bInterval=8**(実在品。本システムは 1 を宣言=7.3-1) |
| EP OUT    | 0x01 Interrupt、64B、bInterval=8                                          |
| 電源      | Bus Powered + Remote Wakeup、MaxPower 500mA                               |

レポートID: 入力 0x30(通常入力)/0x21(サブコマンド応答)/0x81(ハンドシェイク応答)、出力 0x01(rumble+サブコマンド)/0x10(rumble のみ)/0x80(ハンドシェイク要求)/0x82(**用途未確認**)。

**実測の重要点**: ホスト→デバイスの出力レポートは**可変長**(0x01=49B、0x10=10B、0x80=2B)。デバイス→ホストの入力レポートは 64B 固定(ゼロパディング)。

## 2. 0x80 系ハンドシェイク

| 要求  | 意味                          | 応答(実測)                                                     |
|-------|-------------------------------|----------------------------------------------------------------|
| 80 01 | 接続状態・デバイス種別・MAC   | `81 01 00 03 <MAC 6B 逆順>` (03 = Pro Controller)              |
| 80 02 | ハンドシェイク(セッション1回) | `81 02`                                                        |
| 80 03 | ボーレート 3Mbit 切替         | `81 03`。**有線では本体が送ってこない**(実測で未出現)          |
| 80 04 | HID-only・タイムアウト無効    | **応答の有無・形式は未確認**(実測ログにも 0x81 応答が見えない) |
| 80 05 | タイムアウト許可(BT へ戻れる) | 同上未確認。**実測では接続の最初に送られてくる**               |

**MAC のバイト順**: 0x80 01 応答は逆順、サブコマンド 0x02 応答は正順(実測で相互に完全反転を確認)。

## 3. 出力レポート 0x01(ホスト→デバイス)

| オフセット | 内容                                              |
|------------|---------------------------------------------------|
| 0          | 0x01(または 0x10 = rumble のみ)                   |
| 1          | パケットカウンタ(0x0..0xF 循環)                   |
| 2-9        | rumble 8B(ニュートラル `00 01 40 40 00 01 40 40`) |
| 10         | サブコマンドID                                    |
| 11-        | サブコマンド引数                                  |

## 4. 入力レポート 0x21(サブコマンド応答)

| オフセット | 内容                                                                     |
|------------|--------------------------------------------------------------------------|
| 0          | 0x21                                                                     |
| 1          | timer(インクリメント)                                                    |
| 2          | 上位ニブル=電池残量(8=満、LSB=充電中)、下位=接続情報(Pro/USB 給電は 0x1) |
| 3-5        | ボタン 3B                                                                |
| 6-8 / 9-11 | 左 / 右スティック(12bit×2 の 3B パック)                                  |
| 12         | vibrator report                                                          |
| 13         | **ACK**(MSB=1。単純 ACK=0x80、種別付きは 0x80\|種別)                     |
| 14         | 応答対象のサブコマンドID(エコー)                                         |
| 15-49      | 応答データ(最大 35B)                                                     |

**ACK 値(実測)**: 0x01→0x81 / 0x02→0x82 / 0x03→0x80 / 0x04→0x83 / 0x08→0x80 / **0x10→0x90** / 0x21→0xa0 / 0x30→0x80 / 0x40→0x80 / 0x48→0x80

## 5. 入力レポート 0x30(通常入力・IMU 付き)

| オフセット | 内容                                                                          |
|------------|-------------------------------------------------------------------------------|
| 0          | 0x30                                                                          |
| 1          | timer                                                                         |
| 2          | 電池/接続(0x21 と同じ)                                                        |
| 3          | Y=0x01 X=0x02 B=0x04 A=0x08 SR=0x10 SL=0x20 R=0x40 ZR=0x80                    |
| 4          | Minus=0x01 Plus=0x02 Rスティック=0x04 Lスティック=0x08 Home=0x10 Capture=0x20 |
| 5          | Down=0x01 Up=0x02 Right=0x04 Left=0x08 SR=0x10 SL=0x20 L=0x40 ZL=0x80         |
| 6-8 / 9-11 | 左 / 右スティック(12bit パック)                                               |
| 12         | vibrator report                                                               |
| **13-48**  | IMU 36B = 3 サンプル(0/5/10ms 相当)× [accel XYZ, gyro XYZ] 各 int16 LE        |

**生値 → 物理量の換算は、こちらが 0x6020 で返す較正値が決める。**

**静止時も重力ぶんを送ること。** 上の式(原点 0 / accel 係数 16384)から 1G = 生値 4096。実機プロコンが 0x6080 で返す水平オフセットの実測値 `50 fd 00 00 c6 0f` = (-688, 0, 4038) も Z 軸のほぼ 1G と一致する。加速度を全軸 0 で送ると自由落下を報告していることになり、重力から基準の姿勢を決めるゲームではジャイロが効かない。
公開されている変換式(Linux hid-nintendo などが実装しているもの)は次の形で、
分母は**コントローラーが自己申告した係数**である。

```
accel[G]   = (raw - accel原点)  * 4.0   / (accel係数 - accel原点)
gyro[dps]  = (raw - gyro原点)   * 936.0 / (gyro係数  - gyro原点)
```

本システムが返している値(`pademu_procon.c`)は 原点 0 / accel 係数 16384 /
gyro 係数 13371(実機の標準値)。これを式に入れると:

| 軸    | 換算          | 生値 1 あたり        |
|-------|---------------|----------------------|
| accel | 4.0 ÷ 16384   | **0.000244140625 G** |
| gyro  | 936.0 ÷ 13371 | **0.0700022 dps**    |

つまり **gyro は 1 生値 = 約 0.0700 dps** で確定する。よく見る 0.06103 という値は
「±2000dps ÷ 32768」という**較正値を使わない素の読み**であり、上の式とは別物。
(accel 側の 0.000244 は上の式から出る値と完全に一致しており、式が正しいことの傍証になる)

**残る未確認**: Switch 2 がこの式どおりに較正値を使うか(使わず固定係数で解釈する可能性)。
0x30 のレート 60Hz/120Hz も資料内で矛盾しており**未確認**。

### この値をどう扱うか(角度指定は作らないと決めたため、確認は1点だけ)

**角度で指定する機能は採用しない**(ゲーム側の補正で線形にならないため。
specs/procedure-format.md の未決事項を参照)。生値をそのまま送るだけなので、
換算が何であっても運用は成立する。**較正値は標準値のまま固定**する。

残る実用的な問いは **「生値の上限で足りる速さが出るか」** だけ。
上限 32767 は上式では約 2294 dps に相当する。実機で最大値を送って十分速く回れば
それで終わり。足りなかった場合の逃げ道は、**申告する gyro 係数を小さくすること**
(係数を半分にすると 1 生値あたりの dps が倍になり、上限速度も倍になる。
刻みは粗くなる)。ただしこれは **Switch 2 がこちらの較正値を使っている場合のみ**
効くので、そのときは係数を 2 倍/半分にして回転量が比例して変わるかを見て判別する
(角度を読む必要はなく、「半分になったか/変わらないか」で足りる)。

## 6. スティックの 12bit パック(実装の要)

```
生値デコード: x = d[0] | ((d[1] & 0x0F) << 8);  y = (d[1] >> 4) | (d[2] << 4)
```
本システムの符号付き生値(-2048..+2047)は、この x/y に +2048 したものを詰める(1:1 対応)。

## 7. サブコマンド応答の内容

- **0x01 ペアリング(有線でも送られてくる)**: 引数の構造は
  `[0]=フェーズ [1..6]=本体 BT MAC(LE) [7..]=フェーズ依存`。
  - **フェーズ 0x04**(既知本体の記録手渡し): 実測(bypass_procon_log.txt)。
    引数に "Nintendo Switch" の ASCII と鍵とみられる末尾を含む。実機プロコンの
    応答はデータ部 `03`(以降ゼロ)で、本実装も同じ(全バイト一致で検証済み)
  - **フェーズ 0x01**(新規ペアリング開始): **本体にこの個体の登録記録が
    無いとき**に送られ、完了するまで 100〜400ms 間隔で再要求される。
    **完了しない間、本体はコントローラー登録を行わず全ての入力を無視する**
    (2026-08-06 に実測。ハンドシェイク・IMU 有効化・LED まで正常のまま
    操作だけ効かない、という形で現れる)。応答は dekuNukem 資料に従い
    データ部 `[01][自機 MAC(LE) 6B][記述子(内容未解明・ゼロ)]` を返す
  - **フェーズ 0x02**(LTK 要求): データ部 `[02][LTK 16B(各バイト 0xAA XOR)]`。
    LTK は自機 MAC から決まる固定値(毎回同じ = 本体側の保存と矛盾しない)
  - **フェーズ 0x03**(保存): データ部 `03`(従来どおり)
  - **注意**: フェーズ 0x01/0x02 の応答は**実機プロコンでの実測が未採取**
    (dekuNukem の BT 資料準拠)。通らない場合は Pi のバイパスで実物の
    ペアリング交換を採取して突き合わせること。STATUS の pair_reqs /
    pair_step で「再要求が続いている=未受理」を外から判定できる。
    **「pair_step 1/2 のまま=未完」という判定規則も同資料由来の未検証の
    仮定**(正常な有線交換がフェーズ 0x03/0x04 で終わるとは実測していない)。
    入力が効いているのに未完表示が消えない場合は、採取ログで実機の終端
    フェーズを確認し、判定側(cli.py `_print_pairing` / gui.py `statusRows`)
    を実測に合わせて直すこと
- **0x02 デバイス情報**(実測): `03 48 03 02 <MAC 6B 正順> 03 01` = FW 3.72 / 種別 3(Pro)/ 固定 0x02 / MAC / **byte10 は資料の「常に 0x01」に反して実測 0x03** / 色情報あり 0x01
- **0x03** 入力レポートモード設定(引数 0x30 = 通常フルモード)→ 単純 ACK
- **0x04** トリガー経過時間: uint16 LE × 7(L/R/ZL/ZR/SL/SR/HOME、10ms 単位)
- **0x08** 出荷時省電力設定 → 単純 ACK(本体は接続毎に `08 00` を送る)
- **0x10 SPI 読み出し**: 要求 = アドレス u32 LE + サイズ u8(最大 0x1D)。応答 = アドレス u32 LE + サイズ + データ
- **0x30 プレイヤーLED**: 下位4bit=点灯、上位4bit=点滅(USB では点滅も点灯扱い)→ **本システムでは 1P/2P の判別に使う**
- **0x40 IMU 有効化** / **0x48 振動有効化**: 引数 0/1 → 単純 ACK
- **0x21 NFC/IR MCU 設定**: USB でも送られてくる(ACK 0xa0)。応答データ部は実測ログの値をそのまま返す(`01 00 ff 00 03 00 05 01 …(+33)5c`。意味は未解明だが、本体が中身を検査していても通る)

### SPI アドレス(自作側が返す値。生値原則の成立点)

| アドレス         | 内容                                                                                                                                 | 実測応答例                                                                   |
|------------------|--------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| 0x6000           | シリアル番号                                                                                                                         | `ff`×16(未設定)                                                              |
| **0x603D** (25B) | 左右スティック工場較正+本体色                                                                                                        | `ba 15 62 11 b8 7f 29 06 5b ff e7 7e 0e 36 56 9e 85 60 ff 32 32 32 ff ff ff` |
| 0x6020 (24B)     | IMU 工場較正(accel 原点/係数、gyro 原点/係数 各 int16 LE)。**ここが生値→物理量の換算を決める**(§5)                                   | —                                                                            |
| 0x6080 (24B)     | IMU 水平オフセット+スティックパラメータ1                                                                                             | 先頭 `50 fd 00 00 c6 0f`(既定値と一致)                                       |
| 0x6098 (18B)     | スティックパラメータ2                                                                                                                | パラメータ1 の後半と同一                                                     |
| 0x8010           | ユーザー較正領域。0x8010〜0x8025 = スティック(実測 `ff` = 未設定)、**0x8026-0x8027 = ユーザーIMU較正の目印 `b2 a1`(実測で設定済み)** | `ff`×22 + `b2 a1`                                                            |
| 0x8028 (24B)     | ユーザー IMU 較正本体                                                                                                                | `be ff 3e 00 f0 01 00 40 00 40 00 40 ...`                                    |

**ユーザーIMU較正の扱い(2026-07-31 自作側の方針)**: 実測ログでは 0x8026 の目印が
立っており、本体は **0x8028 のユーザー較正を読んで使う**(工場較正 0x6020 への
フォールバックは実測ログに一度も現れない未検証経路)。自作機は実機と同じ道を通す:
目印 `b2 a1` を立て、0x8028 にも**工場較正と同一の値**(原点 0 / accel 係数 16384 /
gyro 係数 13371)を返す。どちらを使われても換算が同一の直線になる(生値原則)。

**較正データの意味**: 9B に 12bit×6(最大/中心/最小の X,Y)。最小・最大は**中心からの相対差分**で格納される。自作機では**中心 2048、振れ幅を最大に取り、線形**になる値を返す(送信分解能の刻みを潰さないため)。

## 8. 接続シーケンス(実測の順序)

```
80 05 -> 80 01 -> 80 02
-> subcmd 0x03(0x30 モード設定)
-> 80 04(HID-only)
-> 0x48(振動 off)-> 0x02 x2(デバイス情報)-> 0x08(省電力 off)
-> 0x10 x複数(SPI: 0x6000, 0x603D, 0x6080, 0x6098, 0x8010, 0x8028 ...)
-> 0x01(有線ペアリング。この初期化列ではフェーズ 0x04 = 既知本体の記録手渡し。ACK 0x81 + `03 00 00...` を返す。フェーズ構造と 0x01/0x02 の応答は 7節 を参照)
-> 0x03 再送 -> 0x04 -> 0x10 x複数 -> 0x40(IMU on)
-> rumble x複数 -> 0x48(振動 on)-> 0x21(NFC/IR、ACK 0xa0)-> 0x30(LED 点灯)
-> 以後 0x30 入力レポートを常時送出
```

**実装上の含意**: 0x80 04 の前にもサブコマンドは流れてくる。つまり**ハンドシェイク完了を待たずにサブコマンド応答を実装しておく必要がある**。

## 9. 未確認事項(実装時に実機で確認)

1. 0x80 04 / 0x80 05 への応答の有無・形式
2. 0x02 応答 byte10 の正しい値(資料 0x01 / 実測 0x03)
3. 出力レポート 0x82 の用途
4. 0x30 のレート(60/120Hz)、gyro 換算係数(0.06103 / 0.070)
5. サブコマンド 0x01(有線ペアリング)のペイロード詳細
6. タイムアウトの具体的秒数
7. **Switch 2 が上記シーケンスをそのまま受理するか(未検証事項3。到着日の最重要確認)**
8. 0x21 サブコマンド応答に含まれるボタン・スティック欄を Switch がゲーム入力として採取するか。現実装は参照実装(mzyy94)と同じくニュートラル固定。**採取していた場合、入力保持中にサブコマンド応答が挟まると一瞬入力が抜ける**(R1 の失敗モード)ため、到着後に確認する
9. HID ゲームパッド方式(保険モード)のレポートディスクリプタは公開実装で広く使われている形をそのまま用いているが、一次資料との照合は未実施(保険モードを使う段になったら照合する)
