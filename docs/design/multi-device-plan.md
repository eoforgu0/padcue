作成: 2026-08-04 ／ 状態: **実装済み**(実機2台で検証済み)。
§0.1 の決定と D1〜D10 は、コードがコメントから参照する契約なので
動かさない(coupler.py / devicepool.py / registry.py)。
この設計に至るまでの改訂: ユーザー決定(§0.1)と、設計自体への敵対的レビュー
14件を反映。残っていた3問の回答も反映した(§3)。画面設計は4案を比較し

## 0. 真の目的と決定済み事項

目的: **Switch 2台+デバイス2台で、2人分の自動操作をする**。

### 0.1 ユーザー決定(2026-08-04。蒸し返さない)

- **開始の同時性はラフでよい**。「全装置へ転送→全転送完了→実行信号を続けて送る」
  方式(開始ズレ数十ms級、WiFi 次第で百ms強)。ミリ秒同期(ARM+GO)は不要
- ズレ対策が要る場面は**手順の調整と「待って選ぶ」(待機分岐)**で行う。そのため
  **2台へ同時に SELECT を送る仕組みは必須**
- **両方が選択待ちに到達したら自動で選んで再開する「自動合流」も必須**
- 識別は**内部 = MAC、表示 = ユーザーが付ける名前**(例: 1P/2P)
- どの Switch に繋がっているかの自動識別は求めない。**物理記名**+GUI の
  「識別」ボタン(その装置だけに短い無害な入力を送り、本体のコントローラー
  画面で反応を見る)。ハンドシェイク中に本体識別子(ホスト MAC 等)が取れないか
  だけは実機ログで一度確認する(取れたら常時表示、取れなければ物理記名で確定)
- **既存の1台運用は損なわない**(装置1台登録の間は従来と同じ見た目・操作)
- **片方異常時の相方の扱いは「開始のされ方」で決まる**:
  それぞれ個別に開始した(かつ自動合流なし)→ 相方は続行。
  **セットとして同時開始した、または自動合流を使っている → 両方止める**
  (自動合流なしでもタイミング調整だけで噛み合わせるセット運用があり得るため、
  「セット開始=連動、個別開始=独立」という開始時の意思で決める)。
  異常 = 装置自身の異常報告、または PC から約5秒見えない状態。
  止め方は「今の周で止める」を既定とする
- **人為の停止は連動しない**(2026-08-05 確定): 連結中でも、人が片方の停止
  ボタンを押したならその装置だけ止まり、相方は続行する(連動するのは
  「異常」だけ)。さらに、**人為的に片方を止めた後**に残された側が自動合流の
  待機分岐へ到達した場合は、相方を待たずに**自動でソロ進行**する(相方の
  不在は人間の意図によるものなので、駐機して待たない。異常で相方が消えた
  場合はこの縮退はせず、警告して§0.1の連動規則に従う)
- **手動操作は対象装置を選んで同時1台のみ**(2台同時の手動操作は対象外)
- **2台は同一 AP・同一セグメント・同一型番**で運用する(探索=自動発見を主経路に。
  IP 手動登録は CLI の逃げ道として残すが、専用 UI は作らない)

## 1. 調査で確定した現状(要点)

**PC 側の1台前提**(全て要改修):

- 設定 `padcue.json` = 単一 host/port。書き手5箇所。CLI は繋がらないと
  **黙って別の1台に乗り換えて保存**する(2台環境では誤爆経路。廃止)
- GUI サーバ: 接続1本+プロセス唯一の lock。片方無応答で毎秒3〜6秒握り、
  もう片方の停止ボタンまで固まる(R3 違反)
- 全 API に装置指定なし。ログはエントリに装置識別が無いうえ装置側読み出しが
  破壊的(後から区別不能)
- ファームの探索応答(UDP)には id=MAC があるが **HELLO(TCP)に id が無い**
  = 接続後の個体確認が不可能。mDNS 名は "pademu" 固定で2台衝突

**問題にならないこと**: ファーム実行系・WiFi 設定(個体 NVS)・TCP サーバは装置独立。
手順・部品は装置に縛られない中立資産。探索は複数台応答を既に収集できる。

**レビューが発見した既存の乖離(2台化と独立の問題)**:
**待機分岐のタイムアウト(timeout_frames / on_timeout)が実機・mock とも未実装**。
バイナリから復号はするが誰もカウントせず、選択が来なければ永久駐機する
(flow-format.md §7 の記述と実装が乖離)。→ 自動合流の脱出口として P4 で実装する
(既知の乖離として作業記録に記載済み)。
**→ 2026-08-06 解消済み**: 実機は supervisor(100ms 周期)が実時間で数え、
mock も同じ規則。0=中断 / 1..n=その腕へ(通常の SELECT と同じ経路)。

## 2. 設計方針

- **D1 データモデルは N 台、UI は2台に最適化**。
  設定: `devices: [{id(MAC・保存キー), name(表示名), host, port}]`。
  **保存キーは常に id**。name はいつでも改名でき、ログやセットの参照は切れない。
  旧形式 {host, port} は初回読込で自動移行(devices の1件目・name="1P")。
  **移行前に padcue.json と logs.jsonl を自動バックアップ**し、移行後も
  旧キー {host, port} を併記保存(P1 期間中の旧 GUI/旧ツールが読めるように)
- **D2 個体照合**。ファーム: HELLO へ id 追加+mDNS 名を `pademu-<MAC下4桁>` へ。
  PC: 接続は**「id 検証付きファクトリ」1箇所に集約**(gui/cli/探索の全経路)し、
  接続確立時に HELLO の id と登録 id を照合、不一致は操作拒否。
  **例外 = 受け入れモード**: 明示操作(device add)の間だけ、id 無し HELLO
  (旧ファーム)の装置に HELLO と OTA のみ許可(新装置の初回更新・登録経路。
  これが無いと「id が無いから拒否 → id を載せる OTA もできない」の鶏卵になる)
- **D3 接続の契約**: **1装置 = 1接続 = 1装置lock**。状態収集も操作(RUN/STOP/
  SELECT)も**同じ接続**を装置 lock の下で使う(ファームは同時1接続・後着横取り
  のため、収集と操作を別接続にすると奪い合いになる)。lock の粒度は1コマンド
  (操作は収集サイクルの合間に必ず割り込める)。収集はバックグラウンドで並列、
  /api/state はキャッシュ即答。片方の無応答はその装置の「未接続」表示に留まる
- **D4 装置に触る API のみ dev(装置 id)必須**(run/stop/select/passthrough/
  status/logs/識別 等)。手順・部品の編集系 API は装置と無関係なので従来のまま
- **D5 ログ**: 回収時に**装置 id タグ**を付与(表示は name に解決)。
  logs.jsonl への書き込みは**単一ライタ**(専用 lock。装置別 lock 化で今の
  「偶然の直列化」が消えるため明示的に守る)。保持上限は装置数×5000 行。
  **回収の所有者は GUI サーバに一本化**(装置側は読むと消えるため、CLI logs は
  GUI サーバ稼働中はそれ経由で読む)。装置間の時刻整列は要件外と明記
  (t_ms は装置ローカル時計。合流の検証はゲーム画面で行う)
- **D6 セット**: `sets/<名前>.json` = `{名前, [(装置id, 手順名, 周回数)…], 設定}`。
  実行画面の主役はセット(1台しか登録が無ければ従来と同じ単独実行 UI)
- **D7 合流(バリア)の仕様**:
  - 対象: セット設定で「自動合流: ON」の待機分岐。対応付けは**到達順**
    (装置ごとに n 回目のバリア到達同士を対にする。周回のたびに毎回停止する
    AWAIT の性質上、これが最も単純で予測可能)
  - 自動選択の腕はセット定義に書く(既定 = 腕1)。画面を見て人が選ぶ分岐は
    自動対象から外し、**手動でも「両方へ同時 SELECT」ボタン**を出す
  - 誤爆防止: SELECT に**世代(その装置の何回目の駐機か)**を付け、装置側で
    照合(古い SELECT・二重 SELECT を拒否)※ファーム小改修
  - 片方が完走/異常/切断でもう片方だけ駐機した場合: 警告を出し、
    §0.1 の連動規則(セット開始・自動合流=両方停止)に従う。無限駐機の
    保険として P4 でタイムアウト(§1 の乖離)を実装する
- **D8 開始プロトコル(セット実行)**:
  1. 事前検査: 全装置が IDLE / id 照合済み / **手順の要求機能と転送方式の照合**
     (ジャイロを使う手順 × hidpad の装置なら開始前に止める)/ fw 版不一致は警告
  2. 転送: ハッシュ不一致の装置にのみ PUT+COMMIT(全装置完了まで開始しない)
  3. 開始: 固定順で RUN を連発(応答は軽い。開始ズレ数十ms級)
  4. **応答喪失時**: RUN は再送できない(非冪等)ため、STATUS で実際に走って
     いるかを確定してから次へ進む。「片方だけ開始」が確定したら §0.1 の
     連動規則に従い、走った側を「今の周で止める」
  - 巻き戻しはしない(STOP で装置は止まるがゲーム内の進行は戻せないため、
    「止めて知らせる」まで)
- **D9 管理系**: OTA/方式切替/config/較正/CLEAR_ERROR は `--device` 必須。
  セット実行中の装置への OTA/方式切替/config は拒否
- **D10 GUI サーバと CLI の仲裁**: GUI サーバ稼働中、CLI の装置操作は
  GUI サーバの HTTP API を経由(プロキシ)する。直結すると1秒ごとの収集と
  接続を奪い合い、間欠故障になるため(ファームの横取り仕様)

### 2b. 実行・監視画面の設計 = 案C「連結レーン方式」(2026-08-05 決定)

4案(A装置カード/Bセット表/C連結レーン/D動かし方切替)を4用途×21シナリオの
操作シミュレーションと2視点審査で比較し、C を採用(18+18/20。A=11+11、B=7+8、
D=17+18)。方向性確定、細部の指摘は実装中に受け付ける。比較に使ったモックは
作者手元の作業記録にあり、リポジトリには含めていない。

**構造**: 装置ごとの縦レーンを横に並べる(両装置が常に1画面内)。1台分の操作
(接続・手順×周回×開始位置・開始/停止/SELECT・状態・タイムライン)は各レーンで
完結し、ボタンは装置名入り(「◼ 1P を今の周で止める」)。レーン上部の
**「連結」**が2台をまとめる唯一の場所: 連結すると連結バーが現れ、
1回実行(1P+2P)/周回実行(1P+2P)/もう一回(同じ条件)/両方停止/自動合流と進む腕/
両方へ同時に選ぶ/「次の合流は自分で選ぶ(1回だけ)」が出る。連結しなければ
これらの語彙ごと画面から消える。**連結バーから開始=連動、レーンから開始=独立**
という §0.1 の規則を画面の形に写像する(モードや状態を覚えさせない)。
1台登録時はレーン1本が全幅になり、従来の6カード構成と見出し・配置が1対1。

> **2026-08-09 の変更**: 「連結バー」は**上部バー**に改めた。バーは2台以上なら
> 常にあり、**連結の語彙だけが出入りする**。連結していないときも残るのは
> 「2台にまたがるもの」= プリセットの保存と連結の入口。以前はバーごと消して
> いたため、連結を外すとプリセットに保存できなかった。原則は
> gui-principles.md §2「上部バーは2台にまたがることだけを置く」が正。

**案Dから移植する3点**: ①プリセット(=盤面のスナップショット保存: 連結・装置×手順×
周回×開始位置×合流の腕)の呼び出し時、連結バーに全容サマリ1行を常設
②相方待ち超過の判定は固定秒でなく「このプリセットのいつもの所要時間の実測+超過」
③通算周回の表示と「続きから再開(残りn周)」

**シミュレーションで確定した必須要求(案に依らず実装する)**:
- 選択待ちの三態を色分離: 青=相方待ち(自動で進む予定・経過秒)/緑=そろって
  進んだ直後/黄=相方が来ない(実測基準の超過)。**黄色を毎周の正常に使わない**。
  赤は装置異常専用
- ワンショット介入「次の合流は自分で選ぶ(1回だけ)」(チェックボックスの
  外し競争をさせない)
- 連結中の装置単独SELECTには「合流の対応がずれる」警告を添える
- 装置の**休止**(今日は使わない宣言。開始・連動・異常判定から除外し、
  赤表示しない)
- 開始ズレ・同時SELECTズレの**ms実測**を画面表示+ログ記録(装置内µsと命名分離)
- 反復テストの対象に「連結(ペア)」を追加(○×を手順版・実測ズレと紐づけ)
- F9=全部止める/F10=もう一回 のホットキー(受け付けをビープ音で返す。
  連結中のみ有効)
- 実行中に触れる欄(周回等)は「次の開始から効く」ことをその場に明記
- 全タブ共通: ヘッダに装置ごとの状態チップ(実行中/選択待ち/異常/未接続)
- 連動停止の発生時は理由+「続きから再開」+「片方だけ続ける」をその場に提示。
  復旧導線(探す/接続)はエラーが出ている場所に置く
- 実行中のプリセット呼び出しはガード(拒否または次回開始への予約)。
  休止レーンは畳んで残りを広げる

**実装順**: P2-1 サーバ土台(接続プール・並列収集・キャッシュ即答・装置系APIの
dev 必須化。既存1台UIを壊さず互換のまま)→ P2-2 画面の連結レーン化 →
P2-3 検査(uicheck)の書き換えと文書改訂。プリセットの保存・自動合流・ペア反復
テスト・ホットキーは P3 で連結バーに載せる。

### 2c. P3/P4 実装設計(2026-08-06 追記。D6〜D8 の実装形)

**部品配置**: 連結・セット実行・自動合流はサーバ(coupler.py)が持つ。
ブラウザを閉じても連動停止・自動合流が動き続けるため(収集と同じ理由)。
GUI は盤面の写像に徹する。

- **連結の保存**: `padcue.json` の
  `coupling: {on, auto_join, arm, oneshot_manual}`。
  対象は台帳の先頭2台(3台以上は対象外のまま)
- **実行の運転記録**: プロジェクト直下 `runstate.json`(実行時生成物・
  非追跡)。内容 = 連結実行の計画(装置×手順×周回×開始位置)、開始時刻、
  開始ズレms、人為停止の記録、プリセットごとの通算周回と合流待ち実測(直近20件)。
  サーバ再起動でも「この組は連結で開始した」が失われないように置く
- **D8 の実装**: /api/couple_run。事前検査(全員 IDLE・手順が変換可能・
  **ジャイロを使う手順×hidpad は拒否**(blob の復号で判定)・fw 版不一致は
  警告として返す)→ ハッシュ不一致の装置のみ転送 → 台帳順に RUN 連発、
  完了時刻差を開始ズレmsとして記録。RUN の応答喪失時は STATUS で確定し、
  「片方だけ開始」なら走った側を今の周で止めて報告
- **人為停止の判定**: /api/stop(GUI・CLI 経由)で止めた装置を運転記録に
  「人為停止」と記す。連動停止(異常起因)はこの印を付けない。§0.1 の
  「人為停止は連動しない・残側の自動合流はソロで自動進行」はこの印で決まる
- **連動停止の止め方**: 既定は「今の周で止める」。ただし**駐機中
  (AWAITING)の装置は即時停止**とする。駐機中は全ニュートラルで停止済み
  相当であり、区切り停止は SELECT が来ない限り永遠に完了しないため
- **同時 SELECT**: /api/select_both {arm}。両方 AWAITING のときだけ受け、
  各装置の await_gen を添えて送る(古い駐機への誤配を装置側でも拒否)。
  2台への送信完了時刻差を「選択ズレms」として記録
- **自動合流(P4)**: 収集キャッシュを監視する専用スレッド(0.5秒周期・
  装置への I/O は SELECT/STOP のときだけ)。対応付けは到達順(await_gen の
  進みを到達回数として数える)。両方駐機 → 設定の腕を同時 SELECT。
  oneshot_manual が立っていれば1回だけ自動を保留し、人の選択後に自動へ戻る
- **相方待ちの超過判定(実測基準)**: プリセットごとに直近の合流待ち時間を最大
  20件記録し、超過 = 待ち > max(中央値×3, 30秒)。実測が無い初回は 30秒
- **異常の定義**(§0.1 のとおり): 装置の異常報告(ERROR/ENGINE_FAULT)、
  または収集が約5秒失敗し続けた状態。連結実行中にどちらかで検出 →
  相方を連動停止し、理由と「続きから再開(残り周)」を提示
- **続きから再開**: 周回は周単位で不可分(区切り停止は周境界で止まる)
  ため、再開 = 残り周回数で先頭から開始。通算周回はプリセット単位で累積
- **PC 側の合成ログ**: セット開始・自動合流・同時選択・連動停止・超過警告
  は PC が logs.jsonl へ追記する(kind = PC_SET_START / PC_AUTO_JOIN /
  PC_SELECT_BOTH / PC_LINK_STOP / PC_WAIT_LATE。装置タグ付き)。装置内µs
  (LATE_EVENT 等)と混同しないよう ms は必ず「ズレ」と書く
- **プリセット**: `sets/<名前>.json`(ユーザー資産・非追跡)。
  `{schema:1, name, linked, auto_join, arm, devices:[{id, proc, loops, resume}]}`。
  保存キーは装置の個体ID(改名に耐える)。実行中の呼び出しは
  拒否(理由を出す)。盤面がプリセットとずれたら連結バーのプリセット名に *
- **ペア反復テスト**: 対象「連結(1P+2P)」= 連結1回実行を1試行として、
  ○×に手順ハッシュと開始ズレmsを添えて記録する
- **ホットキー**: F9 = 全部止める(即時)・F10 = もう一回。連結中のみ。
  受け付けは WebAudio の短いビープで返す(画面を見ずに打てるように)

## 3. 判断事項の決着(2026-08-04。全て §0.1 に反映済み)

- 片方異常時: **開始のされ方で決まる**(個別開始=続行/セット開始・自動合流=両方停止)
- 手動操作: 対象を選んで同時1台のみ
- ネットワーク: 同一 AP・同一セグメント・同一型番 → 探索を主経路に
