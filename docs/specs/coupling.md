# 2台同時運用の仕様

装置2台を1つの画面から扱い、待機分岐で進行をそろえるための仕様。
実装は `coupler.py` / `devicepool.py` / `registry.py` と、画面の上部バー。

D1〜D10 はコードがコメントから参照する契約なので、番号ごと動かさない。

## 1. 目的と前提

**Switch 2台+装置2台で、2人分の自動操作をする。**

- **開始の同時性は厳密でなくてよい**。「全装置へ転送 → 全転送完了 → 実行信号
  を続けて送る」方式(開始ズレ数十ms級、WiFi しだいで百ms強)
- ズレ対策は**手順の調整と待機分岐**で行う。そのため**2台へ同時に SELECT を
  送る仕組み**と、**両方が選択待ちに着いたら自動で選んで再開する「自動合流」**
  が要る
- 識別は**内部 = MAC、表示 = 利用者が付ける名前**(1P / 2P など)
- どの Switch につながっているかの自動識別は行わない。装置へのラベル貼りと、
  画面の「識別」ボタン(その装置だけに短い無害な入力を送り、本体の
  コントローラー画面で反応を見る)で足りる
- **手動操作は対象を選んで同時1台のみ**
- **2台は同一 AP・同一セグメント・同一型番**で運用する(探索を主経路にする。
  IP の手動登録は CLI にだけ残す)

### 片方が止まったときの扱い

**開始のされ方で決まる。**

| 開始のされ方                           | 片方が異常になったら                     |
|----------------------------------------|------------------------------------------|
| それぞれ個別に開始(自動合流なし)       | 相手は続行                               |
| 連結して同時開始、または自動合流を使用 | **両方止める**(既定は「今の周で止める」) |

自動合流なしでもタイミング調整だけで噛み合わせる運用があり得るため、
連動するかどうかは開始時の意思で決める。

ここでいう異常は、**装置自身の異常報告**か、**PC から約5秒見えない状態**。

**人為の停止は連動しない。** 連結中でも、人が片方の停止ボタンを押したなら
その装置だけ止まり、相手は続行する。さらに人が片方を止めたあと、残された側が
自動合流の待機分岐に着いた場合は、相手を待たず**そのまま単独で進む**
(相手の不在が人の意図によるものだから)。異常で相手が消えた場合はこの縮退を
せず、警告して上の表に従う。

## 2. 要件

| #  | 要件                                                            |
|----|-----------------------------------------------------------------|
| R1 | 1つの画面から N 台(当面2台)を登録・命名・見分け・個別操作できる |
| R2 | (装置×手順×周回)の組を一括転送 → 一括開始 → 一括/個別停止できる |
| R3 | 片方の異常・無応答が、もう片方の表示と操作を一切妨げない        |
| R4 | ログ・記録はどの装置のものか常に分かる                          |
| R5 | 待機分岐で「同時 SELECT」と「自動合流」ができる                 |
| R6 | 装置1台だけの利用がそのまま成立する                             |

## 3. 採用しない方式

| 方式                                   | 採らない理由                                                                                                                                     |
|----------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| 時計同期による実行中ずっとの噛み合わせ | 水晶差で約14分に1フレームずれる。ゲーム側のロード/マッチング時間が2台で揃わず、Switch 本体同士もずれるので、同期しても合わない                   |
| ARM+GO(UDP の一斉発火)                 | ARMED という新しい状態を状態機械に統合し、supervisor との整合と解除経路を用意する必要がある。開始ズレ数十ms で足りる用途に対して規模が見合わない |
| 1装置への2制御プロセス同時接続         | ファームウェアは後から来た接続を優先して奪うので、奪い合いになる                                                                                 |
| 2台同時の手動操作                      | 対象を選んで1台ずつ操作する仕様とする                                                                                                            |

## 4. 契約(D1〜D10)

- **D1 データモデルは N 台、画面は2台に最適化**。
  設定は `devices: [{id(MAC・保存キー), name(表示名), host, port}]`。
  **保存キーは常に id**。name はいつでも改名でき、ログやプリセットの参照は
  切れない。`{host, port}` だけの形式は初回読み込みで自動移行し
  (devices の1件目・name="1P")、移行前に `padcue.json` と `logs.jsonl` を
  自動バックアップする。移行後も `{host, port}` を併記保存する
- **D2 個体照合**。HELLO に id を載せ、mDNS 名を `pademu-<MAC下4桁>` にする。
  PC 側は接続を**「id 検証付きファクトリ」1箇所に集約**し(画面・CLI・探索の
  全経路)、接続確立時に HELLO の id と登録 id を照合、不一致は操作を拒む。
  **例外 = 受け入れモード**: 明示操作(`device add`)の間だけ、id を名乗らない
  装置に HELLO と OTA のみ許す。これが無いと「id が無いから拒否 → id を
  載せる OTA もできない」となって先へ進めない
- **D3 接続の契約**: **1装置 = 1接続 = 1装置 lock**。状態収集も操作
  (RUN/STOP/SELECT)も**同じ接続**を装置 lock の下で使う(ファームウェアは
  同時1接続・後着横取りなので、収集と操作を別接続にすると奪い合う)。
  lock の粒度は1コマンド(操作は収集サイクルの合間に必ず割り込める)。
  収集はバックグラウンドで並列に行い、`/api/state` はキャッシュで即答する。
  片方の無応答はその装置の「未接続」表示に留まる
- **D4 装置に触る API のみ dev(装置 id)必須**(run / stop / select /
  passthrough / status / logs / 識別 など)。手順・部品の編集系 API は装置と
  無関係なので dev を取らない
- **D5 ログ**: 回収時に**装置 id タグ**を付け、表示は name に解決する。
  `logs.jsonl` への書き込みは**単一ライタ**(専用 lock)。保持上限は
  装置数 × 5000 行。**回収の所有者は画面のサーバに一本化**する(装置側は
  読むと消えるため、CLI の logs はサーバ稼働中はそれ経由で読む)。
  装置間の時刻整列は要件外(`t_ms` は装置ローカル時計。合流の検証は
  ゲーム画面で行う)
- **D6 プリセット**: `sets/<名前>.json` = `{名前, [(装置id, 手順名, 周回数)…],
  設定}`
- **D7 合流(バリア)**:
  - 対象は「自動合流: ON」のときの待機分岐。対応付けは**到達順**(装置ごとに
    n 回目の到達同士を対にする。周回のたびに毎回停止する待機分岐の性質上、
    これが最も単純で予測できる)
  - 自動で選ぶ選択肢は設定に書く(既定 = 1番目)。人が画面を見て選ぶ分岐のために
    **「両方へ同時に送る」**も出す
  - 誤操作防止として、SELECT に**世代**(その装置の何回目の選択待ち(AWAITING)か)を付け、
    装置側で照合する(古い SELECT・二重 SELECT を拒む)
  - 片方が完走・異常・切断で、もう片方だけ選択待ちした場合は警告を出し、§1 の
    連動規則に従う。無限に選択待ちしないよう待機分岐にはタイムアウトを設ける
- **D8 開始プロトコル**:
  1. 事前検査 — 全装置が IDLE / id 照合済み / **手順の要求機能と転送方式の
     照合**(ジャイロを使う手順 × HID ゲームパッド方式の装置なら開始前に
     止める)/ ファーム版の不一致は警告
  2. 転送 — ハッシュ不一致の装置にだけ PUT + COMMIT(全装置の完了まで
     開始しない)
  3. 開始 — 固定順で RUN を続けて送る(応答は軽い。開始ズレ数十ms級)
  4. **応答喪失時** — RUN は再送できない(非冪等)ので、STATUS で実際に
     走っているかを確定してから次へ進む。「片方だけ開始」が確定したら §1 の
     連動規則に従い、走った側を「今の周で止める」
  - 巻き戻しはしない。STOP で装置は止まるがゲーム内の進行は戻せないので、
    「止めて知らせる」までとする
- **D9 管理系**: OTA / 方式切替 / config / 較正 / CLEAR_ERROR は `--device`
  必須。連結実行中の装置への OTA / 方式切替 / config は拒む
- **D10 画面のサーバと CLI の仲裁**: サーバ稼働中、CLI の装置操作はサーバの
  HTTP API を経由する。直結すると1秒ごとの収集と接続を奪い合い、間欠故障に
  なる(ファームウェアの横取り仕様のため)

## 5. 画面の構造

装置ごとの**縦レーン**を横に並べる(両装置が常に1画面に入る)。1台分の操作
(接続・手順×周回×開始位置・開始/停止/SELECT・状態・タイムライン)は各レーンで
完結し、ボタンは装置名入りにする(「◼ 1P を今の周で止める」)。
装置1台のときもレーン1本の同じ構造にする。

2台以上のときは**上部バー**が常にあり、**連結の操作だけが出入りする**。
連結すると、まとめて実行・両方停止・自動合流と進む選択肢・両方へ同時に送る・
「次の合流は自分で選ぶ(1回だけ)」が現れる。連結を外すとこれらはまとめて消える。

**連結バーから開始 = 連動、レーンから開始 = 独立**という §1 の規則を画面の形に
写す(モードや状態を覚えさせない)。連結していないときもバーが残るのは、
そこに置くものが「2台にまたがるもの」= プリセットの保存と連結の入口だから。
バーごと消すと、連結を外した状態でプリセットに保存できなくなる。
配置の原則は [design/gui-principles.md](../design/gui-principles.md) §2 が正本。

**選択待ちは三態を色で分ける**: 青 = 相手待ち(自動で進む予定・経過秒)/
緑 = そろって進んだ直後 / 黄 = 相手が来ない(実測基準の超過)。
**黄色を毎周の正常に使わない。** 赤は装置の異常専用。

## 6. 連結の実装

**連結・まとめて実行・自動合流はサーバ(`coupler.py`)が持つ。** ブラウザを
閉じても連動停止と自動合流が動き続ける必要があるため。画面は割り当てを写すことに
徹する。

- **連結の保存**: `padcue.json` の
  `coupling: {on, auto_join, arm, oneshot_manual}`。対象は台帳の先頭2台
- **実行の運転記録**: プロジェクト直下の `runstate.json`(実行時生成物・
  非追跡)。連結実行の計画(装置×手順×周回×開始位置)、開始時刻、開始ズレms、
  人為停止の記録、プリセットごとの通算周回と合流待ちの実測(直近20件)。
  サーバを再起動しても「この組は連結で開始した」が失われないように置く
- **D8 の実装**: `/api/couple_run`。事前検査(全員 IDLE・手順が変換可能・
  **ジャイロを使う手順 × HID ゲームパッド方式は拒否**(バイナリの復号で判定)・
  ファーム版の不一致は警告として返す)→ ハッシュ不一致の装置のみ転送 →
  台帳順に RUN を続けて送り、完了時刻差を開始ズレms として記録。RUN の応答が
  失われたときは STATUS で確定し、「片方だけ開始」なら走った側を今の周で
  止めて報告する
- **人為停止の判定**: `/api/stop` で止めた装置を運転記録に「人為停止」と記す。
  連動停止(異常起因)にはこの印を付けない。§1 の「人為停止は連動しない・
  残った側の自動合流は単独で進む」はこの印で決まる
- **連動停止の止め方**: 既定は「今の周で止める」。ただし**選択待ち中の装置は
  即時停止**とする。選択待ち中は全ニュートラルで停止済みに等しく、区切り停止は
  SELECT が来ない限り永遠に完了しないため
- **同時 SELECT**: `/api/select_both {arm}`。両方が選択待ち中のときだけ受け、
  各装置の `await_gen` を添えて送る(古い選択待ちへの誤配を装置側でも拒む)。
  2台への送信完了時刻差を「選択ズレms」として記録する
- **自動合流**: 収集キャッシュを監視する専用スレッド(0.5秒周期。装置への
  入出力は SELECT/STOP のときだけ)。対応付けは到達順(`await_gen` の進みを
  到達回数として数える)。両方が選択待ちしたら設定の選択肢を同時 SELECT する。
  `oneshot_manual` が立っていれば1回だけ自動を保留し、人が選んだあと自動へ戻る
- **相手待ちの超過判定**: プリセットごとに直近の合流待ち時間を最大20件記録し、
  超過 = 待ち > max(中央値×3, 30秒)。実測が無い初回は 30秒
- **続きから再開**: 周回は周単位で不可分(区切り停止は周境界で止まる)なので、
  再開は残り周回数で先頭から開始する。通算周回はプリセット単位で積む
- **PC 側の合成ログ**: まとめて開始・自動合流・同時選択・連動停止・超過警告は
  PC が `logs.jsonl` へ追記する(kind = `PC_SET_START` / `PC_AUTO_JOIN` /
  `PC_SELECT_BOTH` / `PC_LINK_STOP` / `PC_WAIT_LATE`。装置タグ付き)。
  装置内のµs(`LATE_EVENT` など)と混同しないよう、ms は必ず「ズレ」と書く
- **プリセット**: `sets/<名前>.json`(利用者の資産・非追跡)。
  `{schema:1, name, linked, auto_join, arm, devices:[{id, proc, loops, resume}]}`。
  保存キーは装置の個体 ID(改名に耐える)。実行中の呼び出しは理由を出して
  拒む。割り当てがプリセットとずれたら、上部バーのプリセット名に `*` を付ける
- **ホットキー**: F9 = 全部止める(即時)、F10 = まとめて周回実行。連結中のみ
  有効で、受け付けは短いビープで返す(画面を見ずに打てるように)

## 7. この仕様に含めていないもの

仕様の範囲だが、いまは実装していない。

- **装置の休止**(今日は使わない宣言。開始・連動・異常判定から外し、赤くしない)
- **ペア反復テスト**(連結1回実行を1試行として、○× に手順ハッシュと開始ズレms
  を添えて記録する)。成功率は「1回実行を何度か流して見比べる」で代用する
  ([runbook.md](../runbook.md) §5-5)
- **全タブ共通のヘッダに置く、装置ごとの状態チップ**。状態チップはレーンと
  装置パネルにあり、ヘッダにあるのは手動操作中の印だけ
- **通算周回の表示**。値(`total_laps`)はプリセット単位で記録しているが、
  画面には出していない
