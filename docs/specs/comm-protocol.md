# PC とマイコンの通信プロトコル

状態: **実装済み**。PC 側は pctool/padcue/proto.py、
装置側は firmware/main/app_ctrl.c。両実装の正本はこの文書。

## 設計原則

- 遅延不問・利用者1名・LAN 内限定(設計文書の許容条件)。HTTP/MQTT 等は使わず最小
  の自作パケット形式
- 実行中のタイミング経路に PC を関与させない(D2)。実行中に許されるのは RAM フラ
  グ操作(停止指示)と状態読み出しのみ
- 実行中のフラッシュ書き込み禁止(7.4)。転送データは RAM 受け、COMMIT は停止中の
  み

## トランスポート

| 経路                       | 用途                                                                                                                                     |
|----------------------------|------------------------------------------------------------------------------------------------------------------------------------------|
| TCP :5555(マイコン=サーバ) | コマンド/応答。パケットの形: `len u16 \| type u8 \| payload \| crc32`(**この「パケット」はゲームの1描画周期を指す「フレーム」とは別物**) |
| UDP :5557(マイコン=応答側) | 居場所の探索。PC が `PADEMU?` をブロードキャストし、装置が JSON で名乗る                                                                 |

**ログに専用の経路は無い**。実行中は装置内の RAM リングバッファに溜め、PC が
`LOGS`(0x08)で取りに行く(D2「手順データはマイコン側に保持し、マイコン単体で
実行する」/ A-4「記録すべきは異常のみ」)。
読み出すと装置側からは消えるので、PC は受け取った端から `logs.jsonl` へ書く。

探索の応答は `{"magic":"pademu","id":<MAC 12桁hex>,"fw":<版>,"port":5555}`
(`firmware/main/app_discover.c`)。装置は mDNS で `pademu-<MAC下4桁>.local` を
名乗る(固定名 `pademu.local` は2台目と衝突するので使わない)ので、**IP を
固定する設定は要らない**。

PC 側は **探索が先、名前解決は保険**の順で試す(`pctool/padcue/discover.py`)。
順序が逆だと壊れる: 名前解決で得た住所は個体IDを伴わないため、同じ装置の
「ID付きの応答」を隠してしまい、控えたIDとの照合が不一致と判定される。

**ペイロード形式**: `json_len u16 | JSON(UTF-8) | blob`。制御情報は JSON(タイミ
ング経路外のため拡張性・可読性を優先。MCU 側は cJSON)、手順データ等の大きなバイ
ト列は blob に載せる。応答の type は「要求 type | 0x80」、エラー応答は
0xFF(code, message)。参照実装: `pctool/padcue/proto.py`

## エラー応答

エラーは type `0xFF` で返す。ペイロードは `{"code": <下表>, "message": <日本語>}`。
**PC 側は message をそのまま利用者へ見せてよい**(装置が日本語で理由を書く)。
判定に使うのは code だけで、増えることはあっても意味は変えない。

| code                                                                                   | いつ返るか                                                    |
|----------------------------------------------------------------------------------------|---------------------------------------------------------------|
| `BUSY`                                                                                 | 実行中にできないこと(転送・確定・設定・OTA・方式切替)を求めた |
| `BAD_ARG`                                                                              | 引数が足りない・型が違う・範囲外(大きすぎる手順を含む)        |
| `BAD_STATE`                                                                            | その状態では受け付けない(OTA 中でないのに OTA の続き 等)      |
| `NOT_FOUND`                                                                            | 指定した手順が装置に無い                                      |
| `HASH_MISMATCH`                                                                        | 実機の手順が PC 側と違う(転送し直しが要る)                    |
| `STALE_SELECT`                                                                         | 前の駐機に宛てた古い選択(2台の自動合流での取り違え防止)       |
| `CRC`                                                                                  | パケットが壊れている                                          |
| `UNKNOWN_CMD`                                                                          | 未知のコマンド種別                                            |
| `STAGE_FAILED` `COMMIT_FAILED` `START_FAILED` `SELECT_FAILED` `NVS` `NVS_FAILED` `OTA` | 装置内部の失敗。message に ESP-IDF の理由が入る               |

PC 側が独自に付ける code もある(装置とは通信していない失敗)。
`DEVICE_MISMATCH` = 控えた個体IDと違う装置につながった(誤爆防止。
docs/specs/coupling.md D2)。

## デバイス状態機械(LED 表示と対応)

**正本は firmware-architecture.md §6**(AWAITING の遷移表・ERROR 解除を含む)。概
要: BOOT → WIFI_CONNECTING → IDLE ⇄ RUNNING(⇄ AWAITING)/ ERROR(ラッチ、
CLEAR_ERROR で解除)/ OTA

- プレイヤー番号(Switch からのサブコマンド 0x30)受信時は LED に反映(1P/2P 以降の
  判別)
- USB 切断・サスペンドを RUNNING 中に検出した場合: 中断+全ニュートラル+位置(周回・
  index)記録 → ERROR

## 設計上の取り決め

- **OTA の分割転送**: 4KB ごとに `action: data` で送る(begin / data / end の
  3段階)。レジュームは実装しない — 1MB 弱の転送が数秒で終わり、失敗しても
  A/B のもう一方が生きているので最初からやり直せば済む
- **手動操作(パススルー)の形式**: ストリームではなく、1回の PASSTHRU に
  全入力の状態を載せて毎秒30回送る。差分を積む方式(バックログ)は採らない
  — 取りこぼしても次の1回で正しい状態に戻るほうが、人が操作する用途では
  破綻しにくい
