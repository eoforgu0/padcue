# PC と装置の通信プロトコル

通信プロトコルはこの文書に定める。実装は、PC 側が pctool/padcue/proto.py、装置側が firmware/main/app_ctrl.c にある。ここに書いたことは、装置と模擬装置と PC のどれもが満たしている(pctool/tests/test_firmware_docs.py が、この文書と C のソースと proto.py を照合する)。

## 方針

- 伝達の遅延は問わず(requirements.md の許容条件)、使うのは組み立てた本人で、家庭内の LAN の中に限る(R24)。HTTP や MQTT は使わず、必要なだけの自前のパケットの形にする
- 実行中の送信の時刻に PC を関わらせない(P2)。実行中に受け付けるのは、HELLO、停止の要求と「区切りで停止」の予約の解除、読み出し、操作権の取得と解放、LED の点滅、選択待ちの間の選択だけである。どれも送信の時刻の計算には入らない。選択は、タイマーが停止している選択待ちを終わらせるだけである
- 実行中はフラッシュへ書き込まない(P3)。転送した手順データは RAM で受け、保存する COMMIT は停止しているときだけ受け付ける

## トランスポート

| 経路 | 用途 |
|---|---|
| TCP :5555 | コマンドと応答。装置が待ち受ける |
| UDP :5557 | 装置の探索。装置が返す |

TCP のパケットの形は `len u16 | type u8 | payload | crc32` である(UDP の探索はこの形を使わない。下の段落)。len は type と payload を合わせた長さ(=本体部)で、crc32 は含まない。crc32 は本体部に対する CRC-32(zlib の crc32 と同じもの)で、len と crc32 自身は含めない。2 バイト以上の整数はどれもリトルエンディアンで並べる。payload は `json_len u16 | JSON(UTF-8) | blob` で、制御の情報は JSON、手順のデータのような大きなバイト列は blob に格納する。タイミングの経路の外なので、読みやすさと拡張しやすさを優先している(装置側は cJSON)。応答の type は「要求の type に 0x80 を足したもの」、エラー応答は 0xFF である。

本体部の上限は 8192 バイトである。これは装置のパケットバッファーの大きさで、内蔵 RAM の予算から決まっている。PC 側も同じ値を使い(proto.py の MAX_BODY)、送る前に拒否する。装置は、上限を超えた長さを示すパケットに TOO_LARGE を、CRC が合わないパケットに CRC を返してから接続を切る(どこからが次のパケットか分からなくなる)。大きな転送(手順の PUT とファームウェアの OTA)は 4096 バイトずつに分けて送るので、この上限には当たらない。

探索では、PC が UDP 5557 へ `PADEMU?`(7 バイトの ASCII)をブロードキャストで送り、装置が送り元へ応答を返す。応答は `{"magic":"pademu","id":<MAC 12桁hex>,"fw":<バージョン>,"port":5555}` である(firmware/main/app_discover.c)。装置は mDNS で `pademu-<MAC下4桁>.local` を公開する(固定の名前 `pademu.local` は 2 台目と衝突するので使わない)ので、IP を固定する設定は必要ない。

コマンドは、登録した接続先につながらないとき、探索を先に試し、見つからなければ名前解決(`pademu-<装置 ID の下 4 桁>.local`)で追う(pctool/padcue/cli.py)。探索は 1 回ですべての装置の応答が集まり、名前解決はブロードキャストが届かないネットワークのための補助である。どちらで見つけた接続先も、つないだ後に HELLO の装置 ID を照合する。

ログに専用の経路はない。実行中は装置内の RAM のリングバッファーに溜め、PC が LOGS で読み出す。装置は PC とつながっていなくても実行を続け(P2)、記録するのは異常と主なイベントだけなので(P19)、送信する経路を持たなくても足りる。

LOGS は記録を返すだけで、削除しない。削除するのは、PC が次の LOGS で「ここまで受け取った」と知らせたときである。返した時点で削除すると、PC が応答を受け取る前に接続が切れたときに、その記録がどこにも残らない。記録が最も必要なのは、無線が不安定なときである。

- 装置は起動のたびに 32 ビットの乱数 `boot` を決め、記録に起動からの通し番号を付ける
- 応答は `boot`、返した最初の記録の番号 `from`、記録の並び `entries` である。1 回に含まれるのは 48 件までで、番号は `from` から 1 ずつ続く
- PC は受け取った記録を `logs.jsonl` へ書いてから、次の LOGS に、受け取った応答の `boot` と `ack`(`from` に受け取った件数を足した値)を含める。装置は、`boot` が今の起動と同じときだけ、番号が `ack` より前の記録を削除する。違う `boot`(装置が起動し直した)の `ack` は見ない。前の起動の番号で、今の起動の記録を削除しないためである
- PC は entries が空になるまで続けて読む。最後の LOGS が、受け取った分を削除する。1 回の読み出しで送る LOGS は 16 回までとし、読む間に記録が増え続けても読み出しが終わるようにする。残りは次の読み出しの最初の LOGS から読み、最後の `ack` もその LOGS で送る。padcue を起動した直後は `boot` と `ack` を省き、残っている記録を先頭から読む

## コマンド一覧

要求が持つ欄と、その要求に操作権が必要か、実行中でも受け付けるかを並べる。欄を持たないものは「なし」である。PUT と OTA は、JSON のほかに blob でデータを送る。欄はどれも必須で、欠けていれば装置は BAD_ARG で拒否する。例外は 5 つある。HELLO の client_id は、識別子を送らない接続が省く。STOP_AT_MARK の mask は、release が真のときは見ない。OTA の size は、action が begin のときだけ使う。PASSTHRU の buttons から az までは、enable が真のときだけ使う。LOGS の boot と ack は、まだ記録を受け取っていないときに省く。種別は、パケットの type に入れる値である。

| コマンド | 要求の欄 | 操作権 | 実行中 | 種別 |
|---|---|---|---|---|
| HELLO | client_id | 必要ない | 可 | 0x01 |
| PUT | offset, total | 必要 | 不可 | 0x02 |
| COMMIT | id | 必要 | 不可 | 0x03 |
| LIST | なし | 必要ない | 可 | 0x04 |
| DELETE | id | 必要 | 不可 | 0x0E |
| RUN | id | 必要 | 不可 | 0x05 |
| SELECT | arm, gen | 必要 | 選択待ちだけ | 0x0A |
| STOP | なし | 必要ない | 可 | 0x06 |
| STOP_AT_MARK | mask, release | 解除だけ必要 | 可 | 0x0F |
| ACQUIRE | force | 必要ない | 可 | 0x10 |
| RELEASE | なし | 必要ない | 可 | 0x11 |
| STATUS | なし | 必要ない | 可 | 0x07 |
| LOGS | boot, ack | 必要ない | 可 | 0x08 |
| CONFIG | key, value | 必要 | 不可 | 0x09 |
| OTA | action, size | 必要 | 不可 | 0x0C |
| PASSTHRU | enable, buttons, lx..az | 必要 | 不可 | 0x0D |
| CLEAR_ERROR | なし | 必要 | 異常だけ | 0x0B |
| IDENTIFY | なし | 必要ない | 可 | 0x12 |
| USB_RECONNECT | hold_ms | 必要 | 不可 | 0x13 |

「不可」は、実行中(実行と選択待ち)には BUSY で拒否するという意味である。RUN、COMMIT、DELETE、CONFIG、USB_RECONNECT と、OTA の begin は、待機中(IDLE)にだけ受け付け、異常停止と更新の間も BUSY で拒否する。PASSTHRU は、異常停止と更新の間は BAD_STATE で拒否する。

**HELLO** は、送り手が自分の識別子を送る要求である。要求の client_id は送り手の識別子で、これを送った接続だけが操作権を取れる。応答の欄は次のとおりである。PC は接続のたびに `id` を登録情報の装置 ID と照合し、IP の入れ替わりによる混同を防ぐ。

| 欄 | 型 | 意味 |
|---|---|---|
| `magic` | 文字列 | 常に `pademu`。相手が padcue の装置かを判別する |
| `id` | 文字列 | 装置 ID(Wi-Fi の MAC を 12 桁の 16 進で表したもの) |
| `fw` | 文字列 | ファームウェアのバージョン |
| `schema` | 整数 | 受け付ける手順データの形式のバージョン(binary-format.md の schema) |
| `binterval` | 整数 | USB で宣言している問い合わせの間隔(ミリ秒) |
| `partition` | 文字列 | 稼働しているパーティション(`ota_0` か `ota_1`) |
| `reset_reason` | 文字列 | 前回のリセットの理由 |
| `crash` | 文字列 | 最後に異常終了したときの要約(下の段落) |
| `rolled_back` | 真偽 | 更新したファームウェアが確定しないまま再起動し、前のファームウェアへ戻ったか(OTA) |
| `state` | 文字列 | 装置の状態(STATUS の `state` と同じ) |
| `frame_period_ns` | 整数 | フレーム周期(ナノ秒) |
| `breadcrumb` | 整数 | 到達段階。Switch との初期化がどこまで進んだか(STATUS と同じ) |
| `imu_enabled` | 真偽 | 本体がサブコマンド 0x40 で IMU を有効にしたか。ジャイロが動かないときの切り分けに使う |
| `usb_mounted` | 真偽 | Switch と USB でつながっているか(STATUS と同じ) |

`crash` は、装置に異常終了の記録が残っているときだけ中身が入る(そうでなければ空文字)。異常終了したタスクの名前、例外の種類とアドレス、異常終了したアドレス、そこへ至る呼び出しの列である。いつ異常終了したかは示さない。

記録は削除しないので、無線で更新して再起動した後でも、その前に異常終了した場所を読める。そのため、要約は以前の起動のものでありうる。直前の再起動が異常終了によるものかは `reset_reason` で分かる。PANIC、INT_WDT、TASK_WDT のときは、装置は異常終了した場所を記録してから再起動しているので、要約はその直前の異常終了である。

装置は普通に動いている間 USB をコントローラーとして使うので、シリアルのログが出ない。シリアルケーブルをつながずに異常終了した場所を知る手段はこれだけなので、装置は起動のたびにフラッシュの記録を読み、要約を持っておく。

アドレスは ELF と addr2line で行番号に戻せる。要約に入っている `elf` は異常終了したファームウェアの指紋である。アドレスを戻すときは同じソースからビルドした ELF を使うこと。別のビルドの ELF で読むと、それらしく見える別の場所を指してしまう。

なお指紋は ELF ファイルそのものの SHA-256 で、ELF にはビルドしたときのパスが入る。同じソースでも別の場所でビルドし直すと指紋は変わるので、一致しないことが即「別物」を意味するわけではない。確認するなら、記録のアドレスがビルドし直した ELF の関数の境界と合っているかを見る。

**PUT** は手順のデータを RAM へ分けて送る。すべて揃うと装置が id(内容の SHA-256 の先頭 16 バイト = 32 桁の 16 進)を返し、PC は自分で計算した id と照合する。名前は送らない。手順は内容そのもので決まる id で参照する。

**COMMIT** は RAM の内容を `<id>.bin` としてフラッシュへ確定する。確定の前に、いま RAM にある内容の id が要求の id と一致するかを見る。同じ id が既にあれば内容の一致も確認する(混同の防止)。一致しなければ、置いてあるファイルの中身の id を計算し直し、合わなければ書き直し、合えば拒否する。確定は一時の名前に書いてから `<id>.bin` へ名前を付け替えるので、書いている途中で電源が切れても、作りかけのファイルが手順の名前で残らない。LIST は保存済みの手順(id と大きさ)を返す。名前は装置になく、id から名前へ戻すのは PC 側の役割である。DELETE は `<id>.bin` を削除する。ない id を削除しても成功にするので、片付けの途中で既に消えていても失敗しない。ほかの理由で削除できなかったときは DELETE_FAILED を返す。

**RUN** は id を指定して実行する。実行するのは COMMIT で保存した手順だけで、PUT で受け取って COMMIT していない中身は実行できない。id が内容そのものを指すので、別のハッシュの照合は必要ない。周回数は手順の SETCNT に入っており、開始位置は変換器が続きの手順に展開するので、通信では渡さない。選択肢の飛び先も手順の AWAIT レコードに入っている。

RUN と DELETE は、id の形(32 桁の 16 進の小文字)が違えば BAD_ARG で拒否する。形が合っていて装置になければ、RUN は NOT_FOUND を返す。

Switch とつながっていない(USB が未接続)とき、本体がスリープしている(USB がサスペンドしている)とき、RUN は BAD_STATE で拒否する。入力が本体に送られないまま、何もしなかった実行が完了として残らないようにするためである。Switch 2 はスリープしても USB をサスペンドしないので、この拒否は働かない。実行の途中で接続が切れたときは、停止して異常にする(「装置の状態と LED」)。異常停止の間の RUN は BUSY で拒否するので、先に CLEAR_ERROR で異常を解除する(操作画面のサーバーは、開始の前に解除を送る)。

**SELECT** は、選択待ちで止まっているときに進む選択肢を選ぶ。gen は STATUS の await_gen(選択待ちの通し番号)で、必須である。装置が照合し、別の選択待ちに宛てた古い選択を STALE_SELECT で拒否する。gen がなければ BAD_ARG で拒否する。

**STOP** はすぐに全入力を離し、実行を捨てる。何度送っても結果は同じである。エンジンが停止しているのに状態機械が RUNNING か AWAITING に残っているときも、待機へ戻す。「区切りで停止」の予約も消える。

**STOP_AT_MARK** は「区切りで停止」の予約と解除である。mask は区切りのマークの種類(binary-format.md)の論理和で、その種類のマークが付いたレコードの予定時刻に、そのレコードを出さずに全入力を離して待機へ移る。押している入力を予定時刻より早く離すことはない。「区切りで停止」は 3 種類すべて、完了したときの連動の停止は周の境だけを指定する。

予約は上書きで、後から受け取った mask がそのまま予約になる。release が真なら予約を消す。このとき PC は mask に 0 を送る。予約は誰でも送れるが、解除には操作権が必要である(「操作権」)。

mask が選択待ちのマークを含むときは、選択待ちの間に受け取ったらその場で停止し、予約の後に選択待ちに入ったときも待たずにそこで停止する。押した時刻と待ちに入った時刻の前後で結果は変わらない。含まないとき(周の境だけの予約など)は、待ちを続け、待ちが終わった後の対象の区切りで停止する。実行していないときの予約と解除は、受け付けて成功にするが何も起きない(STATUS の stop_at_mark は 0 のままである)。

**STATUS** は装置の今の状態を返す。欄は次の節にある。

**LOGS** は RAM に溜めた記録を返す(返し方と削除の仕方は「トランスポート」の節)。各エントリは `t_ms, kind, a, b, c` である。

| kind | a | b | c |
|---|---|---|---|
| RUN_START | 0(空き) | 手順 id の先頭 64 ビットの上位 | 手順 id の先頭 64 ビットの下位 |
| RUN_DONE、RUN_ABORT | 経過フレーム | 遅れの回数 | 最後に通った区切りのレコード番号(区切りを一度も通っていなければ 4294967295) |
| ENGINE_FAULT | レコードの番号 | 遅れの回数 | 最後に通った区切り |
| AWAIT_TIMEOUT | 待ったフレーム | on_timeout | |
| HOST_INFO | ペアリング(サブコマンド 0x01)の引数の先頭 4 バイト | 続きの 4 バイト | |
| STATE | 前の状態 | 次の状態 | |

- RUN_START は、ログの枠が 64 ビットなので、id の全 128 ビットではなく先頭の 64 ビットを格納する。PC はこの接頭辞を、送った手順のコピーの id と照合して名前に戻す。コピーが数千件あっても、64 ビットの接頭辞が衝突する確率は無視できる
- 装置は周回を数えないので、何周したかは PC がレコード番号と変換の対応表から出す
- HOST_INFO の a と b は、合わせて引数の先頭 8 バイトである。PC はこのうち 2 から 7 バイト目(= 本体の BT MAC 6 バイト)を本体の識別子として使う(先頭のフェーズ番号と末尾のフェーズ依存のバイトは、同じ本体でも変わる)
- STATE の値は、「装置の状態と LED」の節が並べる 7 つの状態を BOOT=0 から順に数えた番号である

**CONFIG** は frame_period_ns などの設定で、NVS に保存する。受け付ける値は、frame_period_ns が 1000 から 100000000 の整数、usb_binterval が 1 から 16 の整数、wifi_ssid が 1 から 32 バイト、wifi_pass が空か、8 から 63 バイトか、16 進数 64 桁である。パスワードの範囲は WPA の決まりで、空はパスワードのない Wi-Fi を表す。範囲の外の値は BAD_ARG で拒否し、保存しない。

usb_binterval は USB で宣言する問い合わせの間隔(ミリ秒。既定は 1)である。USB のディスクリプターは起動のときに作るので、次の起動から使う。配布するファームウェアは 1 種類なので、ビルドの設定にはしない。

wifi_ssid と wifi_pass も次の起動から使う。装置は両方が保存されているときだけつなぐ(パスワードのない Wi-Fi は、空の wifi_pass を保存して表す)。保存した値は、起動のときに一度つながるまで新しい値として扱い、つながらなければ装置は Wi-Fi の設定待ちで起動する(firmware-architecture.md §6)。配布するファームウェアは 1 種類なので、Wi-Fi の値はビルドに入れない。

**OTA** はファームウェアの更新で、検証してから再起動し、次の HELLO でロールバックの有無を報告する。新しいファームウェアは、最初の起動で 1 分以内に Wi-Fi につながらなければ確定せずに再起動し、前のファームウェアへ戻る。つながらないバージョンを確定すると、次の OTA も PC からの操作もできなくなるからである(診断モードで起動したときは除く。firmware-architecture.md §6)。

**CLEAR_ERROR** は異常のラッチを解除して待機へ戻す。記録を回収する前に自動では解除しない。

**PASSTHRU** は手動操作の中継である。PC 側の入力の状態を、そのままコントローラーの出力にする。欄は enable、buttons(u32)、スティックの lx、ly、rx、ry(-2048 から 2047)、ジャイロの gx、gy、gz と加速度の ax、ay、az(それぞれ i16)である。手動操作を始めるときと続けるときは、すべての欄を送る。終えるとき(enable が偽)は、入力を離した静止の姿勢に戻すので、ほかの欄は見ない。異常と更新の間も拒否する。RUN で実行を始めたときと、物理ボタンを長押ししたときも、手動操作は終わる。実行を始めたときに残すと、実行が終わった後(異常で停止した後も)に、実行の前の手動操作の入力がまた流れる。

**IDENTIFY** は LED を 5 秒間、白く速く点滅させる。0.15 秒ごとに点灯と消灯をくり返す。机に並べた装置のどれが、画面のどの装置かを判別するためのものである。LED の表示だけを変え、状態と入力は変えないので、操作権は不要で、実行中、選択待ち、異常、更新の間も受け付ける。続けて受けたら、その時点から 5 秒にする。5 秒たつと、いまの状態の表示に戻る。

**USB_RECONNECT** は USB をいったん切断し、hold_ms ミリ秒後に再接続する。Switch に、装置を挿し直したときと同じように認識し直させるためのものである。hold_ms は 100 から 10000 の整数である。切断の前に、Switch とのやり取りの状態(到達段階、Switch への登録、本体の識別子)を最初からにする。切断してから Switch が設定し直すまで、STATUS の usb_mounted は偽になる。Switch が認識し直さなければ偽のままなので、再接続で認識し直したかは usb_mounted と breadcrumb で分かる。記録には、挿し直したときと同じく USB_UMOUNT と USB_MOUNT が残る。切断すると入力が途切れるので、待機中にだけ受け付ける。再接続の前(hold_ms の間)にもう一度受けたときと、USB を始めていない診断モードでは、BAD_STATE で拒否する。

## 操作権

装置は操作権を 1 つ持つ。中身は、所有者の識別子と最後に通信した時刻である。操作権が必要なのは、装置を動かす要求(RUN、SELECT、PASSTHRU)、装置に入っているものを変える要求(PUT、COMMIT、DELETE)、装置の設定と中身を変える要求(CONFIG、OTA)、USB を再接続する要求(USB_RECONNECT)、状態を変える要求(CLEAR_ERROR)である。必要ないのは、停止の要求(STOP と、STOP_AT_MARK の予約)と読み出し(HELLO、LIST、STATUS、LOGS)、操作権そのものの操作(ACQUIRE、RELEASE)、それに LED の表示だけを変える要求(IDENTIFY)である。この分け方によって、停止することと状態を見ることは、どの接続からでもいつでもできる。STOP_AT_MARK の解除(release が真)は、停止しないようにする要求なので必要である。所有者でない接続が解除できると、所有者が停止させたかった区切りを越えて実行が続く。

識別子は、padcue を置いたフォルダーごとに最初に作る乱数である。同じフォルダーの操作画面、コマンド、テストのツールは同じ値を読むので、互いに拒否されない。別のフォルダーに置いた padcue は別の値になるので拒否される。作る側は 32 桁の 16 進にする。装置は形だけを見て、64 文字までの英数字と `-` と `_` を受け取る。

HELLO で識別子を伝えると、装置はその接続を所有者に結び付ける。ACQUIRE は操作権を取る要求で、force が真ならほかの所有者から取り上げる。取り上げても実行は続く。RELEASE は解放で、所有者でない接続が送っても成功にする。識別子を送らなかった接続は操作権を取れず、ACQUIRE を NOT_OWNER で拒否される。いまの所有者と同じ識別子からの ACQUIRE は、force が偽でも通る。

生存の確認には、その接続で送られた任意のパケットを使う。無通信が 30 秒続くと操作権は失効する。所有者の接続が HELLO で別の識別子を送り直したときと、識別子を付けずに送り直したときは、その接続の通信を生存の確認に数えなくなる。PC がスリープから戻ったときやサーバーを起動し直したときは、同じ識別子で取得し直す。これが通常の流れで、force は必要ない。失効した後も接続は無通信の 180 秒まで残り、その間に来た要求は、操作権の必要ないものは受け付け、必要なものは NOT_OWNER で拒否する。サーバーは拒否されたら取得し直して送り直す。

装置は制御の接続を 4 本まで同時に受ける。同時につなぐ相手として、操作画面のサーバー、コマンド、テストのツール、別の PC の 4 つまでを見込んでいる。受信のバッファーは接続ごとに持ち、送信は 1 本を順番に使う。応答は 1 つずつ返すので、送信を分け合っても順番待ちにならない。5 本目は、受け取ってすぐ閉じる。エラー応答は返さず、相手はつないだ直後に切られたことで分かる。既にある 4 本はそのまま動き続ける。

相手が消えた接続(PC の電源が切れた、PC の回線が切れた)は、TCP の keepalive で約 25 秒で閉じる(firmware-architecture.md §2)。無通信の 180 秒は、接続は保たれているが相手が何も送らないときに、その接続を残す上限であり、消えた相手の接続が 4 本の枠を 180 秒まで占めることはない。

応答を読まない接続も閉じる。装置は応答 1 つを送り終わるまで 1 秒待ち、相手が読まなくなってから閉じるまでは最長で約 2 秒かかる。すべての接続を 1 本のタスクで担当するので、送り終わるのを待つ間は、ほかの接続の停止も受けられないためである。

LIST が返す手順は 64 件までである。超えたぶんは含めず、`truncated` を真にして知らせる。RUN と DELETE は id で指すので、含まれなかった手順も id が分かれば実行も削除もできる。ただし LIST からはその id を知る手段がないので、黙って短い一覧を返すと、装置に残っている手順に気づけない。64 件の根拠は、一覧の応答が 1 件あたり約 55 バイトで、64 件でも約 3500 バイトと、本体部の上限 8192 バイトに収まることである。

更新は始めた接続の、手動操作は最後に入力を送った接続のものである。別の接続が切れても中断しない。その接続が切れたときは、更新は中断し、手動操作は解除する。手動操作を解除しないと、押しっぱなしの入力が装置に残る。

物理ボタンは、長押しが停止と、操作権と手動操作の解除、短押しが「区切りで停止」である。長押しで手動操作も解除するのは、手動操作の入力を送っていた PC が消えたとき(ノート PC のふたを閉じたときなど)に、装置が最後の入力を送り続けるからである。

## STATUS の欄

| 欄 | 型 | 意味 |
|---|---|---|
| `state` | 文字列 | 装置の状態(7 値) |
| `running` | 真偽 | 実行しているか |
| `awaiting` | 真偽 | 選択待ちで止まっているか |
| `await_arms` | 整数 | いまの選択待ちの選択肢の数 |
| `await_gen` | 整数 | 起動からの選択待ちの通し番号。1 から増え、実行をまたいでも戻さない。SELECT では、この値をそのまま送る |
| `boot` | 整数 | 起動の印(LOGS の `boot` と同じ値)。起動ごとに変わる |
| `run_gen` | 整数 | 起動からの実行の通し番号。RUN で実行を始めるたびに 1 進み(始める途中で失敗した RUN でも進むことがある)、まだ実行していなければ 0 である。停止した後も次の RUN まで同じ値を返す。PC は `boot` と組で実行を見分ける(経過フレーム数と手順の id では、同じ手順をすぐ始め直したことを見分けられない) |
| `event_index` | 整数 | いま指しているレコードの番号 |
| `frames_elapsed` | 整数 | 開始からの経過フレーム。長さのある選択肢を通ると `total_frames` を越える(`total_frames` は選択肢の長さを数えない) |
| `total_frames` | 整数 | 手順の総フレーム(0 = 総量なし) |
| `proc` | 文字列 | いま RAM にある手順の id |
| `manual` | 真偽 | 手動操作の中か |
| `last_mark` | オブジェクト | 最後に通った区切り |
| `stop_reason` | 文字列 | 停止した理由 |
| `engine_err` | 整数 | 手順データの異常の理由 |
| `stop_at_mark` | 整数 | 「区切りで停止」の予約 |
| `stopped_mask` | 整数 | 停止させた「区切りで停止」の予約 |
| `button_after_stop` | 文字列 | 実行していない間に押された装置のボタン |
| `owner` | オブジェクト | 操作権の所有者 |

`last_mark` は最後に通った区切りである。`index` がレコードの番号、`frame` がその区切りを通った時点の経過フレーム数(`frames_elapsed` と同じ数え方)、`counters` がその時点の各カウンターの値で、`counters[i]` がカウンター番号 i の値である。PC は `frames_elapsed` との差から、区切りを通ってからの経過を出し、図の上の現在位置に使う。長さは、その実行で SETCNT を一度でも通ったカウンター番号の最大に 1 を足した数で、まだ通っていない番号の値は 0 である。PC は、変換の対応表が複製ごとに持つ「どのカウンターを見るか」と照合して本来の回番号を出す。区切りを一度も通っていなければ null である。RUN で消え、実行が終わった後も次の RUN まで残る。

装置は、マークの付いた STATE か AWAIT の予定時刻にこの位置を更新する。出して続けるときも、出さずに停止するときも同じである。その瞬間はエンジンが停止していて先読みがないので、割り込みの先読みの影響を受けない。カウンターの値を含めるのはこの区切りの時点のものだけで、いま動いている値は含めない。

`stop_reason` は停止した理由である。`finished`(完了)、`stopped`(STOP を受けた)、`at_mark`(「区切りで停止」の予約で停止した)、`button`(物理ボタンの長押し)、`error`(異常)の 5 つで、実行している間と、電源を入れてから一度も実行していない間は空文字である。RUN で空文字に戻る。物理ボタンの短押しは予約なので、それで停止したときの理由は `at_mark` である。

`engine_err` は、手順データの異常で停止したときの理由の番号(pademu_core.h の pademu_err_t)で、異常がなければ 0 である。`stop_reason` と同じく RUN で 0 に戻る。始められなかった RUN では、`last_mark`、`stop_reason`、`engine_err`、`stopped_mask`、`button_after_stop` は変わらない。RUN が 0 に戻す計測値(`late_*`、`deliver_*` と、`dropped_replies` から `replies_sent` までの送信の計測値)も、始められなかった RUN では戻さない。

`stop_at_mark` は「区切りで停止」の予約で、真偽ではなく mask をそのまま返す(0 = 予約なし)。予約は、その予約で停止したとき、STOP を受けたとき、実行が終わったとき、次の RUN のときに消える。画面の押された状態と、タイムラインに出す停止の目印は、この値から描く。正式な値を持つのは装置で、画面は持たない。

`stopped_mask` は、「区切りで停止」の予約で停止したときの、停止させた予約の mask である。予約(`stop_at_mark`)は停止すると消えるので、どの予約で停止したかはこちらで見る。PC は、完了の連動停止の予約(周の境だけ)で停止したのか、人が重ねた予約(装置の上面のボタンの短押しは 3 種すべて)で停止したのかを、これで区別する。どちらも同じ周の境で停止することがあり、停止した区切りでは区別できない。予約のほかの止まり方のときと、実行している間は 0 である。`stop_reason` と同じく RUN で 0 に戻る。

`button_after_stop` は、実行していない間に押された装置の上面のボタンで、`short`(短押し)か `long`(長押し)、押されていなければ空文字である。両方押されたら `long` を返す。実行していない間は停止させる実行がないので、ボタンの停止と「区切りで停止」の働きは何もしない(長押しによる操作権と手動操作の解除は行う)。ただし、周回の終え方のために予約で停止し、ほかの装置を待つ間は、PC から見ると実行の途中である。PC は、その間に人がボタンで停止させたことをこれで知る。実行している間に押されたボタンは停止か「区切りで停止」の予約になるので、ここには残らない。`stop_reason` と同じく RUN で空文字に戻る。

`owner` は操作権の所有者で、`id` が識別子、`idle_ms` が最後の通信からの経過ミリ秒である。所有者がいなければ null である。所有者でない接続にも同じものを返す。画面が「操作権なし」を出すのに必要だからである。

装置の様子を測った値も返す。`usb_mounted`、`usb_suspended`、`breadcrumb`、`imu_enabled`、`pair_reqs`、`pair_step`、`input_mode`、`late_events`、`max_late_us`、`deliver_late`、`deliver_max_us`、`dropped_replies`、`failed_replies`、`dropped_inputs`、`bad_reports`、`ep_busy`、`inputs_sent`、`replies_sent`、`log_dropped`、`free_heap` である。遅れの計測が 2 種類あるのは、割り込みが定刻に入ったか(`late_*`)と、実際に USB へ渡すまで遅れなかったか(`deliver_*`)が別物だからで、両方そのまま出す。`free_heap` は空きヒープで、手順のバッファーの大きさを決める目安にする。

## エラー応答

エラーは type `0xFF` で返す。ペイロードは `{"code": <下表>, "message": <日本語>}`。PC 側は message をそのまま利用者へ見せてよい(装置が日本語で理由を書く)。判定には code だけを使う。

| code | いつ返るか |
|---|---|
| `BUSY` | 実行中にできないことを求めたか、待機中にだけ受け付ける要求を待機中でないときに求めた |
| `BAD_ARG` | 引数が足りない・型が違う・範囲外(大きすぎる手順を含む) |
| `BAD_STATE` | その状態では受け付けない(選択待ちでないときの SELECT、異常停止でないときの解除など) |
| `NOT_FOUND` | 指定した手順が装置にない |
| `STALE_SELECT` | 前の選択待ちに宛てた古い選択。次の選択待ちを、その選択で進めないために拒否する |
| `NOT_OWNER` | 操作権が必要な要求を、所有者でない接続が送った |
| `TOO_LARGE` | 本体部が上限を超えた(このあと接続を切る) |
| `CRC` | パケットが壊れている(このあと接続を切る) |
| `UNKNOWN_CMD` | 未知のコマンド種別 |

装置の中の失敗は `STAGE_FAILED`、`COMMIT_FAILED`、`DELETE_FAILED`、`START_FAILED`、`SELECT_FAILED`、`NVS`、`OTA` で返る。message はほかのエラーと同じく利用者に見せる文で、ESP-IDF の理由は装置の記録に残す。`OTA` は、更新の途中の失敗のほか、更新を始めていないのに続きを送ったときにも返る。

PC 側が付ける code もある(装置が返したものではない)。`NOT_PADEMU` は、つないだ相手が pademu として応答しなかった。`UNASSIGNED` は、登録情報のその名前に装置 ID が割り当てられていない。`DEVICE_MISMATCH` は、登録した装置 ID と違う装置につながった(誤操作の防止。coupling.md D2)。`ID_MISMATCH` は、転送した手順について装置が返した id が、PC が計算した id と違った。

## 装置の状態と LED

状態の遷移は firmware-architecture.md §6 が定める(AWAITING からの移り先と、ERROR の解除を含む)。状態は BOOT、WIFI_CONNECTING、IDLE、RUNNING、AWAITING、ERROR、OTA の 7 つで、STATUS の `state` に出る。ERROR は CLEAR_ERROR を受けるまで抜けない。

- LED は状態で決まる。例外は IDENTIFY を受けてからの 5 秒で、白く速く点滅する。プレイヤー番号(Switch からのサブコマンド 0x30)は、シリアルのログに出すだけで、装置の記録(LOGS)にも表示にも使わない(LED は 1 個で、状態の表示に使い切っている)
- 実行の間(RUNNING と AWAITING)に USB の切断かサスペンドを見つけたら、実行を停止し、全入力を離し、停止した位置を記録して ERROR にする。選択待ちで止まっている間に Switch がスリープしても、続きの入力は本体に送られないので同じにする

## 設計判断

- **OTA の分割転送**: action が begin で始め(size に全体の大きさを書く)、4096 バイトずつ data で送り(blob に更新のデータを格納する)、end で検証して再起動する。途中でやめるときは abort を送る。始めた接続が切れたときも同じく中断する。途中から続きを送る仕組みは持たない。1MB 弱の転送は数秒で終わり、失敗しても A/B のもう一方のパーティションのファームウェアがそのまま動くので、最初からやり直せば済む
- 手動操作の形式: 1 回の PASSTHRU に全入力の状態を含めて、毎秒最大 30 回送る。前の状態からの差分だけを送る方式は採用しない。すべてを含めれば、取りこぼしても次の 1 回で正しい状態に戻る
