# 装置へ送る手順データの形式と実行モデル

手順の保存形式は file-format.md が定める。この文書は、それを変換して装置へ送るバイナリの形式と、装置がそれをどう実行するか(何が、いつ送られるか)を定める。

## 方針

- 時間はフレームを単位とする整数で表す。フレーム周期の整数倍でない長さは、ゲームが入力を読む位相への依存を残すからである(P8、hardware-design.md §1-3)。フレーム周期そのものは装置の設定で、ナノ秒の整数で持つ(comm-protocol.md の CONFIG)
- 装置へは変換を済ませた形を送る。実行しながら手順の文面を解釈すると、その処理が送信の時刻を決める経路に入るからである(P3)
- 別の手順の呼び出しと、回数だけで決まる選択は、変換のときに展開する。装置が実行中に行う判定は、くり返しの回数を数えること(SETCNT と DJNZ)と、選択待ち(AWAIT)だけである(P16)
- 時刻は開始からの絶対時刻で計算する(P8、hardware-design.md §1-4)
- 手順の意味は、各フレームのすべての入力の状態の並びである(P7、concepts.md §4)。押し続ける入力やスティックの状態は、くり返しの境界を暗黙にまたがない。くり返しの先頭では、くり返しに入る前の状態に戻る

## バイナリ形式

装置は手順を、名前ではなく中身から決まる id で保存し、参照する(P23)。id はこのバイナリの SHA-256 の先頭 16 バイト(16 進で 32 桁、128 ビット)である。装置はファイル名を `<id>.bin` にし、人の読む名前は持たない(名前とメモは PC の側だけが持つ)。同じ中身なら同じ id になるので重複は生まれず、中身が変われば別の id になる。装置は書き込むときに、同じ id のものがあれば中身を比べる。違えば、置いてあるファイルの中身から id を計算し直し、合わなければ(書いている途中で電源が切れたファイルなど)書き直し、合えば拒否する。128 ビットが衝突する確率は無視できるほど小さいが、比べれば、衝突しても別の中身と混同しない。実行(RUN)で読むときも中身の id を確かめ、合わなければそのファイルを消して、見つからないものとして答える。名前を装置へ送らないので、名前の長さは装置の制約を受けない。

**ヘッダー(18B)**: 次の 5 つの欄を、この順にリトルエンディアンで並べる。

| バイト | 欄 | 型 | 意味 |
|---|---|---|---|
| 0..3 | magic | 4B | `PDT0` |
| 4..5 | schema | u16 | 形式のバージョン |
| 6..9 | event_count | u32 | レコードの数 |
| 10..13 | total_frames | u32 | 実行全体の総フレーム数(周回数のぶんを含む) |
| 14..17 | crc32 | u32 | 整合性のチェックの値(下の「整合性検証」) |

total_frames の 0 は総量なしを表す。選択待ちになる選択肢の外に無限のくり返しを含む手順と、選択待ちになる選択肢の中身を長さ 0 とみなしたときの長さが 0 の手順(操作をすべて選択肢の中に書いた手順など)がこれになる。選択待ちになる選択肢の中にだけ無限のくり返しがある手順は、その選択肢を選ばなければ終わるので、総量を持つ。装置はこの値をそのまま進捗の総量に使う。

schema はこの形式のバージョンで、いまは 1 である。復号は、バージョンの違う手順データを拒否する。バージョンを上げるのは、同じバイト列を別の意味に読む変更と、変換器が新しい形を出し始める変更である。変換器が出さない形を拒否するだけの変更(使わない命令を外すなど)では上げない。変換器がそれまでに出した手順データは、変更の後も同じ意味に読めるからである。

**整合性検証**: crc32 は、ヘッダーのうち crc 欄を除いた部分と、レコード部を対象にする。ヘッダーを含めるのは、total_frames が周回の時刻に直接使われる値で、ヘッダーのビット化けも見つける必要があるからである。復号は次のことを確認し、合わなければ手順データを拒否する(Python の参照実装では DecodeError を出す)。C 実装も同じ検証を必須とする。

- magic が `PDT0` で、schema が復号のバージョンと同じであること
- CRC が合うこと
- レコード部の長さが、event_count 件ぶんであること
- どのジャンプ先も、0 以上 event_count 未満であること
- 時間を消費しない閉路がないこと。後方への DJNZ は、advance が 1 以上のものか、飛び先から自分までの間に時間を進めるもの(advance が 1 以上の DJNZ か AWAIT)があるものだけを通す。AWAIT と ARMJOIN の飛び先は前方だけである

手順全体を囲むくり返しの DJNZ は advance が 0 になるが、1 周ぶんの時刻は中のくり返しが進めるので、この形は通る。実行する側も、1 回のアラームで適用する、時刻を進めないレコードを 64 件までとする。チェックを通ってしまった手順でも、割り込みが戻らなくならないようにするためである(firmware-architecture.md §3)。

**イベントレコード**(32B 固定長): どのレコードもバイト 0..4 とバイト 31 が共通で、間の 26 バイト(バイト 5..30)を opcode ごとに使う。

| バイト | 欄 | 型 | 意味 |
|---|---|---|---|
| 0..3 | frame | u32 | 時刻の基準(base)からの相対フレーム |
| 4 | opcode | u8 | 命令の種類 |
| 5..30 | 本体 | 可変 | opcode ごとの中身 |
| 31 | mark | u8 | 区切りのマーク |

opcode は STATE=1、SETCNT=2、DJNZ=3、END=4、AWAIT=5(選択待ち)、ARMJOIN=6(選択肢の終わり)である。これ以外の番号は、復号が拒否する。制御フローの命令(SETCNT、DJNZ、END、ARMJOIN)は frame を使わず、0 を書く。使わないバイトにも 0 を書く。本体(バイト 5..30)の中身は opcode ごとに次のとおりである。

- STATE: buttons u32、L スティック 3B、R スティック 3B(各 12bit を 2 軸ぶん Pro コントローラー形式で詰める)、ジャイロ i16 を 3 軸、加速度 i16 を 3 軸(バイト 5..26)
- SETCNT: counter u8、value u32
- DJNZ: counter u8、target u32、advance u32
- END: 中身はない
- AWAIT: 下の「AWAIT レコード」のとおり
- ARMJOIN: target u32、delta u32

mark(バイト 31)は区切りのマークで、ビットの論理和で持つ。0x01 がラベル、0x02 が周の境、0x04 が選択待ちである。マークが付くのは STATE と AWAIT だけで、ほかのレコードは 0 を書く。復号は、未知のビットが立ったレコードと、マークを持たない opcode で末尾が 0 でないレコードを拒否する(C 実装も同じ検証を必須とする)。マークは時刻にも制御の流れにも影響しない。同じフレームのレコードが統合されるときは、マークを論理和で残す。装置は「マーク付きレコードの予定時刻に、そのレコードを出さずに全入力を離して待機へ移る」という 1 つの規則で「区切りで停止」を実現する。

変換器がマークを置くのは 5 か所である。ラベルの STATE、周回数のくり返しの各回の先頭の STATE(その DJNZ の飛び先)、そのくり返しを抜けた直後の STATE、AWAIT と、1 台のグループで AWAIT を省いた合流点の STATE である。抜けた直後に STATE がなければ、時間を進めない STATE を 1 つ置いて目印にするので、周回数のくり返しの DJNZ の後ろには STATE が 1 つ続く。周回数が無限の変換は例外で、くり返しを抜けることがないので、この STATE を置かない。DJNZ の後ろは END になり、くり返しの後ろのブロックも変換に入らない。マークが付いた STATE は、くり返しの先頭で同一フレームの過渡状態として取り除く対象から外す。取り除いて本体の先頭へマークを移すと、1 点しかないはずの区切りがくり返しの回ごとに現れるためである。

**AWAIT レコード**: frame は待ち始める相対フレームである。本体は、バイト 5..8 が timeout_frames u32(時間切れまでのフレーム数。0 は時間切れなし)、バイト 9 が on_timeout u8(時間切れで進む選択肢の番号 1..n。時間切れがなければ 0)である。選択肢の数 n はバイト 10 の u8、飛び先はバイト 11..30 の u16 を 10 本である。使わない飛び先には 0 を書く。

飛び先を u16 にするのは、32B のレコードに収まる飛び先の数を最大にするためである。装置に保存できるレコードは 3071 件なので、番号は u16 に収まる。

装置はここでタイマーを停止し、PC の SELECT を待つ。入力は変えない。待つ間に全入力を離すときは、変換器が AWAIT の直前に、同じ時刻の全入力を離した STATE を置く(手順の側の「待つ間の入力」。file-format.md §5)。

時間切れがあるのに on_timeout が 0 のもの、n を超えるもの、時間切れがないのに on_timeout が 0 でないものは、復号が拒否する。

時間切れは、装置の監視のタスクが 100ms ごとに確認する。数え始めるのは、そのタスクが選択待ちを最初に見たときなので、時間切れの選択肢へ進むのは、書いた長さより最大で約 200ms 遅れる。時間切れは、来ない相手や選ばれない選択を待ち続けないための上限であり、フレーム単位の精度は持たせない。

待った時間はエンジンの時計に含まれないので、予定時刻の修正は不要で、待った長さは以後の時刻の精度に影響しない。飛び先は前方だけである。後方を許すと、時間を消費しない閉路ができるからである。

合流点とスクリプトも AWAIT である。どちらも装置から見れば選択肢が 1 本の選択待ちにすぎず、決めるのは PC である。合流点は、グループの相手のレーンが同じ名前の合流点へ来たら PC が SELECT を送る。名前は装置へ送らない。時間切れを書いてあれば、その長さで 1 本しかない選択肢へ進む(相手が来なくても止まったままにならない)。1 台のグループで開始したときは待つ相手がいないので、変換が AWAIT を省き、0 フレームで待たずに通過する。ただし区切りのマーク(MARK_AWAIT)は残す。残さないと、同じ手順でもグループの台数で「区切りで停止」の停止する位置が変わり、編集画面に見えている切れ目でも停止しなくなる。増えるレコードは合流点 1 つにつき多くても 1 件で、同じフレームに STATE が既にあれば、新しいレコードは置かずに、その STATE のマークに論理和で加える。

**ARMJOIN レコード**: 本体は target u32 と delta u32 である。選択肢の末尾に置き、実行時に `shift += delta; idx = target` とする。STATE は出さず、時刻だけを動かす。送信の時刻はどのレコードも `emit = base + frame + shift` で、選択肢ごとの長さの違いは整数の `shift` だけに足し込む。delta はその選択肢の長さである。こうして、時刻を開始からの絶対時刻の整数で保つ(hardware-design.md §1-4)。選択肢の後ろに共有する続き(target が指す合流先)は、選択肢を長さ 0 とみなして、AWAIT と同じ frame から 1 回だけ置く。くり返しの中でも、`DJNZ.advance` は選択肢を長さ 0 とみなしたときの本体の長さであり、選択肢の長さの違いは shift が吸収する。選択待ちを含まないくり返しの中では shift が変わらないので、各回の送信の時刻は frame と advance だけで決まる。入れ子の選択待ちや、続けて通った選択待ちの長さは、通った選択肢の delta の和として shift に積み重なる。飛び先は前方だけである(AWAIT と同じ理由)。

**位置からの開始**: 装置は開始位置を受け取らない。実行は必ず先頭のレコードから始まる。途中の位置から始めるときは、その位置から続く手順を PC 側が合成し、別の手順データとして転送する。周回数と同じく、位置が違えば内容が違うので別の id になる。

開始位置は {path, block, turns} で表す。path は一番上の手順から位置のあるファイルまでの「別の手順」のブロックの識別子の列、block はそこから始めるブロックの識別子(空文字は手順の先頭)、turns は位置を囲むくり返しの何回目かを外側から順に並べたものである。書かなかったぶんは 1 回目とみなす。block がくり返しのブロックのときは「そのくり返しの、指した回の先頭」を指し、周回の境界で停止した位置はこの形になる。変換器が出力する開始位置の一覧は、先頭と名前の付いたラベルのすべてで、くり返しの中も選択肢の中も出る。ただし、実行されない「それ以外」の中のラベルは出さない(file-format.md §7)。

合成した手順は、位置の直前の状態を置く先頭の STATE(frame 0)で始まり、位置から今の回の終わりまでが続く。その後ろに、内側のくり返しから順に、そのくり返しの残りの完全な回(SETCNT と本体と DJNZ)と、そのくり返しより後ろの続きを置く。実行の順がそうだからである。例えば手順が `[A, L1 {B, L2 {C, 位置, D}, E}, F]` で、位置が L1 の k1 回目、L2 の k2 回目にあるとき、合成した手順は次の並びになる。

```text
STATE(位置の直前の状態), D, L2 の k2+1 回目から最後の回まで, E,
L1 の k1+1 回目から最後の回まで, F
```

位置が k 回目にあるとき、残りの回は k+1 回目から総回数までを対象に「対象の回」の展開をやり直すので、回番号は先頭から通した場合と同じ絶対の番号になる。残りが 1 回のときも、周回数のくり返しであれば SETCNT と DJNZ を置く。回数が 1 のくり返しは普通なら本体だけを並べるが、周回数のくり返しではこの 2 つが周回のカウンターそのもので、進捗表示の元になるからである。ただし「対象の回」で区間に分かれたときは、回数が 1 の区間は本体だけになる。

**生値原則**: スティックとモーションは、変換を掛けない整数の生値で持つ。スティックは中心 0 の符号付き 12bit(-2048..+2047。X は左が負、Y は下が負)である。ワイヤ形式(0..4095)へは 2048 を足すだけの 1 対 1 の対応で、+1 が送信できる最小の単位にあたる。正の側が 1 つ少ないのは、ワイヤが 4096 段階で偶数だからである。バイナリには、値に 2048 を足したワイヤ形式で格納する。

ジャイロと加速度は、各軸 i16 のセンサーの生値である。加速度の「指定なし」は 0 ではなく、静止姿勢の `(0, 0, 4096)`(1G)である。加速度センサーは重力も測り、全軸 0 は自由落下で、実機にはない状態だからである。生値原則は「変換を掛けない」ことであって、「既定値を 0 にする」ことではない。0 を明示すれば 0 がそのまま送られる。

% や方向名のような見せ方と書き方は上位層(画面と変換器)が担当し、装置へは生値だけを送る。例えば編集画面は、スティックの生値に「右上 50%」のような向きと強さを付けて見せる。生値の直接の入力と表示は常にできるようにする。キャリブレーション応答(サブコマンド 0x10)は、直線の対応になるように装置の側で定義し、経路の途中で分解能を落とさない。

**実行モデル**: 時刻は開始からの絶対時刻で計算する(hardware-design.md §1-4)。

- 実行エンジンは、時刻の基準 base と、通った選択肢の長さの合計 shift を持つ。どちらも整数のフレーム数である。STATE は、絶対時刻 `開始時刻 + (base + frame + shift) * 周期` に出力する
- **DJNZ**: カウンターを 1 減らし、0 より大きければ target へ飛ぶ。飛んでも飛ばなくても、base に advance(くり返し 1 回ぶんの時刻の進み)を足す。base は整数の演算だけで進むので、タイマーの誤差は積み重ならない。SETCNT を通っていないカウンターか、回数を使い切った(0 の)カウンターの DJNZ に来たら、手順データの異常として停止する(装置は PADEMU_ERR_COUNTER、参照実装は EngineError)。0 から減らすと、32 ビットで数える装置では回り込んで約 42 億回くり返すからである。変換器はこの形を作らない
- **SETCNT**: カウンターに回数を入れる。値 0xFFFFFFFF は無限を表す(装置は 1 ずつ減らすだけで、実際には尽きない)。値 0 は復号が拒否する
- 周回はイベント列の中にある。変換器は、周回数のくり返しを書いていない手順では手順全体を SETCNT と DJNZ で囲み、書いてある手順ではそのくり返しの回数に周回数を入れる。周回数が違えば内容が違うので、別の id の手順データになる。装置は周回を数える仕組みを持たない。何周目かは、装置が返す「最後に通った区切り」と、変換のときに作った対応表から PC が出す(comm-protocol.md の STATUS)
- **END**: 手順の終わりである。ここで実行は終わり、先頭へは戻らない。END は時刻を持たないので、実行は直前のレコードを出したところで終わる。

  変換器は、手順の終わりの時刻に STATE がなければ、END の直前にその時刻の STATE を 1 つ置く。手順が待ちで終わっても、その待ちのぶんまで実行してから終わる。

  中に無限のくり返しがある手順にも置く。このときの終わりの時刻は、無限のくり返しを 1 回と数えた長さで、その後ろのブロック(変換に入らない)は数えない。装置はこの STATE に到達しないが、PC は無限のくり返しを 1 回として 1 周の図を描くので、図の右端にこの STATE を使う。置かないのは、周回数が無限で、かつ変換の中に無限のくり返し(無限の回数になった周回数のくり返しを含む)がある変換だけである。終わりに到達せず、図にも使わないからである。周回数のくり返しより後ろから始める続きは、ほかに無限のくり返しがなければ、周回数が無限でも終わりに到達するので置く
- STATE は全状態のスナップショットで、差分ではない。出力の状態が変わるのは STATE の時点だけで、くり返しは同じスナップショットの列を、base をずらして再生する
- 制御フローの命令はフレームを消費しない。判定はマイクロ秒の単位で済むので、R1 を損なわない
- **ブロックの自己完結性**: 変換器は、手順の frame 0 と、くり返しの中身の先頭に、全状態のスナップショットを置く。このため、実行の始まりと、くり返しの各回の始まりの出力は、手順データだけで決まり、直前の実行の状態に依らない
- **同一フレームの統合**: 同じフレームの中の複数の状態の変更は、後に書いたものを優先して 1 つの STATE にまとめる。統合は制御フローの命令をまたがない。くり返しの先頭では、直前にある同じフレームの STATE を、本体の先頭のスナップショットで置き換える

**参照実装**: `pctool/padcue/engine.py` が、この実行モデルを実行できる形で定義する。ファームウェアの C 実装は、同じバイナリに対する出力の列(フレーム番号と状態)がこれと完全に一致することで検証する(`pctool/tests/test_firmware_core.py`)。

## 変換が出す拒否と警告

変換が拒否する形と、警告にとどめる形の一覧は、file-format.md の 8-2 と 8-3 にある。この文書の形式から来る制約は次の 2 つである。

- レコード数が装置の保存容量を超える手順は、変換が拒否する。上限は 3071 件である。96KiB = 98304 バイトからヘッダーの 18 バイトを引き、1 件 32 バイトで割った商である(file-format.md §8-2)
- 1 回が時間を進めないくり返し(時間を進めるレコードも AWAIT もないもの)は、変換が拒否する。装置の上で、時間を消費しない閉路になるからである

1 フレームの長さの入力は、ゲームに読まれないことがある(hardware-design.md §1-2)。変換は警告せず、編集画面が、長さを 1 にした欄の下で知らせる。

## 設計判断

- **モーション値の表現**: i16 の生値だけで表す。書く側は、フレーム表の列(フレームごとの値)と、それを短く書くジャイロのブロック(速さと長さ)を使う。角度で書く形(「30 フレームで 90 度」)は採用しない。ゲームは入力に補正(平滑化、不感帯、加速の曲線)を掛けるのが普通で、生値とフレーム数の積から画面の回転角への対応が線形にならない。線形でなければ角度を生値へ変換する 1 つの係数はなく、角度で書けても意味を持たない。ゲームごとに実測する手間と、外れたときの分かりにくさが、得られる手軽さに見合わない
- **スティックの座標**: 12bit の生値で表す(生値原則)
- **分岐の詳細仕様**: 「分岐」ブロックの仕様は file-format.md §5 にある(くり返しの中にも置け、複数でも入れ子でもよい。選択肢は AWAIT 1 つあたり最大 10 本)。この文書の形式では、AWAIT と ARMJOIN のレコードとして現れる。選択肢の「選択条件」は PC 側だけが持つ情報で、AWAIT レコードにも実行エンジンにも影響しない
- 周回と手順の境界で入力が重なっても知らせない。くり返しの末尾と次の回の先頭、手順の末尾と次の周の先頭が同じフレームで重なると、末尾の入力は次の先頭で上書きされる。これはブロックの意味(P7)のとおりで、押し続けたまま次の操作へ移る使い方もあるので、害があるかは手順を書いた人にしか分からない
