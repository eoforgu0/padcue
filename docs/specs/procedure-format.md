# 手順データ仕様 v0

状態: **実装済み**。手順の正本形式は flow-format.md で、
本文書はその実行モデル(何がいつ送られるか)を定める。個々の取り決めと
その理由は末尾にまとめてある。

## 設計原則(設計文書からの制約)

- 時間は常に**フレーム単位の整数**(A-2: 非整数フレーム時間は位相依存を残すため)。
  フレーム周期そのものはデバイス側設定(µs 連続値)
- PC 上の正本はテキスト DSL。デバイスへは**コンパイル済みバイナリ**を転送(実行時
  パースをタイミング経路に置かない)
- 実行時の判定は RAM 内カウンタ+ジャンプのみ(µs、7.5 の内部分岐)。サブルーチンは**コ
  ンパイル時に展開**
- スケジューリングは開始時刻からの絶対時刻(A-3)
- **ブロック(状態関数)意味論**: 手順およびループ本体は「区間内
  の全フレームの入力状態を完全に定義する自己完結ブロック」であり、反復はブロック
  の**正確な再生**である。持続状態(hold/stick)はブロック境界を暗黙に越えない(周
  回の先頭では本体開始時点の状態に戻る。周回をまたいで維持するには loop の前で設
  定する)。これは行列方式(1行=1フレーム・完全状態)の一般化であり、イベント持続方
  式で生じる隠れ状態バグを構造的に排除する。
  press/hold 等の命令は毎フレーム状態を生成する省略記法にすぎない

## DSL(テキスト、1行1命令)

```text
# コメント
proc farm_loop                 # 手順名
pre "祠の前でメニューを閉じ、カメラ北向き"   # 前提条件メモ(実行前に表示される)

press A 2                      # A を 2 フレーム押して離す
press A+B 2                    # 同時押し
hold ZL                        # 押しっぱなし開始(明示 release まで)
release ZL
wait 30                        # 30 フレーム待機(全状態は維持)
stick L -1200 0                # 左へ約6割倒す。生値 (x,y): -2048..+2047、中心 0、左と下が負
stick L up                     # 方向プリセット: neutral / up / down / left / right
loop 500 {                     # 制御フロー命令にコンパイル(展開しない)
  call collect_item            # サブルーチン呼び出し(コンパイル時に展開)
  wait 60
}
end
```

- ボタン名: A B X Y L R ZL ZR PLUS MINUS HOME CAPTURE LS RS DU DD DL DR(十字キー)
- モーション(ジャイロ/加速度)の書き方は3つ: DSL の
  `gyro <ひねり> <上下> <水平> [フレーム数]`、フローの gyro ノード、部品の
  GP/GY/GR/AX/AY/AZ 列
- 外部分岐の待機点は `wait_branch` として実装済み(タイムアウトと待機中の全
  ニュートラル出力を含む)。仕様は flow-format.md §6

## バイナリ形式

**ヘッダ(50B)**: magic "PDT0" / schema_version u16 / name(UTF-8, 32B) /
event_count u32 / **total_frames u32(手順1周の総フレーム数)** / crc32

**整合性検証**: crc32 は**ヘッダ(crc 欄を除く)+レコード部**を対象とする
(total_frames は周回タイミングが直接依存する値であり、ヘッダのビット化けも検出す
る必要があるため)。decode は CRC・レコード長・**全ジャンプ先の範囲(0 ≤ target <
event_count)**・手順名の UTF-8 正当性に加え、**時間非消費の閉路がないこと**(後方
JMP は禁止、後方 DJNZ は advance ≥ 1 必須)を検証し、違反は DecodeError とする(C
実装も同じ検証を必須とする)。実行側にも多層防御として「1アラームあたりの時間非消
費イベント適用数の上限(64)」を置く(firmware-architecture.md §2)

**AWAIT レコード**: frame(待ち始める相対フレーム)/ timeout_frames u32 /
on_timeout u8(0=中断、1..n=その選択肢へ)/ 選択肢の数 u8 / 飛び先 u32×4。
デバイスはここで**全ニュートラルにしてタイマーを止め**、PC の SELECT を待つ。
**待った時間はエンジンの時計から丸ごと抜ける**ので、予定時刻の付け替えは
要らない(待った長さは精度に影響しない)。飛び先は前方のみ(時間を消費
しない閉路を作らない)

**再開点(部分実行)**: 実行の開始位置は任意 index ではなく、コンパイラが出力する**再
開点表**({name, index, base, frame}。**トップレベルのラベルがそのまま再開点**に
なり、そこには全状態スナップショットが置かれる)から選ぶ。

デバイスは範囲と「**そこから最初に到達する時間消費イベントが STATE であること**」
を検証する。SETCNT(くり返しのカウンタ初期化)は時間を消費しないので手前に挟まって
よい — ラベルをくり返しの直前に置くと再開点は必ず SETCNT を指すため、ここを
STATE のみに限ると「くり返しの直前のラベルからは実行できない」ことになる。

**再開点は時刻 0 に寄せる**。飛ばした前半ぶんの絶対時刻をそのまま使うと、実行開
始から前半の長さぶん何も出さずに待つことになる(「回収」から試したいのに 3.5 秒動
かない)。デバイスは再開点の絶対フレーム(= base + その STATE の frame)を全送出時
刻から引く。周回数を 2 以上にした場合も**各周回がその位置から始まる**(区間の繰り
返し)。1 周の長さは `total_frames - 引いた量`。

この計算は PC 側の参照エンジンとデバイス側で一致していること(`test_resume.py` が
送出列の完全一致で検証する)。

**イベントレコード(32B 固定長、schema v2)**:

| フィールド | 型          | 意味                                                                                                                                                                                                               |
|------------|-------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| frame      | u32         | **セグメント基準の相対フレーム**(制御フロー命令では未使用=0)                                                                                                                                                       |
| opcode     | u8          | STATE=1 / SETCNT=2 / DJNZ=3 / JMP=4 / END=5 / **AWAIT=6**(待機分岐)                                                                                                                                                |
| 残り 27B   | opcode 依存 | STATE: buttons u32 + Lスティック 3B + Rスティック 3B(各 12bit×2軸のプロコン形式詰め)+ ジャイロ i16×3 + 加速度 i16×3。SETCNT: counter u8, value u32。DJNZ: counter u8, target u32, **advance u32**。JMP: target u32 |

**生値原則**: スティック・モーションは**無変換の整数生値**で持つ。ス
ティックは**中心 0 の符号付き 12bit(-2048..+2047。X は左が負、Y は下が負)**。ワ
イヤ形式(0..4095)へは +2048 するだけの 1:1 対応で、**+1 = 送信分解能の最小刻み**(±
が非対称なのはワイヤが 4096 段階=偶数のため。バイナリへの格納は値+2048 のワイヤ
形式)。ジャイロ・加速度は各軸 i16 のセンサー生値。**加速度の「指定なし」は 0 で
はなく静止姿勢 (0, 0, 4096) = 1G**(加速度センサーは重力も測るため。全軸 0 は自由
落下で実機には無い状態)。生値原則は「変換を掛けない」ことであって「既定値を 0 に
する」ことではない。0 を明示すれば 0 がそのまま送られる。% や角度・方向名などの
便利表記はすべて生値への変換の糖衣構文として上位層(GUI/コンパイラ)で扱い、生値の直接入
力・表示を常に可能とする。キャリブレーション応答(サブコマンド 0x10)は自作側が直
線マッピングになるよう定義し、経路上で刻みを潰さない。HID ゲームパッド方式(保険
モード)はスティック 8bit(値>>4 の 256 段階)・モーション非対応であり、分解能ギリ
ギリの精密検証はプロコン方式の成立が前提となる

**実行モデル(時刻の扱い、A-3 適合)**

- 実行エンジンは時刻基準 **base**(整数フレーム)を持ち、STATE を絶対時刻「開始時
  刻 + (base + frame) × 周期」で送出する
- **DJNZ**: カウンタをデクリメントし、>0 なら target へジャンプ。**成立・不成立
  にかかわらず base += advance**(ループ1周ぶんの時刻進行)。base は整数演算のみで
  進み、タイマー誤差は蓄積しない
- **END**: 手順1周の終了。RUN 指示の loop_n(セッション周回数)が残っていれば base
  を「周回開始 + total_frames」に合わせて先頭から再実行する。区切り停止
  (graceful)はこの境界で効く
- STATE は全状態のスナップショット(差分ではない)。**出力状態が変わるのは STATE
  イベントの時点のみ**で、ループは同じスナップショット列を base をずらして再生す
  る
- 制御フロー命令はフレームを消費しない(判定 µs、R1 非毀損)。周回カウンタは実行状
  態としてクエリ可能(進捗表示に使用)
- **ブロックの自己完結性**: コンパイラは手順の frame 0 とループ本体の先頭に必ず
  全状態スナップショットを挿入する。したがって各周回・各セッション周は手順データ
  の定義のみで決まり、直前の実行状態に依存しない
- **同一フレームの統合**: 同一フレーム内の複数の状態変更は後勝ちで単一 STATE に
  統合する(統合は制御フロー命令を跨がない。ループ入口では直前の同一フレーム
  STATE を本体先頭スナップショットが置換する)。RUN の loop_n は **0 = 止める
  まで無限にくり返す**(`pademu_core.c` の `pademu_engine_init_at`)

**参照実装**: `pctool/padcue/engine.py` が本実行モデルの実行可能な定義。ファーム
ウェアの C 実装は「同一バイナリに対する送出列(フレーム番号+状態)の完全一致」で検
証する

## リント

**警告**(`# lint:allow-<名前>` で個別抑制可):

- **1 フレーム長**の押下・待機・ジャイロ(A-1: 指示 N に対し実際は N−1〜N+1。N=1
  では下限が 0 になり**まったく現れない**ことがある。境界あたり最大約 6%。
  `allow-1f`)
  - 2 フレーム以上は下限が 1 以上なので「現れない」ことは起きない(長さが ±1 フレー
    ムぶれるのは残る)。過剰な警告を避けるため 2 フレーム以上は警告しない
- 同一フレーム内で打ち消された押下・上書きされたスティック値(0フレーム=出力に一
  切現れない操作)
- ループ本体が入力状態を変えたまま終わる(周回先頭で本体開始時点へ巻き戻る。
  `allow-loop-reset`)
- ジャイロが一定値のまま 60F 以上続く(Switch 側のゼロ点自動較正に吸収され、回転
  停止と逆回転が起きる。実測。`allow-gyro-const`)。ループ・分岐の境界
  をまたぐ定常は境界ごとに測り直すため過小評価があり得る(直線的な手順は正しく検
  出)
- ループ末尾の入力と次の周回の先頭の入力が同一フレームに衝突する(余裕 0)
- 手順末尾の入力変化が終端フレームちょうどにある(セッション周回 loop_n>1 で衝突)

**エラー**: 未定義ボタン・範囲外スティック値・call の循環と未定義呼び出し(**未使
用 proc も含め全 proc を検証**)・時間を消費しないループ本体(n>1)・u32 超過(行番
号つきで報告)・pre の位置違反(proc 直後に1回のみ)

## 設計上の取り決め

- **モーション値の表現** → **i16 生値のみ**。作成側は行列の列(毎フレーム値)
  と、その糖衣構文である gyro ブロック/DSL 命令(速さ+長さ)。角度指定(「30F で 90°」)
  は**採用しない** — ゲーム側が入力に補正(平滑化・不感帯・加速カーブ)を掛けるの
  が普通で、「生値×フレーム数 → 画面の回転角」が線形にならない。線形でない以上単
  一の係数は存在せず、角度で書けても意味を持たない。得られる利便に対して、ゲーム
  ごとの実測作業と外れたときの分かりにくさが見合わない
- **スティックの物理座標系** → 12bit 生値(生値原則を参照)
- **checkpoint(待機あり分岐)の詳細仕様** → `wait_branch` として確定。仕様は
  flow-format.md §6(選択肢ごとに分岐より後ろの続きを展開する方式。トップレベル限定・
  入れ子不可・選択肢は最大4本)。本文書の側では AWAIT イベントとして現れる
- **フロー層の正本** → 入れ子の構造化データ(JSON。flow-format.md)。本 DSL
  テキストは実行経路では使わず、コンパイラ本体の可読な入力として維持する
